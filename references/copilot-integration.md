# 协作契约 · DesignWise 与 Copilot 的接口

> **读这份文档的时机**：一项设计任务的**验收承诺、跨方依赖或未闭合缺口需要跨交接持续跟踪**时；
> 或要把设计成果登记进 Copilot 的任务与证据时。
> **不读的时机**：局部修正、已有设计系统下的小改动、只做素材或只做评审且能就地验收——按 `SKILL.md` 直接做。
> **立场**：Copilot 管治理，DesignWise 管设计方法与专业验收，ZCode 是唯一执行与技术决策主体，
> Astra 只给意见。本文是四者在**交界处**交换什么、何时交换、谁对结果负责的唯一说明；
> 它不规定设计方法、不推进设计阶段、不保存任务状态。

---

## 1. 职责与准入

### 1.1 边界（不重叠、不互借）

| 角色 | 唯一权威 | 不做什么 |
|---|---|---|
| 用户 / ChatGPT 侧 | 业务目标、优先级、重大取舍、最终产品与设计验收 | 不做设计实施 |
| ZCode 主 Agent | 工程执行与技术决策、调度（含判断是否入管） | 不代替用户做业务取舍 |
| Copilot | 任务合同、完成条件、工作项、状态、证据登记、收口 | **不做设计判断、不做设计裁决**，不替代技术决策 |
| DesignWise（本 skill） | 设计方法、判据、产物契约、专业设计验收 | 不建任务状态、不登记证据、不调度 |
| Astra（经 Copilot 认知通道） | 对具体难题的认知意见 | 不做工程、不读仓库、不批准也不否决 |

一句话：**任务状态只在 Copilot；设计结论只在 DesignWise 的产物与验收里；工程事实以 ZCode 现场为准；认知只是意见。**
本表展开 `SKILL.md` §1 的角色边界；口径冲突时以 `SKILL.md` 为准。

### 1.2 准入：问两个问题，不是对照清单

1. 具体是**哪一项**验收承诺 / 跨方依赖 / 未闭合缺口需要跨交接持续跟踪？（要能指名对象）
2. **为什么本次就地设计验收闭合不了它？**

两问都成立才进入 Copilot；任一为否就由本 skill 直接做，照常留证据，不建合同。

| 有可指名的跟踪对象 | 就地验收能闭合 | 结果 |
|---|---|---|
| 否 | — | **不建合同**：按 `SKILL.md` 阶段与门直接做，证据留在设计产物里 |
| 是 | 是 | **不建合同**：就地闭合并把闭合证据写进产物记录 |
| 是 | 否 | **进入 Copilot**：建合同与完成条件，设计产物按 §2 关联证据 |
| 是 | 否，且方案仍有实质分歧或证据冲突 | 进入 Copilot，并按 §4 判断是否咨询 Astra（两者相互独立） |

**示例只用于校准，不构成白名单**：

- 一只按钮按既定规范调色、验收标准不变 → 就地做，不入管。
- 同一调色改变了多方约定的通过标准、需要协调复验 → 入管；方案明确则**不调 Astra**。
- 整机改版但验收标准与责任方都明确、单会话可完成 → 工作量不等于治理需求；用户要求或需跨会话恢复时才入管。
- 单个图标却改变了对外素材的一致性承诺 → 入管（改动小，治理需求真实）。

**不构成准入理由**：改动文件多或少、交付物是 PNG 还是 Markdown、任务名称叫"改版"、想多一次模型意见、
想让外部模型批准设计。**用户明确要求使用 Copilot 时直接入管**，不受两问限制。

## 2. 合同与证据

### 2.1 设计信息落在合同哪里

不新增合同结构：设计信息写进 Copilot 合同正文与既有完成条件。

| 设计信息 | 落点 | 不落 |
|---|---|---|
| 设计目标与要解决的问题 | 合同正文「目标」 | — |
| 产品定位与用户场景 | 合同正文背景（各一句） | 不写完整 brief |
| 页面/模块/状态范围（`P*`/`S*`/`X*`） | 合同正文「范围」+ 产物路径 | 不复制地图 |
| 品牌/平台/技术/业务约束 | 合同正文「约束」 | — |
| 设计交付物 | 合同正文「交付物」= 真实路径 | 不贴二进制 |
| 验收（设计与工程分开） | **完成条件**：可观察、可判定、写明归属 | 不写"看起来好" |
| 明确不允许改变的内容 | 合同正文「不改什么」 | — |

验收条件必须可观察：写「`coverage.json` 中 `P1`/`P3` 的 `device` 全为 `pass`，未测项显式 `not-tested` 并说明原因」，
而不是「页面通过评审」。`not-tested` 是**如实标注未测**，只在本次验收确实无法执行时使用；**没有实现的项仍保持
`native: todo` 并让整体算 `PARTIAL`，不得改标 `not-applicable`/`not-tested` 去满足条件**（`not-applicable`
只表示产品本身不存在该页/状态）。设计条件与工程条件分开列，不互相顶替。

### 2.2 产物 → 证据：引用，不复制

| 治理要回答的 | 引用什么 | 登记方式 |
|---|---|---|
| 哪项决定、谁作出 | `direction-approved.md` 的决策段 | `evidence --add --file <路径>` |
| 依据哪份材料 | `design-brief.md` / `concept-index.json` / `direction-divergence.json` | 同上（文件型证据带 sha256） |
| 设计产物在哪 | `prototype/index.html`、`prototype/screenshots/`、`handoff/` | 同上，或用 `--capture-cmd` 记录渲染/校验命令的真实输出 |
| 设计是否验收 | `prototype-notes.md` 评审记录、`verification-report.md` 的双验收结论 | 同上 |
| 覆盖是否闭合 | `coverage.json` | 同上，配合 `check-deliverables.py` 的输出 |

规则：

- **先登记后引用**：`criterion` / `record` 引用的证据必须是本任务已登记、未归档的 `E<n>`。
- **不复制**图片、源码、日志进任务状态：视觉材料的真身留在设计产物目录；`cognition-consult --image`
  时 Copilot 只记 sha256、尺寸与说明。
- **一条条件不靠两份材料**：同一份证据不能同时证明设计验收与工程验收，两类结论分开登记。
- 证据要能说明「哪项决定由谁作出、该产物支持哪条标准、还缺什么」；只有截图路径或只有 `E<n>` 都不够。

### 2.3 不新建的东西

不建第二套任务状态，不建 DesignWise 自己的证据库或登记表，不向 Copilot `state.json` 假设自定义字段，
不复制 Copilot 命令手册。命令与参数以 Copilot **当前版本**为准（`~/.zcode/skills/copilot/`），
本文只约定接口语义。

## 3. SG0–SG6 与 A/B/C/E

**SG 是设计工作的事实状态，A/B/C/E 是治理判断的时机；两者相关但不是同一套编号，也不一一对应。**
下表只说明每个 SG 有哪些东西可以交给治理、通常在什么语境下交换。它**不是阶段转移规则**：
任何一个 SG 完成都不证明治理门通过，任何一次 CONSULT 也不证明 SG 通过。

| SG | 可交给治理的产物或判断 | 常见治理语境 | 交换条件 |
|---|---|---|---|
| 0 产品理解 | `design-brief.md`（目标、`P*`/`S*`/`X*`、出处、范围冻结） | A 启动理解（合同与完成条件成形） | 目标可判定、范围闭合 |
| 1 概念方向 | `direction-approved.md`（决策与理由）、`concept-index.json`、差异实测 | B 规划（方向取舍本身是治理对象时）、C（方向被验证否定） | 决策记录为唯一实施基线 |
| 2 HTML 原型 | `prototype/`、`coverage.json`、真实截图 | C（覆盖缺口、方案被真实渲染否定） | 覆盖矩阵闭合 |
| 3 评审与打磨 | `prototype-notes.md` 评审记录、`asset-manifest.json` | C（重要视觉问题改变方案）、E 前的设计结论 | 致命项清零 |
| 4 原生交接 | `handoff/` 七件套与四类等价契约 | 合同「交付物」引用 | 实现端不需要看图猜结构 |
| 5 原生实现 | 原生工程路径、构建/安装日志、落地映射 | 工程工作项证据与失败分流（§5） | 构建、安装、可启动 |
| 6 真机验收 | `verification-report.md` 终版、`coverage.json` 终版 | E 收口判断 → G1–G3 收口 | 工程与设计双验收分别达标 |

A/B/C/E 的触发、材料与配对命令由 Copilot 按其自身生命周期决定（A 启动理解、B 调查后规划、
C 重大事件追加、E 收口前综合判断；D 已退役）。**本 skill 不调度、不等待，也不为凑阶段创建治理动作。**

## 4. 认知（Astra）

三个判断互相独立：**是否进入 Copilot**、**是否咨询 Astra**、**设计是否验收通过**。
任一为真都不自动带出另一个。

**值得问**：重要设计决定仍有实质分歧；证据之间冲突；高代价取舍且咨询可能改变选择。
**不值得问**：局部可逆调整；方案已定只需复验；问题只是「好不好看」；只想让外部模型背书。

**输入结构**：要判的具体问题 → 候选方向/方案 → 约束与产品事实 → 已有证据与仍缺什么 → 误判代价。
有画面且有真实像素才评画面（`--image` 最多 6 张）；无图咨询必须声明未看画面、不得评价像素
（交接包与问法见 `design-review-handoff.md`）。

**输出**：advisory。采纳/修改/拒绝由 ZCode 判断，需要留痕时用 `cognition-accept` 登记；
**采纳不是设计验收，未采纳不是任务失败**。同一材料同一问题不重复付费；不因等待认知停止设计工作。

## 5. 失败分流

| 现象 | 责任方 | 处理 |
|---|---|---|
| 产品理解错误、目标与方案不匹配 | DesignWise 重新分析，ZCode 决策 | 回阶段 0 补事实与出处；不用改文案掩盖 |
| 信息架构、交互路径、视觉方向不成立 | DesignWise 修订方案 | 回阶段 1/2；不在原型上打补丁 |
| 设计不符合产品视觉身份 | DesignWise 修订视觉决策 | 按 `visual-identity.md` 与 `cross-product-differentiation.md` |
| 原型渲染、脚本、构建、安装异常 | ZCode | 工程修复后重跑受影响验证 |
| 原生实现偏离已认可设计 | ZCode 修复，DesignWise 复验 | 修结构、不做降级替换；复验给新证据 |
| 工程约束改变了设计目标 | ZCode 更新约束，双方重新评估 | 影响完成条件时同步 Copilot 合同 |
| 合同目标/范围/条件实质变化 | Copilot | `contract --amend`；旧认知结论不再覆盖新合同 |

原则：

- **能局部修的不重启全流程**；不改变目标的缺陷修复不更新合同。
- **PARTIAL 不是终点**：仍有未闭合条件时继续推进（DesignWise 补设计与复验、ZCode 修工程），不据 PARTIAL 收口。
- **两类缺口分开记**：设计未达标与工程未达标各自保留未满足条件、责任方与复验依据；混合问题拆开处理。
- 重要方案失败时重新评估，不机械重复失败路径；再咨询条件见 `design-review-handoff.md` §1。

---

## 6. 边界（硬性）

- 不恢复 `sol-*`、`call_gpt.py`、远程设计裁决或任何「等模型批准」的门；认知结论不是设计批准。
- 不改 Copilot 源码与运行时，不手改副本，不给宿主加钩子。
- 不把本文扩成设计方法或 CLI 手册：方法在 `SKILL.md` 与其余 references，命令以 Copilot 当前版本为准。
- 不把一次任务的结论沉淀成跨项目默认审美或默认治理动作；身份与产品原则仍归使用方项目。
