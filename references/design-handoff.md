# 设计交付契约 · DesignWise → Web / Android / PPT

> **读这份文档的时机**：设计已实现为 HTML 高保真原型、准备交给 Web / Android 工程或 PPT 制作方落地时。
>
> **一句话立场**：**交付的是规格，不是截图。** 开发 agent 不该靠"看截图猜数值"来还原设计——间距猜错 4dp、色值差一号、状态漏一半，就是返工。本契约把设计转成**可执行、可核对**的交付包，让实现端照着做即可。
>
> **与 `gpt-visual-workflow.md` 的关系**：那是"怎么做出设计"＋"开发期怎么按需补素材"（§4.7），这是"怎么把设计交出去、怎么验收实现"。三者首尾相接：概念图 → 视觉转译（`visual-translation.md`）→ HTML 实现 → **本契约的交付包** → 实现端落地 → **本契约 §8 反馈闭环**。

---

## 0. 什么时候需要交付包

| 场景 | 要不要交付包 |
|---|---|
| 设计要交给**别的工程/别的 agent**实现（Web 前端、Android 原生、PPT 制作） | ✅ **必须** |
| 设计就是最终产物（幻灯片/信息图/动画/纯 HTML demo） | ❌ 不需要，HTML 即交付物 |
| 只是给用户看方案 / 内部探索 | ❌ 不需要 |

> **原则**：**只要有人要照它实现，就给交付包**。交付包的完整性 = 实现端不需要猜的程度。

---

## 1. 交付包结构（一个目录，七件套）

放在项目目录下，命名 `handoff/`（或项目约定的交付目录）：

```
项目名/handoff/
├── README.md               # 入口：这是什么、怎么用、清单勾选状态
├── structure.md            # ① 页面结构与信息层级
├── design-tokens.md        # ② 设计规范（色彩/字体/间距/圆角/阴影/动效）
├── states-interactions.md  # ③ 页面状态与交互行为
├── copy-data.md            # ④ 真实文案与数据口径
├── assets.md               # ⑤ 素材清单与引用关系
├── adaptation-a11y.md      # ⑥ 适配与无障碍要求
└── baselines/              # ⑦ 关键页面验收基准图（PNG）
    ├── home.png
    └── ...
```

**`README.md` 必须含**：产物性质（设计交付包，非产品代码）、基准技术栈建议（Android 原生 / Web 二选一）、七件套勾选清单、以及一句红线提示（见 §5）。

> **HTML 原型本身也是交付物之一**：作为**视觉基准**随包交付（放 `handoff/` 旁或 `prototype/`），但明确标注"**基准，非实现代码**"。

## 2. 七件套逐项规格

### ① `structure.md` — 页面结构与信息层级

- **页面清单**：每个页面的名称、职责、入口来源（从哪进、能去哪）
- **结构树**：页面内区块的自顶向下顺序（谁在谁上面），每块一句话职责
- **信息层级**：每页**视觉第一主角**是什么（如"今日步数"），次主角、工具性元素各是什么
- **不可变边界**：结构上不许动的东西（如"四 Tab 不可增删"、"必含周报模块"）
- **与 spec 的对应**：每个页面/区块指回 `spec.md` 的哪一条需求（保证需求不丢）

### ② `design-tokens.md` — 设计规范（原理化，不是"照着截图看"）

**必须给 token 表和数值**，让实现端直接映射到平台（Android `colors.xml`/`dimens.xml`；Web CSS 变量）：

| 类别 | 要给什么 |
|---|---|
| **色彩** | token 名 + **色值（HEX/ARGB）** + 职责（主色/强调/文字分级/背景/描边/状态色） |
| **字体** | 字族（中文/数字各一）+ 字号 + 字重 + 行高 + 字间距，逐层级（display/标题/正文/标签） |
| **间距** | 基础栅格（如 4/8dp）+ 常用间距 token（页面边距/区块间距/组件内距） |
| **圆角** | 各层级半径值（卡片/按钮/输入/标签） |
| **阴影/描边** | 具体参数或"等价效果"描述（避免"轻微阴影"这类空话） |
| **动效** | 时长 + 缓动（duration + easing），关键转场的参数 |

> **交付 token 的值与"职责"，不是"截图上的观感"**。实现端要能不看图就填出 `colors.xml`。**色值以设计规范为准**（若来自品牌 asset 协议，注明来源）。

### ③ `states-interactions.md` — 页面状态与交互行为

- **状态矩阵**：每页/每组件有哪些状态（默认 / 加载 / 空 / 错误 / 数据不足），*各自长什么样*
- **交互行为**：点击/滑动/切换后的结果；哪些是真实可交互、哪些只是展示
- **状态机**：多步流程的状态流转（如 tab 切换、弹窗开合、任务进度）
- **边界状态**：数据为 0 / 首次使用 / 无权限 / 断网时的呈现（**不许留空**）

### ④ `copy-data.md` — 真实文案与数据口径

- **文案原文**：界面上每一句用户可见文字（中文原文，逐字），标注用在哪
- **数据口径**：每个数字/指标的定义与来源（如"今日步数=当日累计，来源计步服务"）
- **数据不足态**：未达条件时显示什么（如"数据积累中"、"待解锁"）——**真实态必须写明，不许让实现端自造**
- 🔴 **红线**：**所有数值/文案 = 产品规范的真实值，GPT 概念图里的数字一律不得进此表**（幻觉数据）。

### ⑤ `assets.md` — 素材清单与引用关系

逐张列（呼应 `gpt-visual-workflow.md` §4.6）：

| 列 | 内容 |
|---|---|
| 文件名 | 素材路径（如 `assets/images/bg-<用途>.png`） |
| 用途 | 用在哪页/哪组件/哪种状态 |
| 尺寸 | 目标像素 + 透明/不透明 |
| 来源 | 真实素材（官方/用户提供）or GPT 生成（附 `img-prompts/` 链接）+ 模型 |
| 引用关系 | 工程侧怎么引（Android `res/drawable-*`、Web 相对路径/静态资源） |

> **简单图标/图形不要塞进素材清单**——注明"用原生 SVG/CSS 实现"，给形状规格而非位图。

> 🔴 **阶段 4 验证素材的三种去向**（见 `gpt-visual-workflow.md` §5.1）：**A 直接复用**（迁入 `assets/images/`，过 §4.6 规格）／**B 按工程要求重出正式素材**（视觉语言不变）／**C 用矢量或代码实现替代**（收益更高时）。选 C 时在本清单写明"非位图实现"及实现位置；选 A/B 时给出 `img-prompts/` 链接与实测尺寸。**不要把 `prototype/assets/img/` 里的验证态路径直接写进交付清单**——交付引用的是 `assets/images/` 下的最终素材。

### ⑥ `adaptation-a11y.md` — 适配与无障碍

- **屏幕适配**：目标尺寸/比例范围、响应式断点、横竖屏、安全区（刘海/手势条）
- **字体缩放**：系统放大字体后各页表现（**不截断、不重叠、不遮挡**）
- **对比度**：按**三档**给值（见 `content-guidelines.md`「对比度（三档判定）」）——① 正文文字 ≥4.5:1（大字 ≥3:1）、② 重要图标/图形 ≥3:1、③ 纯装饰无门槛但须标注。**必须附逐对实测表**：`前景色 / 背景色 / 实测比 / 档位 / 判定`。🔴 **档 ① 或档 ② 低于门槛 = 交付包不合格**，须先调整色值再交。机械校验：`python3 scripts/check-contrast.py pairs.json`（退出码 1 = 有阻断项）
- **点击区**：最小触摸目标（如 ≥48dp）
- **无障碍**：content description / 语义标签 / 焦点顺序 / 色盲友好

### ⑦ `baselines/` — 关键页面验收基准图

- 每页一张（或每页每个关键状态一张）**PNG**，来自 HTML 原型的真实渲染
- 命名与页面一一对应；在 `README.md` 里给对照表
- **用途**：实现端实现完，拿自己的截图与本基准**并排比对**（差异判定见 `gpt-visual-workflow.md` §6.1——对意图负责，不对像素负责）

## 3. 交付形态：三平台，同一套七件套（实现端决策）

**七件套是平台无关的设计契约，不重复三套。** 每个平台的差异只是**一层"平台适配"**——在七件套之上补该平台特有的映射信息。实现端按自身技术栈选一份读法，**不要为每个平台重写交付包**。

| 目标平台 | 实现端自选技术栈（🔴 不强制） | 在七件套之上补什么 | 交付重点 |
|---|---|---|---|
| **Web** | 项目既定框架（React / Vue / 原生），**不强制**用设计原型的 HTML | `design-tokens.md` → CSS 变量（`:root`）；响应式断点；静态资源路径 | 响应式与浏览器兼容 |
| **Android 原生** | Kotlin + Compose，或 XML 布局——**🔴 禁止把原型 HTML 塞进 App** | token → `colors.xml` / `dimens.xml` 建议映射；drawable 规格；dp/sp 口径 | 触摸区 / 系统字体缩放 / 安全区 |
| **PPT / 演示文稿** | 现有 deck 链路（`references/slide-decks.md` + `editable-pptx.md` / `pptx-from-rendered-html.md`）——**不重造** | 文字/图表**尽量保持可编辑**（走 pptx 路线时用真文本框/图形，不把整页拍成图）；版式按母版 | 可编辑性（甲方要能改） |

**关键约定**：
- **保留各平台原生实现方式**——交付包给**规格与基准**，实现端用什么技术、怎么落地由它决定，DesignWise 不指定框架。
- **PPT 可编辑性**是硬要求：能走可编辑 PPTX 的（`scripts/pptx_from_rendered.py` / `html2pptx.js`）就不要交图片版 deck；**文字、图表、版式尽量是原生 PPT 对象**，甲方才能改母版整体生效。转档规则与两条路的选择见 `references/slide-decks.md` 与上述两份 reference，**本节不重复**。
- **PPT 交付的"基准图"**用每页渲染截图（对应 §1 的 `baselines/`），比对方式与 Web/Android 相同。

> 🔴 **HTML 原型 ≠ 任何平台的最终实现代码**：原型是**视觉基准**，不是拿去编译/上线的源码。三端都按交付包**各自实现**，用 §7 基准图验收。

## 4. 交付包自检（发出去之前必过）

- [ ] 七件套**齐全**，`README.md` 勾选表与实际一致
- [ ] `structure.md` 每个页面都指回 spec 的某条需求（**需求零丢失**）
- [ ] `design-tokens.md` 给出**值**，不只是"照着图看"
- [ ] `states-interactions.md` 覆盖**空/加载/错误/数据不足**四态，无留空
- [ ] `copy-data.md` 的数值**逐项等于 spec 真实值**（幻觉数据 = 0）
- [ ] `assets.md` 每张素材可被工程**直接引用**（路径有效、格式/透明符合）
- [ ] `adaptation-a11y.md` 给了对比度（含**逐对实测表**，档 ①/② 无不合格项）/ 点击区 / 字体缩放的具体口径
- [ ] `baselines/` 每个关键页面都有基准图，且来自真实渲染（非概念图）
- [ ] 明确标注"HTML 原型是基准，非实现代码"

## 5. 红线（违反即返工）

| 红线 | 为什么 |
|---|---|
| **交付包缺原理化规格（只给截图）** | 开发只能猜，还原度不可控 |
| **把概念图（GPT 效果图）当基准图交付** | 概念图是探索态、含幻觉数据与不可实现效果（§3.5.3） |
| **把原型 HTML 当 Android 最终代码** | 原型非产品源码，平台/性能/维护都不成立 |
| **文案/数据表里混入 GPT 幻觉值** | 伪造产品数据，违反产品规范 |
| **素材清单里的图工程引用不了** | 交付不等于可用；路径/格式必须落地 |

## 6. 与验证闭环的衔接

交付包**完成度**是 `gpt-visual-workflow.md` §6.2 闭环检查的第 6 项（"交付内容是否完整"）。**交付包自检（§4）全绿 = 该项 PASS**；实现端落地后，再用 §7 的验收基准图比对，闭合"设计 → 实现"的最后一环。

---

## 7. 验收基准图怎么用

1. 实现端实现完成后，按 `baselines/` 的页面清单，逐页截取自己的实现截图
2. 与基准**并排**，按 `gpt-visual-workflow.md` §6.1 四项（布局/字体层级/素材/配色气质）比对
3. **判定**：不要求像素级一致；**对设计意图负责**——用户确认的视觉方向（`visual-translation.md`）是否被实现继承
4. 发现实质偏差 → **定向修复**（只改被点名项），不推倒重来

> **诚实标注**：若实现端尚未运行（如 Android 工程没编译），验收只能是**模拟验收**（拿原型截图 vs 基准图），**必须标注为 PARTIAL，不得报告"全链路真实通过"**。

## 8. 真实实现反馈闭环（交付之后 · 开发期）

> **边界**：DesignWise 提供**设计判断与验收规范**，**不代替执行 agent 操作开发细节**（编译、跑 App、抓日志都是实现端的活）。本节只规定"拿到真实产物后，怎么比对、怎么闭环"。

**回路（实现端执行，DesignWise 给判据）**：

```
实现端真实运行（真机/浏览器/PPT 打开）
  → ① 获取真实截图（与 baselines/ 同尺寸或同比例）
  → ② 与 DesignWise 基准逐页并排比对（§8.1 五项）
  → ③ 检查真实业务数据（数值 = copy-data.md 真实值，非幻觉）
  → ④ 检查可读性与无障碍（对比度档 ①/②、点击区、字体缩放）
  → ⑤ 发现偏差 → 定向修复（只改被点名项，不推倒重来）
  → ⑥ 重新运行验证（回到 ①，复验范围按缺陷影响面）
```

### 8.1 比对的五项（与 §7 基准图同源，补齐"真实数据/无障碍"两项）

| # | 检查项 | 关注什么 | 判据来源 |
|---|---|---|---|
| 1 | **布局** | 主要区块位置/比例是否走样；首屏核心行为是否仍在首要位置 | `baselines/` 基准图 |
| 2 | **色彩** | 主色/底色/情绪基调是否跑偏；是否落在 `design-tokens.md` 的 token | `handoff/design-tokens.md` |
| 3 | **字体** | 标题/正文/标签层级是否被压平；字号是否达标 | `handoff/design-tokens.md` 字号层级 |
| 4 | **素材** | 素材是否错位/拉伸/用错图；是否与 `assets.md` 清单一致 | `handoff/assets.md` |
| 5 | **关键状态** | 空/加载/错误/数据不足四态是否都实现（**不许留空**） | `handoff/states-interactions.md` |
| + | **真实业务数据** | 界面数值 = `copy-data.md` 真实值（**幻觉数据 = 0**） | `handoff/copy-data.md` |
| + | **可读性 / 无障碍** | 对比度档①②达标、点击区达标、字体放大不截断 | `handoff/adaptation-a11y.md` + `scripts/check-contrast.py` |

**判定原则**：**不要求像素级一致**——对**用户确认的设计意图**负责（`visual-translation.md`），不对像素负责。

### 8.2 修在哪一侧（🔴 关键分流）

| 发现的问题 | 在哪修 | 为什么 |
|---|---|---|
| **普通页面问题**（这个页面的间距、这个组件的状态） | **项目内修**（实现端改自己的代码） | 页面级问题，不是 skill 的锅 |
| **通用设计规则有缺陷**（同类问题在多个项目反复出现、或规则本身错/缺） | **才改 skill**（DesignWise 源码基线） | 规则缺陷要回流到 skill，否则每个项目重复踩 |

> **不要为单个页面的实现问题改 skill**——那是过度反应。**只有规则本身的缺陷**（如某条无障碍门槛定错、某个交付项缺失）才回流。

### 8.3 复验范围（不重跑全流程）

**定向修复 → 按缺陷影响面定复验范围**，不重跑整个设计流程。风格/措辞/可读性偏好不算实质问题，不改。复验通过 = 该项闭环；仍不合格 = 记录并继续，**不无限循环生图/改稿**。

## 9. 交付后经验回流（不新建系统）

交付完要判断一件事：**这次的发现值不值得影响下一个项目？** 不值得就到此为止，
写进交付说明即可——**记录不是义务，回流才有义务**。

**四类证据，去向不同**（关键是别把某一种当成另一种）：

| 证据类型 | 长什么样 | 去哪 | 不该去哪 |
|---|---|---|---|
| **preference（用户偏好）** | 用户原话：「这个配色太吵」「按钮再大一点」 | 本机 memory（跨会话的稳定偏好），**只对这位用户/这个项目有效** | 不进 skill 源码、不进知识库、不进外观账本 |
| **observed（单项目观察）** | 只在一个项目里看到、未复现的现象 | 留在该项目的设计记录里 | 不写成通用规则——一个项目不足以下结论 |
| **verified（已复现或已测量）** | 同类问题在 ≥2 个项目出现，或有脚本/实测证据（对比度实测值、真机复现） | **工程事实与坑** → 知识库候选；**能被测出来的** → 直接改脚本 + 加测试 | 不停在「经验之谈」的口头结论 |
| **superseded（被取代）** | 旧做法被新做法或平台限制淘汰 | 在原记录处标注被谁取代，**不默默删除** | 不留两套并存的说法让下一个人猜 |

**三条边界**：

1. **经验不扩大授权**：用户这次同意某种做法，不等于下次自动同意（尤其涉及业务规则、隐私、付费）。
2. **单个用户的口味不进分发层**：`references/` 与 `scripts/` 是所有人共用的；只有**规则本身的缺陷**
   （§8.2 的判定）才改源码基线，且要过项目验证门。
3. **不带秘密与个人数据**：回流内容里不出现真实用户信息、内部链接、凭据；原始截图与日志不随经验走。
