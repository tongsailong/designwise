# 评审交接包 · 把真实视觉材料交给独立审美咨询

> **读这份文档的时机**：阶段 0/1/3/5–6 出现高价值视觉判断、且 ZCode 自评仍有实质不确定时；
> 或要向 Copilot 的认知通道（`cognition-consult`）提交一次审美咨询。
> **一句话立场**：涉及画面判断时，咨询的价值来自**真实像素 + 明确的改动上下文 + 可判定的问题**；
> 论证层咨询可以无图，但不得冒充看过画面。**它是补充证据，不是审批节点。**

---

## 1. 什么时候值得发起（ZCode 自主判断，不由用户点名）

先过三个问题：

1. **影响面**：这次判断只改一个细节，还是会牵动整套视觉语言、多页结构或后续大量返工？
2. **产物状态**：现在有没有可判断的真实产物（brief / 真实概念图 / 当前截图 / HTML↔真机同状态对照）？
3. **自评把握**：按 `critique-guide.md` 与 `polish-loop.md` 过一遍后，是否还剩实质不确定？

**影响面大 × 有真实产物 × 自评仍有实质不确定**，三者同时成立才发起。用户提出正常设计需求即可，
不需要额外指定咨询通道；ZCode 在流程里自行判断，并在 `prototype-notes.md` / `design-brief.md` 写一句
"发起/跳过及理由"。**跳过是正常结果，不是失职。**

| 阶段 | 高价值认知机会 | 材料 | 不发起 |
|---|---|---|---|
| 0 产品理解 | 艺术指导论证链、视觉母题、产品气质与差异化；可提出替代论点 | brief 草案 + 已核实的产品事实/约束（可无图） | 事实未查清；只是套风格词 |
| 1 概念 | 真实方向图的视觉表达、原创性、构图、方向取舍；可提出替代母题/构图 | 2–3 张真实方向图 + 方向卡/差异实测 | 方向已定且无新图；用文字描述代替图 |
| 3 原型/打磨 | 真实截图的视觉盲点、优先修改项、值得保留的细节 | 3–6 张代表性截图 + 交接包（有图） | 局部细节；同批图同问题 |
| 5–6 交接/验收 | 仅当出现重要视觉偏差或设计意图损失 | HTML 基准与真机同状态截图对照（有图） | 常规还原、token 替换、无新证据 |

**两种模式不能混**：

- **认知咨询（可无图）**：阶段 0/1 讨论产品事实到艺术指导的论证、母题与取舍；Copilot 没看到画面，
  输出必须声明"未看画面"，**不得评价像素、构图实现或视觉完成度**。
- **视觉咨询（必须有图）**：阶段 1/3/5 的画面判断；没有真实像素就不发起视觉结论，
  不用 OCR、文字描述或源码分析冒充截图。

**不发起也要照常评审**：DesignWise 自评是必需项，外部咨询是可选增强。没有 Copilot 时这条链路
不存在，各阶段照常按本地判据完成。**同一次调用只问本次真正不确定的事**：缺陷、值得保留与创造性
选项可以合并问，不为同一批图拆成多次调用。

## 2. 材料：一个包，两个消费者

```bash
python3 scripts/review_packet.py --spec review-packet.json \
  --out design-demos/<task>/prototype/review-packet.md --json
```

`review-packet.json` 与图片同目录或写相对路径（相对 spec 所在目录解析）。字段：

| 字段 | 必填 | 内容 |
|---|---|---|
| `product` / `audience` / `goal` | 是 | 产品、用户与场景、本次目标（各一句） |
| `direction` | 是 | 采用/融合的方向与一句理由 |
| `dna` | 建议 | 视觉 DNA（`visual-depth.md` §6 的压缩版） |
| `device` | 是 | 设备、分辨率、设计基准（dp/pt） |
| `version` | 建议 | 原型或构建版本标识 |
| `changes_since_last` | 否 | 相比上次评审改了什么；首次评审可省（脚本按"首次评审"输出，不阻断） |
| `images[]` | 是 | `path` / `screen`（`P*`/`S*`） / `state` / `scale` / `note` |
| `questions` | 否 | 覆盖默认九问中的部分；不写则用全部九问 |

**脚本负责的事实校验**：文件存在、可解码、每张图有 `screen` 与 `state`、同一文件不重复、
同一 sha256 不重复（防同一张图换个名字充数）、输出 `sha256` 与 `宽×高`。
**脚本不判断设计好坏，也不把历史截图认成当前版本**——版本标注由提交者负责。

**图片选择**：3–6 张，覆盖代表性屏幕与状态（默认态 + 一个异常态或大字号态）；一张图只代表
一个屏幕/状态。不要把整页长图缩成一张、不要拼贴、不要只给首屏就要求评整个 App。

## 3. 九个问题（默认问法）

脚本内置，可按本次重点覆盖其中几条：

1. 这一版是否有独特且站得住的视觉概念，还是可以套到任何同类产品上？
2. 第一眼落点对不对？用户最该先看到的信息，是不是视觉上最重的元素？
3. 构图与视觉重量是否协调：主体、留白、边缘元素之间有没有互相争夺？
4. 色彩、字号层级、材质、光线是否统一在同一套关系里？
5. 有没有明显的模板感或 AI 味：无来由的渐变、阴影、大圆角卡片、玻璃拟态、装饰形状？
6. 是否匹配该产品的用户、使用场景与定位（而不是匹配某种流行风格）？
7. 哪些视觉细节值得保留，不要在后一轮打磨里改掉？
8. 如果只能改三处，改哪三处对整体提升最大？给到具体位置与目标状态。
9. 主代理可能忽略的视觉问题是什么（跨页一致性、密度节奏、极端内容、深色模式）？

**问题写法**：一次只问真正需要判断的事；问"哪里、为什么、怎么改"，不问"好不好看"；
不问"给我打个分"。问题太泛时先自己按九问过一遍，把已能判断的排除掉，只留下真正的不确定。

### 3.1 创造性问题（前置/方向阶段可选，最多 2–3 个）

找缺陷之外，也可以让 Copilot 的认知通道提构想与取舍。只在真正需要新选项时问：

1. 在不改产品事实与约束的前提下，有没有第二个更贴合内容的视觉母题？它来自哪个产品事实或行为？
2. 现有哪个细节值得放大成签名，而不是继续加装饰？
3. 论证链（产品事实 → 情绪目标 → 视觉论点 → 母题/形式 → 具体决定）哪一步最弱？给替代走法与代价。
4. 如果只能保留一个视觉决定，保留哪个？为什么？

创造性建议是候选，不替代真实生图、不改变用户已确认的方向；采纳与否仍由 ZCode 决定。

## 4. 提交给 Copilot 认知通道

Copilot 当前入口是 `cognition-consult`（零工具、单轮、advisory）；命令与参数以 Copilot 自身文档为准（`~/.zcode/skills/copilot/`）。**什么时候该问、什么时候连治理都不需要，见 `copilot-integration.md`；本文只讲怎么提交一次已经决定要问的咨询。** **正式 REVIEW（`cognition-review`）只在用户明确要求时使用**；日常审美咨询用 consult 即可，不要为一次咨询建审批流程。

**无图认知咨询**（阶段 0/1，只讨论论证链与母题）：

```bash
python3 -B ~/.zcode/skills/copilot/scripts/copilot_dispatch.py cognition-consult \
  --state <state> --stage stage \
  --materials <task>/design-brief.md \
  --question "这套艺术指导的论证链哪一步最弱？有没有更贴合产品事实的母题？"
```

材料里必须写明这是无图咨询；输出若评价画面，按无效意见处理。

**有图视觉咨询**：把 `review-packet.md` 作为材料，图片用 `--image` 逐张提交（单次最多 6 张、单张 ≤8 MB，PNG/JPEG/WebP），`--image-note` 与图片顺序一一对应：

```bash
python3 -B ~/.zcode/skills/copilot/scripts/copilot_dispatch.py cognition-consult \
  --state <state> --stage stage \
  --materials <task>/prototype/review-packet.md \
  --question "这一版的第一眼落点与跨页一致性是否成立" \
  --image <task>/prototype/screenshots/r2-p1.png --image-note "P1 默认 1.0" \
  --image <task>/prototype/screenshots/r2-p3.png --image-note "P3 阅读 1.0"
```

- 交接包里的图号顺序必须与 `--image` 顺序一致；超过 6 张时挑代表性屏幕，其余留在交接包里。
- Copilot 侧的通用问题清单是兜底；**本文件的问题与交接包 `questions` 优先**，不要求两边逐字一致。
- 若宿主不具备 Copilot 或通道不可用：**如实记录"未做外部审美咨询"**，继续用本地评审与打磨，不得用文字描述代替像素，也不得伪造外部 PASS。

## 5. 意见怎么用

| 步骤 | 要求 |
|---|---|
| 逐条核实 | 对照截图确认问题真实存在；指不出位置的评价视为无效 |
| 分类 | `accepted`（采纳）/ `modified`（采纳但改法不同）/ `rejected`（不采纳，写理由） |
| 落盘 | 写入 `prototype-notes.md`：轮次、图号、问题、严重度、决定、改动前后图 |
| 优先级 | 与本地评审合并排序：致命 → 重要 → 打磨；**外部意见不自动升级严重度** |
| 复验 | 采纳项改完重渲染受影响屏；用新截图对照，不以"已按建议修改"作为证据 |
| 登记 | Copilot 侧用 `cognition-accept --call-id <call_id> --status accepted\|modified\|rejected` 登记采纳结论；两侧记录指向同一批图与 sha256 |

**不采纳不是对抗**：外部意见可能与产品规则、平台约束或用户已确认方向冲突；写清理由即可。
**采纳也不等于设计完成**：仍须自己按判据复验，不把"外部意见说好"当 PASS。

## 6. 边界（硬性）

- **不恢复旧链路**：`call_gpt.py`、`bridge_evidence.py --image` 的设计裁决用途继续退役。
- **不新建第二套记忆**：设计结论的住所是 `direction-approved.md`、`prototype-notes.md`、
  `review-packet.md` 与 `coverage.json`；Copilot 只留调用与采纳台账。
- **不做审批门**：外部意见不进 SG0–SG6，不改变完成条件，不阻塞已授权工程动作。
- **不重复付费**：同一批像素 + 同一问题只问一次；重问必须有新版本、新状态或新材料。
- **图片三态不混用**：参考图、概念图、原型/真机截图各自标注来源；概念图不得当原型证据。
- **知识沉淀有分类**：咨询结论按 `design-handoff.md` §7.1 判断是否值得回流；一次设计的色板、
  风格、材质或布局**不得自动变成其他项目的默认审美**。
