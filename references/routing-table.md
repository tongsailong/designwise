# 任务路由 · App UI 单入口

> **读这份文档的时机**：收到任务，先判断载体、再判断从哪个阶段进入、哪些请求不在范围内。
> **权威**：阶段与 Gate 以 `SKILL.md` 为准（0–6 / SG0–SG6）；本文只做**入口判定**，不另立流程。
> **一条流程，深度按改动范围**：入口看已有产物成熟度（§2），深度看改动范围（§2.1）；不按任务名分层。

---

## 1. 第一判断：是不是 App UI

| 任务信号 | 入口 |
|---|---|
| App / 移动应用 / iOS / Android 的界面、改版、多页面视觉体系 | 阶段 0 起（整机/多页面须建全量页面-状态地图） |
| App 的 HTML 高保真原型 / 可交互原型 / 设计方向探索 | 阶段 0 起；已有有效 brief 可从阶段 1 进 |
| App UI 图片素材生成 / 处理 / 复用 / 清单 | 阶段 3 的素材环节；不改方向与结构 |
| App 的商店截图 / 分发渠道宣传图（画面主体是**真实界面**） | 阶段 3 素材环节 + 身份对齐；**不走 0–6 全流程**（不做状态地图、不做原生交接），口径见 `SKILL.md` §0 与 §6.5 |
| App 设计评审 / 视觉方向判断 | 按已有产物进入阶段 1 或 3；只评审不改文件 |
| App 原生 UI 交付 / 实现 / 真机验收 | 阶段 4 / 5 / 6（按已有 `handoff/` 决定） |
| App 原生质感 / 动效 / 体验状态专项评审 | 按已有产物进入阶段 2 或 3；只评审不改文件；证据看真实截图与录屏 |
| 幻灯片 / PPT / deck | **不在范围**：说明边界，转交相应工具 |
| 视频 / 动画成片 / 宣传片 | **不在范围** |
| 配音 / 音频 / 音乐 / SFX | **不在范围** |
| 信息图 / 海报 / 封面 / 纯平面 | **不在范围** |
| 生产级 Web App / 后端系统 / SEO 站 | **不在范围** |
| 纯代码重构 / 图层级可编辑 PPTX | **不在范围** |

**分界线在内容来源，不在画布形状**：画面主体是真实 App 界面（含界面 + 版式 + 文案的商店图）
→ 在范围，按上表那一行走；画面主体是纯图形/插画/照片拼贴、与 App 界面无关 → 不在范围。
两种都不做整机流程，差别只在后者连素材环节也不接。

**不确定载体时问一句**：「这是 App 界面任务，还是其他载体？」不猜，也不硬套。

## 2. 第二判断：从哪个阶段进入

按**已有产物的成熟度**进入（与 `SKILL.md` §2.1 一致；本文件不复制那张表，避免两套口径）：无有效 brief → 阶段 0；有效 brief + 地图 + 出处 → 阶段 1；方向已是实施基线 → 阶段 2；当前原型只需局部改动 → 阶段 3（只改受影响屏）；有效 `handoff/` → 阶段 5；只改后端 → 不触发本流程；已有成熟设计系统 → 阶段 0 缩短，引用现有 token。

**判不准按更高阶段处理。** 「局部迭代」不是降低质量门的理由，只是省掉重新探索。

### 2.1 哪些改动算局部迭代（深度参考）

| 改动 | 走法 |
|---|---|
| 文案、间距、圆角、单组件状态、Bug、适配、替换已登记素材 | 阶段 3（只改受影响屏）或直接改原生，复用 brief/方向记录；只复验受影响项 |
| 新增一个页面或一条核心流程 | 阶段 0（该页 + 出入状态）→ 该页原型 → 受影响项评审；结构沿用现有体系，不出概念图 |
| 信息架构 / 导航变化 | 阶段 0 起，**必须重看状态地图** |
| 换 token / 圆角 / 字体（不改信息架构与视觉母题） | 阶段 3 局部修正；按全局影响面重渲染并重审所有 token 消费者，见 `SKILL.md` 阶段 3 |
| 换视觉母题 / 视觉语言（结构或气质方向变） | 阶段 1 起（方向要重新判断） |
| 跨多页面视觉体系 / 品牌探索 | 阶段 0 起完整走 |
| 用户要求"再探索几个方向" | 阶段 1，不是局部迭代 |

## 3. 特殊入口

### 3.1 涉及具体品牌/产品

- 先**事实验证**（产品存在性、版本、规格、发布状态），再取品牌资产（logo/产品图/UI 截图/色板/字体）。
- 具名产品/品牌必须取官方 logo；设计里出现几个就取几个。
- 生成图不得冒充真实产品/品牌资产。
- 协议 → `references/brand-asset-protocol.md`。
- **先读该产品的视觉身份档案**（项目既有设计目录，通常 `docs/design/visual-identity.md`）；
  没有就在本任务内建**最小三栏**（`Core Motif` / `Visual Invariants` / `Anti-patterns`），
  不替产品发明风格，方法见 `references/visual-identity.md` §2–§3。
- **跨项目参考必须写明借用了哪一维**（如「只借纸纹尺度，不借版式」），且不得高于本产品身份、
  本产品品牌资产与本产品历史素材；不得把另一个产品的方向块、材质描述、参考图直接搬进来。
  优先级见 `visual-identity.md` §4，检查见 `cross-product-differentiation.md` §5。

### 3.2 已有设计系统 / 代码 / 截图

- 从现有 token、组件、页面结构长出来；**「沿用现有体系」不等于必须继承上一版信息架构**。
- 设计自由度（IA、页面数量、导航、交互、视觉语言）属常规范围；业务规则、隐私、安全、商业化边界不因设计自由度放宽。
- 现有代码是**事实来源**，不是"设计已经对了"的证明。

### 3.3 需求模糊 / 用户不可达

- 需求模糊：按 best judgment 补齐假设（标 `ASSUMPTION`），用真实视觉建立判断；只问阻塞正确实施的必要问题。
- 用户不可达：可以完成到方向决策，但**不得把 ZCode 的设计决策写成用户选择**；业务事实类假设必须标 `ASSUMPTION`，交付时说明风险。
- 涉及权限/安全/发布/生产数据：按全局与项目规则，不因「自主推进」获得新授权。

### 3.4 只做评审

- **方向判断**：看真实图片，按 SG1 条件逐项给结论（缺哪项写哪项）；不替代用户验收。
- **设计评审**：按 `critique-guide.md` 六维 + 构成十条关系 + App 三项附加检查 + 原生质感与动效检查，给缺陷、严重度、改法；有 spec 时加跑一致性核验。测量用 `design_measure.py` 取事实，不代替判断。
- **可选审美咨询**：ZCode 按「影响面大 × 有真实产物 × 自评仍有实质不确定」自行判断（用户不必点名）；有图用 `review_packet.py` 生成真实截图交接包，无图的论证链咨询须声明未看画面（`design-review-handoff.md`）；咨询不审批、不改变阶段，跳过写理由。
- **动效/质感评审**：截图只能评静态层级与材质；转场、反馈、可中断、减少动态必须看录屏/连续帧。
- **代码/变更独立复核**：按全局 §5 用独立上下文；**没有视觉能力，不得冒充视觉评审**。
- 只评审不改文件；评审结论不等于工程完成证据。

### 3.5 只做素材/生图

- 先判断是否内容必需、能否复用；再按 `image-generation.md` 写 prompt、生成、校验、登记。
- 素材必须进 `asset-manifest.json`；概念图不得当正式素材。
- 不因「只做素材」跳过来源、许可、裁切与消费者记录。
- **对外素材（商店图 / 宣传图）先对齐产品视觉身份**：读身份档案；没有就建最小三栏。
  prompt 里的方向块只能来自**本产品身份 + 本次 Campaign**，并写明它实现了哪条 `Visual Invariants`；
  不得沿用另一个产品的方向块（`image-generation.md` 的身份块规则）。
- **与另一产品存在混淆风险时才做六项检查**，触发条件见 `cross-product-differentiation.md` §0；
  其余素材任务不查，不把差异化变成固定税。

### 3.6 只做原生实现/验收

- 需要 `handoff/`、`baselines/`、`asset-manifest.json`；缺规格先补，不靠猜。
- 真机装包只走宿主授权入口；没有真机 → `PARTIAL`/`BLOCKED`，不编造。
- **落地不是换皮**：逐页说明结构/层级/交互如何实现或有依据保留；构建成功、token 替换不算落地。
- **三方对照**（旧版 / HTML / 新版）阶段 5 建立、阶段 6 完成；旧版基线缺失如实报缺口，不降级安装旧包补基线。
- 验收矩阵见 `app-visual-workflow.md` 阶段 6。

## 4. 判断线（谁做什么，不混同）

**本表是速查；职责边界、准入判据与证据关联以 `SKILL.md` §1 与 `copilot-integration.md` 为准**（本表不重复理由与判据）。

| 事项 | 谁负责 | 不是什么 |
|---|---|---|
| 产品目标、优先级、重大取舍、最终验收 | 用户 / ChatGPT 侧 | 不是设计实施 |
| 产品理解、方向、原型、评审、交接、实现、修复 | ZCode 原生 Agent | 不是等外部批准 |
| 复杂/高风险设计的独立复核 | 可选 ZCode 内置子 Agent（只读复核） | 不是审批节点、不改文件 |
| 任务合同、状态、证据、收口 | Copilot（验收承诺/跨方依赖/未闭合缺口需跨交接跟踪时，准入判据见 `copilot-integration.md`） | 只做治理；可经其认知通道（`cognition-consult`）给建议，但**不做设计裁决**、不是普通开发前置门；DesignWise 不调度也不等待 |
| 方法、判据、产物契约 | DesignWise（本 skill） | 不实施、不决策 |

**已退役**：`call_gpt.py --mode CONSULT`、把远程模型当设计批准者的旧链路与 `sol-*` 命令（Copilot v9.10 起统一为 `cognition-*`）、任何"等模型批准"的设计门。认知建议由 Copilot 按其自身生命周期调度，只提供意见，不承担设计判断、不是设计批准；DesignWise 不另建调度，也不等待它。文档里再出现旧口径即为缺陷。

## 5. 一句话路由

- **新 App UI → 阶段 0 起；方向数量按场景定（新产品概念默认三个独立结构假设，已有产品按实质分歧）。**
- **整机重设计 → 先页面-状态地图与出处，再方向；没有覆盖矩阵与三方对照不算落地。**
- **原生质感/动效 → 按平台语法与 motion token 设计，证据看录屏；只改网页套路或补动画不算升级。**
- **素材 → 先做资产计划，再生成/复用；生成物必须进原型与 manifest，只交 prompt 不算。**
- **商店图/宣传图 → 先读产品视觉身份，再定本次 Campaign；不走 0–6 全流程，也不靠换色通过差异化。**
- **已定方向的局部改动 → 复用记录，从阶段 3 进。**
- **就地能验收 → 不入管**；验收承诺、跨方依赖或未闭合缺口要跨交接跟踪 → 按 `copilot-integration.md` 入管；**入管不等于调 Astra**。
- **只改后端 → 不触发视觉流程。**
- **非 App 载体 → 明确说明不在范围，不硬套。**
- **不确定 → 问载体，再按成熟度进入。**
