**Phase 3.7 · 📝 Visual Brief（方向探索的共同输入，自动生成；默认单一最佳方案）**：先由 agent 从产品需求/用户画像/核心价值/设计目标**自动生成** `design-brief.md`（六段，含"本轮产物性质=概念探索 or 正式素材"+"真实数字/中文文案/交互逻辑以产品规范为准"两条明确 + **硬约束/可探索约束分层**），再据此生成提示词（多方案分支时生成各方向的差异化 prompt）。参考资产（现有界面截图/已选方向/品牌元素）可经 `--ref` 图生图提供结构，但**图中数据不可当事实**。详见 `references/gpt-visual-workflow.md` §2.0。

- **方向要求**：方案数量按 `SKILL.md`「项目规则优先」（**默认 1 个**；实质分歧或用户明确要求时 2–3 个）。走多方案分支时共用同一份 spec（含「用户 + 核心行为」一行），差异在**布局骨架 / 信息组织 / 视觉母题**，**不只是换配色**；不虚构功能；效果图明确标注为**概念参考**。**差异必须落到 prompt 并落实为可见的真实候选图**（各条 prompt 至少母题/骨架/形式元素三处结构性不同），只换配色=无效差异化。🔴 **硬约束之外允许融合**——不要为"看起来不同"把合理元素在方向间机械互斥（§2.0 约束分层）
- 🔴 **成本口径**：生图是 DesignWise 正常模型能力，**任务范围内自主生成，不需要逐次付费审批**（`references/gpt-visual-workflow.md` §1.5）；🔴 **每个候选方向各 1 张真实候选图是必要投入**（不是可省项），失败有限重试、已有素材优先复用、不做"探测式"生成、也不为凑数硬出方向
- **提示词自动生成**：英文 prompt 由 agent 从 Brief 直接生成（六槽位规则见 `references/gpt-visual-workflow.md` §2.3；**图标/符号类走 §2.3.1 专用槽位**），**不要求用户写**；🔴 **区分「探索期初始视觉提示词」与「收敛期最终提示词」**——探索提示词用来产生不同方向，**不得原封不动当最终概念图提示词**；中文文案以引号原样嵌入并标注 `render this Chinese text exactly`
- 🔴 **概念图必须转译再实现**：方向确定后，**先**按 `references/gpt-visual-workflow.md` §3.5 产出 `visual-translation.md`（可提取 / 不得照搬 / 概念图vs正式素材边界 / 断链自检四类），把"看中的图"翻译成可实现的 token 与组件规则，**再**进实现——**不许确定方向后直接开写 HTML**
- **不适用则不进入**：幻灯片 / 信息图 / 动画 / 纯排版 / 局部微调 / 用户明说「不要效果图」→ **走 HTML/CSS，不调 GPT**（载体不匹配，不得为「流程完整」强行生图）
- **产物形态按通路判定**：本通路下候选方向的产物是「**候选方案卡（含完整生图 Prompt）+ 每方向 1 张真实候选图**」（`design-demos/direction-*.png`；**默认 1 个方向**，多方案分支 2–3 个）——**不是多个 HTML**；方向确定后用收敛型最终提示词**只生成 1 张正式概念图**。产出自检以「真实候选方案 + 每方向真实候选图 + 1 张正式概念图」为准（**单一方案即 1 张**），**缺 HTML 不构成「没走完」**，也不为未采用的方向做 HTML；HTML fallback 通路按同样数量口径自检（「每方向 1 个 `.html` + 截图」，默认 1 个）。
- **第一次评审（Phase 5）**：① 🔴 **Gate 1 已在候选图生成后执行**（默认原生自检基于真实候选图判断并（多方向时）给推荐；用户授权后才用 `zcode_vision --confirm-gpt-review`；Copilot 仅点名，§2.6.1），**必须先于方向确定**；② **专家机制对真实候选图评审**（§3.1：用途识别 / 实际视觉层级 / 品牌一致性 / 视觉细节 / 真实小尺寸表现 / 创新与审美质量 / 工程可实现性）；③ 🔴 **方向归属按分支**：**多方案分支由用户从真实候选里选定**；**单一方案由 agent 定并标注 `agent 决策`**（依据与风险进 `design-brief.md`）。发现问题按 §3.2 归因（**Prompt 设计问题 / GPT 执行偏差 / 工程几何问题**）选最低成本修复，**不重启完整方向探索**。🔴 **用户确认真实视觉后**才把**概念图路径 + 用户确认原话**写入 `direction-approved.md`（单一方案另注「方向由 agent 决策」；**创意决策记录不在这里**，它在 `design-brief.md` 的「生图前」/「生图后 · Gate 1」两节，§2.8）；**用户确认前该文件不存在属正常，不构成缺漏**；**方向确定前不进入正式 UI 实现**
- 🟡 **方向授权的三种处理**：**多方案分支**：用户可达 → 停轮等选定；用户本轮明确授权自动选定 → 按 §2.7 保留推荐 + 依据 + 原话。**单一方案**：agent 决策并标注，不停轮。**用户不可达且未授权 → 不得批量实现、不得把 ASSUMPTION 当成确认、不得创建 `direction-approved.md`**，只做 1 个标注 `ASSUMPTION（待用户确认）` 的可逆代表屏 + 设计系统草案（记录写进 `design-brief.md` / `design-state.md`）。
- 🔴 **方向确定后只做该方向**：不再为未采用的方向制作 HTML、工程资源或完整实现，**也不为其生成额外图片**（效率硬规则）
- **方向确定后的链路**：🔴 **生成收敛型最终提示词 → 正式概念图 → 质量自检**（§2.8）→ 概念图转译（§3.5）→ 按需做**一套** HTML 原型（阶段 4，判定与要求见 `references/gpt-visual-workflow.md` §3.6；图片素材规则见 §3.6.3）→ 客观尺寸/几何/遮罩/对比度验证 → **第二次评审与定向迭代**（阶段 5，§3.7）→ 产品化落地（阶段 6，验证素材三选项 §5.1 + 按需 GPT 正式图片素材）→ 真实验收 → **产出设计交付包**（`references/design-handoff.md`：结构/token/状态/文案数据/素材/适配无障碍/基准图七件套，交 Web/Android/PPT 各自实现）
