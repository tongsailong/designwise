# GPT 视觉概念工作流 · 让 GPT 负责视觉创意，DesignWise 负责工程实现

> **读这份文档的时机**：App / Web / 交互原型类任务，需要先探索视觉方向、或需要为正式设计配图时。
>
> **一句话立场**：本文件**不替换**原有 HTML/CSS 三方向探索，而是在它之上加一条**更靠前的 GPT 视觉探索通路**——让 GPT 出候选方向图、概念效果图与正式图片素材，DesignWise 出可运行的真实 UI；🔴 **视觉方向由「真实候选图 → Gate 1（默认原生自检；授权后用 `scripts/zcode_vision.py --confirm-gpt-review` 基于像素比较并推荐；Copilot 仅点名）→ 用户选定」确定，不在生图前由文字评审代定**。**GPT 不可用时：L1 / L3 及判定为「不适用」的任务继续走 HTML/CSS，能力一条不减；L2 需探索视觉方向的任务按 §1 / §2.2.1 报告并暂停生图环节，不得静默改用 HTML/SVG 冒充概念图。**
>
> **与 `references/product-value.md` 同构**：都是「在原有流程上加一层判断」，不新增检查点，不新增并行流程。

## 0. 全流程（七个阶段）

> **一句话立场**：**GPT 负责创意探索；Gate 1 / Gate 2 默认由原生自检在真实像素上比较并判断，外部 `scripts/zcode_vision.py` 仅用户授权后使用（Copilot 正式 REVIEW 仅用户点名）；专家机制负责提示词级文字评审，用户负责选定方向，HTML 按需验证体验，DesignWise 负责可靠实现。**
>
> 🔴 **两个 GPT 通道，职责不许混淆**：**生图**（默认 `scripts/zcode_image.py`；方法论沿用 `huashu-gpt-image`）负责「产生 / 探索」视觉方向；**视觉评审**默认由 **DesignWise 原生自检**负责（主模型直接读真实图片，结论标注「自检」）；**外部 GPT 评审**仅当用户明确授权 GPT 评审通道时，才用 **`scripts/zcode_vision.py --confirm-gpt-review`**（直连 CPA Responses API 的 `input_image`，只收磁盘真实图片；**不是** `copilot` Skill 的正式 REVIEW，没有台账 / 审计 / 轮次限制）。**只有用户明确点名 Copilot、或明确要求使用 `copilot` Skill / Copilot 正式 REVIEW 时**，才走 `~/.zcode/skills/copilot/` 的正式 REVIEW 通道。未授权时不得用 zcode_vision 绕过 Copilot 的启用限制。本文件里的「专家评审」若不特别注明，均指 **DesignWise 自主执行的文字级 / 证据级评审**（`references/critique-guide.md`），**不等于**视觉评审——视觉评审只出现在 **Gate 1（§2.6.1）** 与 **Gate 2（§3.7.6）** 两个节点。
>
> 🔴 **本分支的核心时序不变式（2026-10-16 修订）**：**视觉方向必须在真实候选图产生之后才被决定。** 提示词专家评审（§2.6）**只能**判文字可判项、**不能**决定方向；Gate 1（§2.6.1，默认执行者是原生自检；授权后 `scripts/zcode_vision.py --confirm-gpt-review`；用户点名时 Copilot 正式 REVIEW）**必须**在**多个真实候选图已生成**之后执行，基于像素比较并给出**推荐**；**最终方向由用户在看完真实候选图后选定**。**禁止**任何形式的「未见图先定方向」。

**贯穿三条的效率硬规则**（全文以此为准）：

1. 🔴 **先见真实候选图，再定方向**——初始提示词 → 提示词专家评审 → **生成多个真实候选方向图** → **Gate 1（默认原生自检；授权后用 `scripts/zcode_vision.py --confirm-gpt-review`；Copilot 仅点名）** → **用户选定方向**。**禁止**在真实候选图产生之前用文字评审代替视觉判断、或自动替用户定方向（§2.6 / §2.6.1 / §2.7）。
2. **方向只选一次，选定后收敛**——用户确认方向后**重新生成收敛型最终提示词**（§2.8），只锁定已选视觉语言，**不重新引入新方向、不重跑方向选择**。
3. **第二次评审允许低成本定向迭代**——视觉不满意针对该方向重新生图 / 交互不满意改现有 HTML / 必要时两者结合；**不从头重复整个流程**，也不同时维护多套 HTML（§3.7）。

**职责分工（不变式）**：

| 谁 | 负责 | 不负责 |
|---|---|---|
| **GPT（图像生成）** | 视觉创意探索、候选方向图与概念效果图、原创插画/背景/场景图 | 产品判断、真实 UI、交互逻辑 |
| **原生自检**（默认）/ **`scripts/zcode_vision.py`**（授权后）/ **`copilot`**（仅用户点名） | 基于**真实像素**比较候选方向、给推荐与依据（Gate 1，§2.6.1）；阶段门槛评审（Gate 2，§3.7.6）；证据不足时明确缺证 | 执行工程任务；自行读磁盘取证；替用户作最终选择；被自动升级为 copilot 正式 REVIEW |
| **DesignWise（专家机制）** | 需求理解、产品价值判断、**提示词级文字评审**（§2.6）、生成候选方向图、默认在 Gate 1 / Gate 2 做原生自检；授权后才调用 `scripts/zcode_vision.py --confirm-gpt-review`（用户点名 Copilot 时才改走 copilot 正式 REVIEW）并据结论推动流程、控制 GPT 介入频率、工程实现、执行与客观验证 | 不做视觉创意赌博，不把效果图当界面交付，不重复实现 GPT 调用与图片通路，不在无真实图时宣称视觉结论 |
| **用户** | 看完真实候选图后**选定视觉方向**（唯一能做的方向决策）；命中 §2.9 的情形必须由用户决定 | —— |

**判断顺序仍是**：有用 → 好懂 → 舒服 → 有意义。GPT 出的图再好看，不解决真实用户问题就是精致的 slop。

## 1. 能力探测（第一步，必须实测，不得凭配置断言）

GPT 指 **OpenAI 实际提供的图像生成能力**（gpt-image 系列），不得用其他模型冒充。

🔴 **模型口径（唯一权威，勿在别处重复写死版本号）**：默认模型**不在此文件硬编码**，而由能力检测确定的**当前可用型号**决定。判定顺序：① ZCode 默认入口 `scripts/zcode_image.py --health` 返回的可用 image 模型清单（实测 2026-10-24 含 `gpt-image-1.5` / `gpt-image-2` / `gpt-image-2.5` / `gpt-image-2.5-flare` / `gpt-image-2.5-sunburst`）；② 脚本默认 `gpt-image-2.5`（`--model` 可覆盖）。**取两者交集里最可用的 gpt-image 系列型号**；当前实测默认即 `gpt-image-2.5`。
> 调用时**不必显式传 `--model`**（走脚本默认值即最新已验证型号）；只有当检测出的默认型号变化、或需改用清单内其它型号时才调整，且型号名仍须落在 gpt-image 系列内。
> ⚠️ **别把 `gpt-image-2.5` 抄进多个文档**——SKILL.md 等位置一律**引用本节**（写「§1 默认模型」而非字面版本号），型号升级时只改本处口径，不产生多处失同步。

**铁律：发现模型名 / 工具配置 / API 文档 ≠ 生图可用。** 只有真实调用并拿回图片才算通过。

**探测三步（按序，任一步给不出结论就往下走）**：

> 🔴 **成本口径——第 1、2 步零成本，第 3 步会真实出图**：第 1 步 `--health` 只探测接口、不出图、不花额度，可直接跑；第 3 步「真实出图」会消耗额度或产生费用——**在本轮设计任务范围已明确的前提下，可直接进入真实出图，不需要逐次申请付费授权**（GPT 生图是 DesignWise 正常的模型能力，与日常代码 agent 调用付费大模型一致，口径见 §1.5）。进入生图环节时向用户**说明**「调用哪个模型、走哪条链路、是否按量计费」——这是**告知**，不是**审批**。模型由本节检测确定。

1. **有没有生图通路**：查当前环境是否存在可调用的图像生成能力
   - 本机首选：`scripts/zcode_image.py --health`（ZCode 默认入口，只探测、不出图、不花额度；生图方法论见 `~/.zcode/skills/huashu-gpt-image/`）
   - 其他环境：OpenAI Images API（`/v1/images/generations`、`/v1/images/edits`）或等价服务
2. **是不是真 GPT**：确认返回的模型名属 **gpt-image 系列**（如 `gpt-image-2.5` / `gpt-image-2` / `gpt-image-1.5`）。模型名对不上 → 不叫 GPT 生图，如实说明。
3. **真实出图（🔴 付费步骤，成本口径见 §1.5——任务范围内可直接生成）**：用一张最小测试图实跑一次，确认：

| 检查项 | 判定 |
|---|---|
| 是否真实调用生图端点 | 有本次调用的成功记录（响应 / usage 记录），可关联到输出文件 |
| 是否返回实际图片 | 文件存在、能解码打开、非空白/纯色 |
| 能否本地保存 | 落盘成功，不依赖临时链接 |
| 尺寸、格式正确 | 目标像素 / PNG 或 JPG，元数据与预期一致 |
| 是否支持后续编辑 | 图生图（参考图编辑）通路存在 |
| 是否满足素材使用需求 | 单元素、可集成、无多余 UI |

> ⚠️ **来源证据不可省**：普通程序（SVG + 图像合成）也能产出「像样的 PNG」。判「真模型生成」须有**本次调用成功记录 + 与输出文件的关联**；只检查「目录里多了文件」「PNG 里没有元数据」都不够。

**探测结论只有两种**：
- **PASS**：真实 GPT 生图成功 → 走本文件第 2-6 节。
- **FAIL**：不可用 → **明确报告技术限制并暂停生图环节**；可交付完整英文 prompt 供用户在 ChatGPT 出图后把图交回继续。**不得假装成功，不得静默改用 HTML/SVG 冒充概念图**。仅当用户本轮明说「用 HTML 就行 / 不要效果图」，或任务判定为「不适用」（幻灯片/信息图/动画/纯排版/局部微调）时，才走 HTML/CSS 通路（边界见 §2.2.1 / §3.6.4）。

> ⚠️ **PASS ≠ 必然出图**：探测通过只说明「通路存在」。是否出图由**任务是否需要**决定（§1.5 生成范围 + §2.1 判定），**不为「探测」而生成**。

## 1.5 生成范围与成本控制（🔴 自助执行 · 不再逐次审批）

> **一句话**：**GPT 图片生成是 DesignWise 正常的模型能力**——用户已要求做视觉概念探索、且任务范围明确时，**直接生成，不需要每次生成前额外申请付费授权**。这与日常代码 agent 调用付费大模型（按任务自主调用、事后如实记用量）是同一条基本原则。

**为什么取消逐次付费 Gate**：实测一次 App 图标的正常探索，重复的逐次授权把「做设计」卡成「做审批」，而费用风险其实很低（方向数按任务价值定、无批量、定向迭代只重出受影响的那张）。把「该不该调」交给 agent 的任务判断、把「花了多少」如实记账，比每次停下来等签字更能发挥 GPT 的探索速度和视觉创造力。

**自助出图的前提（同时满足才直接生成）**：
1. **任务命中本通路**（§2.1「需探索新视觉方向」——App 图标 / 启动页视觉改版 / 首页或重要页面整体设计 / 多页面视觉体系 / 品牌视觉探索 / 插画主视觉 / App·Web·交互原型），或阶段 4 的验证素材 / 阶段 6 的正式素材需求；
2. **在本轮任务范围内**：用户的目标与交付物已明确，生成服务于它；
3. **数量符合实际需要**（🔴 2026-10-16 修订）：**候选方向图是必要投入**——每个候选方向各 1 张真实候选图（§2.2 第 8 项），**这是 Gate 1 与用户选定方向的唯一视觉依据，不算「多余生成」**；用户选定方向后再用**收敛型最终提示词生成正式概念图**；定向迭代只重出受影响的那张；阶段 4/6 素材按清单一次列全——**不为「凑数」「再来一张更好」「探测」反复生成**。

> 🔴 **不要为了省图而退回「生图前定方向」**：只出方案卡不出候选图，会让 Gate 1 拿不到像素、用户也失去选择依据（§2.2.1 明确禁止）。**方向的正确性优先于省下几张候选图的成本**——方向选错造成的返工远贵于几张候选图。同时**也不为凑数硬出方向**（§2.2：方向数按 L2 规则定；单方向仅限用户明示或选定后迭代，并记录原话）。

**不再需要**：用户本轮逐次的「授权出 N 张」原话，也不用把审批四要素写进 `direction-approved.md` 的审批表。

**仍需如实记录（成本与用途留痕，不是审批）**：模型名（由 §1 检测确定）、本次生成的张数与用途、以及平台能拿到的用量/费用记录（工具返回什么记什么）。落在 **`design-brief.md` 的「## 生成记录」一节**（§2.0）或项目产物目录，**供回溯，不阻断执行**。🔴 **不写进 `direction-approved.md`**——那个文件只在**真实视觉确认之后**创建（§3.3）。

**成本控制（自助的配套约束）**：
- 按实际任务需要决定生成数量，优先避免无效重复调用
- 调用失败先读原因（额度/网络/上游拒绝），**有限重试**（同一次失败不盲目重试；先判明是否已受理），防止无限循环
- **编辑优先**：同一方向的微调走图生图（`--ref`），不从零重生成（§7）
- 已有合格素材优先复用，不为微小差异反复生图
- **任务规模明显扩大**（如从「3 张概念图」变成「批量产品素材」）→ 按**正常任务范围变更**处理（与用户确认范围），**不是**恢复逐张付费审批

**🔴 安全边界（取消的是审批，不是别的）**：本节只取消「DesignWise 普通 GPT 生图调用的专属逐次付费审批」。**不得**借此修改 CPA 凭据 / 模型路由 / 账户计费配置，不得开通新付费服务、扩大文件/系统/网络权限、绕过其他安全授权规则（`git push`、发布、生产修改等高风险操作仍按用户全局安全规范的原授权要求执行——本 skill 不覆盖也不放宽它们）。**发现全局安全规则与新机制冲突**时，先说明真实冲突与影响，**优先在 DesignWise 范围内解决**，不擅自改全局安全策略。

**拦截/暂停的合法动作（仅在任务判定或技术受阻时）**：
- **任务不命中本通路**（局部修改 / Bug 修复 / 功能实现 / 适配 / 结构性任务）→ 不进生图，走对应链路（§2.1）
- **零成本例外** → §1 第 1 步 `--health` 只探测、不出图、不计费，可直接跑（结论仍须并入判断）
- **禁止** → 用 HTML 截图 / 代码绘图冒充 GPT 生成图（§2.2.1）；超出任务范围的大规模批量生图（按范围变更处理）

### 2.0 Visual Brief（三方向探索的共同输入 · 自动生成）

**为什么**：prompt 的质量上限由输入决定。三张概念图若共用一句含糊需求，必然糊成同一张；差异来自**同一份 Brief 的三个不同侧写**。所以先由 agent **自动生成**一份 `design-brief.md`（`huashu-gpt-image/references/prompt-patterns.md` 的方法论照用，本 skill 只规定输入结构）。

**Brief 六段（从产品需求自动推导，用户无需参与）**：

| 段 | 内容 | 来源 |
|---|---|---|
| 1. 产品定位 | 是什么、一句话说清、不可变的结构边界（tab/页面数） | spec.md |
| 2. 用户画像 | 一个具体人物 + 一个具体时刻 + 由画像推出的硬 UX 约束（字号/点击区/无障碍） | spec.md |
| 3. 核心价值 | 有用→好懂→舒服→有意义 四层，各一行 | `references/product-value.md` |
| 4. 情绪目标 | **要什么**（一处真实情绪机会，见下；没有就写「本版不加情绪价值」）/ **不要什么**（硬门控：禁焦虑、禁伪成就、禁医疗暗示） | spec.md + `references/product-value.md` §0.5 |
| 5. 视觉关键词 + 色彩 | 整体 + 逐页关键词；已知 token 色值（有则填） | 品牌资产 / 已定方向 |
| 6. 差异化维度表 | 三个方向各自的**母题 / 骨架 / 情绪**（见下） | §2.2 |

**两个"明确"，Brief 里必须写死**：
- 🔴 **本轮产物性质**：开头标 `性质：概念探索（exploration only）` 或 `性质：正式素材制作（production asset）`。两者 prompt 规则不同（§2.3 vs §4.3），**不许混用**——概念图可含 UI，正式素材不许含整张 UI。
- 🔴 **事实来源优先级**：**真实业务数字、中文文案、交互逻辑一律以产品规范（spec.md / brand-spec.md）为准，GPT 输出不作数**。Brief 里每条数据后标注其真实来源。

**🔴 约束分层（Brief 必写，直接决定 prompt 的软硬）**：把需求拆成两类，分开放，**不许混写成一大串禁令**：

| 类别 | 是什么 | 在 prompt 里怎么写 | 举例（计步器图标） |
|---|---|---|---|
| **硬约束** | 违反即不成立的底线——产品用途、已有品牌体系、必要尺寸/安全区、可访问性、法律与伦理红线（禁医疗误导、禁虚假数据） | **写进每条 prompt 的正文/禁令段，明确、可核对** | 一眼看出是「走路/计步」；底色 `#17375E` 满底 + 图形 `#F4F5F3` 两色；图形落在 66dp 安全圆内；48px 仍可辨；无文字、无医疗元素、无金色 |
| **可探索约束** | 构图方式、图形组合、视觉隐喻、具体表现手法——**这些是创意空间，交给 GPT** | **只写"希望传达什么"，不写"必须用哪个元素"** | 「用形状建立识别，语气克制可信」；**不写**「首条必须最高最粗」「禁止出现足迹」这类锁死手法的句子 |

> 🔴 **不要为了让方向看起来不同，就机械互斥元素**：例如「足迹 + 起点刻度」可以是**有效方案**，不应仅因为「A 方向要求不用足迹」就禁止这种融合。**差异应在"表达重点与气质"上，而不是靠禁掉合理元素来强行区分**。硬约束之外，允许 GPT 在品牌边界内提出更好的视觉表达。

> **参考资产（可选、有条件时必用）**：
- **可用**：现有界面真机截图、已选定方向的渲染截图、品牌元素（logo / 色板 / 字体规范）。
- **怎么用**：走图生图 `--ref <截图>`（`/v1/images/edits`），把「保真结构 + 换视觉语言」写进 prompt——比纯文字描述稳得多。
- **红线**：参考图只提供**结构与气质**，其中的**数字/文案仍以 spec 为准**（截图里的旧数据不得进 prompt 当事实）。

> **Brief 是"探索"还是"素材"的判断门**：先判性质，再选 prompt 规则。**判断不出的，按概念探索处理**（更保守：探索态不污染交付）。

**🔴 本文件同时承载「阶段 2 的过程记录」（不另建文件）**：`design-brief.md` 除六段 Brief 外，追加三节——

| 节 | 什么时候写 | 内容 |
|---|---|---|
| `## 创意决策记录（生图前）` | §2.6 提示词专家评审完成后、**生图之前** | 原始候选方向与方案卡 / 提示词评审关键发现（Keep / Fix）/ 本轮人工参与（格式见 §2.8） |
| `## 创意决策记录（生图后 · Gate 1）` | **真实候选图生成后**、Gate 1（§2.6.1）执行完 | 候选项与图片路径 / 证据条目 ID / GPT 裁决与推荐方向 / 依据与风险 / 用户最终选择 / 收敛型最终提示词 |
| `## 生成记录` | 每次概念图生成之后 | 模型名 / 张数 / 用途 / 可获得的用量记录（成本留痕，见 §1.5 / §4.7.3） |

> 🔴 **为什么分两节**：生图前只有**提示词级**结论（不构成方向决策），生图后的 Gate 1 才有**像素级**结论——两者混写会让「还没看图」的判断看起来像「已定方向」。**方向决策的结果只在第二节里**。
> 🔴 **为什么不写在 `direction-approved.md`**：那个文件是**真实视觉确认 Gate** 的物化证据（含义见 §3.3）——用户确认前就往里写，会让「用户还没确认」的状态**看起来已经批准**，等于提前满足 Gate。**用户确认前 `direction-approved.md` 不存在，是正常状态，不是缺漏。**

### 2.1 什么时候走这条（阶段 2 的触发面与强制力）

**这是阶段 2「GPT 视觉概念生图」的适用判定。** 判定对象是**任务性质**，不是产物形态的细枝末节：

**需探索新视觉方向 → 本阶段为强制前置环节**（适用场景）：
- **App 图标设计**
- **启动页视觉改版**
- **App 首页或重要页面整体设计**
- **多页面视觉体系**
- **品牌视觉探索**
- **插画、主视觉与其他视觉创意任务**

**不适用 → 不进本阶段，直接进实现与验证（阶段 6-7 或原 HTML/CSS 链路）**：
- **已有明确设计的局部修改**、Bug 修复、功能实现、适配（改的是实现，不是视觉方向）
- **简单文案或布局修正**
- 幻灯片 / deck、信息图、数据可视化（结构由内容决定，靠 GPT 画文字必糊）
- 动画 / 宣传片（走 `storyboard-basics.md` 分镜卡）
- 纯排版 / 文档型产出
- 用户明确说「不要效果图 / 直接写 HTML」

> ⚠️ **「不适用」不是「不想做时的出口」**：判断依据是**任务是否在探索新视觉方向**。幻灯片即使含视觉设计也不进本阶段，因为它的结构与文字必须由 HTML/CSS 精确控制——这是**载体不匹配**，不是省事。

### 2.2 多方向视觉探索的要求（与原有三方向门同构）

各方向共用**同一份需求与核心功能**（即 Phase 3 spec，含「用户 + 核心行为」一行），差异必须在**视觉方向 / 布局 / 表达方式**上明显区分：

- ✅ **不只是换配色**：配色差异是入场券不是方向差异。各方向应在**布局骨架、信息组织、视觉母题**上结构性不同
- ❌ **不虚构必要功能**：各方向都要覆盖同一份核心功能，不得为了让某套好看而发明不存在的功能
- ✅ **以产品价值判断约束设计**：各方向是同一件真实事的三个价值侧重（如 极简数字型 / 高密度仪表盘型 / 激励叙事型），不是三个臆想需求
- ✅ **标明概念参考**：效果图默认是「概念参考」，不是可直接交付的界面
- 🔴 **硬约束之外允许融合**：方向间的区分应落在**表达重点与气质**上；**不要为了"看起来不同"就把合理元素在方向间机械互斥**（如禁止某方向出现足迹）——那会不必要地压缩创意空间（§2.0 约束分层）

**三套差异化逻辑**（沿用 Fallback 三套逻辑，只是产出换成效果图）：
- **逻辑一 · 秒数轮盘**：`date +%S` % N 从风格库取号，强制打破「每次都选安全极简」
- **逻辑二 · 现实参照**：锚定一个真实存在、设计极出色的标杆产品/站点，迁移其设计语言
- **逻辑三 · 最佳设计师**：设想预算无上限时最适合本产品的工作室/设计师，启用其设计哲学

**差异必须落到 prompt 上（不是只写在 Brief 里）**：各方向的 prompt 至少三处结构性不同——**母题（visual motif）/ 布局骨架 / 视觉母题对应的形式元素**。若两个 prompt 的差别只在配色与形容词，**不算差异化**，退回重写。检验法：把几条 prompt 并排看，能否只读 prompt 就预言"这几张图会明显不同"？不能 → 差异不足。

> **参考资产参与差异化**：方向二（现实参照）优先用 `--ref` 喂真实标杆截图或本产品现有截图；方向三（最佳设计师）可喂品牌资产。方向一（轮盘）保持纯文字，作为「无既有惯性」的对照。

> **方向数量（不人为规定固定数）**：具体数量由**任务复杂度、信息价值与实际生图成本**决定——价值低或用户已给出充分约束时可只做 2 个，**不要为凑数硬出**；**也不需要固定上限**。三种差异化逻辑是默认取材方式，不是必须凑满三种。
>
> 🔴 **但必须真的有差异**：**若两个候选实际上只是间距 / 圆角 / 尺寸等微小变化，不得把它们包装成两个独立视觉方向**（那是伪多方向，违反 §2.2 的差异化判据）。
> 🔴 **方向数量下限**：L2 默认 3 个方向，确有依据可降为 2 个并写进 `design-brief.md`，**不得只做 1 个**；只有用户本轮明示「一版就行」或已选定方向后的迭代才可单方向，并记录用户原话。**不得把单方向包装成多方向比较**（Gate 1 相应只做单方向评审，§2.6.1）。

**🔴 每个候选方向的产物 = 「候选方案卡」+「1 张真实候选图」**——方案卡七项供 §2.6 的提示词专家评审逐条对照；真实候选图供 §2.6.1 的 Gate 1 在像素上比较：

| # | 字段 | 要求 |
|---|---|---|
| 1 | **核心概念** | 一句话说清这个方向在表达什么（不是"用了什么风格"） |
| 2 | **用户应识别的产品价值** | 用户第一眼该读出「这是干什么用的」——呼应 `references/product-value.md` 的「有用」层 |
| 3 | **视觉母题与构图** | 图形骨架 / 母题 / 排布与留白（母题必须从内容长出来，见 Fallback 第五问） |
| 4 | **品牌一致性** | 与 `brand-spec.md` / 既有视觉体系的关系（色值、气质、禁忌） |
| 5 | **预期优势** | 这个方向相对其他方向真的强在哪（可判定，不写"更高级"） |
| 6 | **潜在风险** | 自己先说出它可能翻车的地方（用途识别 / 小尺寸 / 可实现性 / 与品牌冲突） |
| 7 | **完整 GPT 生图 Prompt** | 英文、按 §2.3（图标/符号走 §2.3.1）自动生成，**可直接投喂生图模型** |
| 8 | **真实候选图**（`design-demos/direction-*.png`） | 用第 7 项 prompt 实际生成的 1 张图——**这是 Gate 1 的唯一视觉判据**，落盘文件而非描述 |

**四条硬要求（针对"看起来有几种其实只有一种"）**：

- 🔴 **不只是不同配色**——差异要落在母题 / 骨架 / 表达重点上（判据见上方"差异必须落到 prompt"）
- 🔴 **不依赖设计师名字代替创意**——参照设计师 / 工作室名可以写进 prompt 帮助定气质，但**不能替代核心概念与形式表达**（同 §2.3.1 第 3 条：抽象形容词与名人不构成质量保证）
- 🔴 **硬约束必须进入实际 Prompt 正文**——只写在 Brief 表里不算（实测教训见 §2.3.1 第 1 条）
- ✅ **可探索约束留给 GPT**——构图方式 / 图形组合 / 隐喻手法只写"希望传达什么"，不锁死手法；**也不机械禁止不同方向使用相似的有效元素**（§2.0 约束分层）

### 2.2.1 🔴 展示真实图像结果 + 禁止静默回退为代码绘图（硬约束）

**必须**：
1. **真正调用 GPT 图像生成能力**——不是默认进入 HTML/CSS 绘图。能力可用且任务需要时，本阶段**不许跳过生图直接画 HTML**。
2. 🔴 **每个候选方向都要有真实候选图**（§2.2 第 8 项）——**只出方案卡不出图 = 方向探索没做完**，Gate 1 拿不到像素就无从比较（§2.6.1）。这是本分支 2026-10-16 修订的核心：**视觉方向必须在真实图基础上被选定**。
3. **展示真实图像结果**（落盘文件），让用户直观比较——**不许用文字描述代替图**。
4. **保持视觉方向与产品定位一致**，同时允许真正有价值的创意探索。
5. **概念图不要求满足最终工程资源规范**（尺寸/格式/透明背景等在阶段 6 才管）。

**禁止（任一条即违规）**：
- ❌ 未经说明**以 HTML 截图冒充 GPT 概念图**
- ❌ 以 **SVG 或程序化绘图代替强制概念生图**
- ❌ 🔴 **只交方案卡 / 文字描述就宣称「多方向探索完成」或直接进入方向选择**（候选方向必须有真实图）
- ❌ 🔴 **在真实候选图产生前就替用户定下方向**（用文字评审或 auto 决策代替 Gate 1 + 用户选择）
- ❌ **用像素级微小变化伪装成两个独立方向**（伪多方向，§2.2）
- ❌ 在**方向定下来之前**为各个候选方向分别制作 HTML 原型（见阶段 4，§3.6）
- ❌ 超出本轮任务范围的大规模批量生图（按任务范围变更处理，§1.5）

**🔴 能力不可用时的正确动作——明确说明并暂停，不静默回退**：

| 情形 | 正确动作 | 禁止 |
|---|---|---|
| **能力探测 FAIL**（生图通路不存在或非 gpt-image 系列） | **明确报告技术限制**，暂停阶段 2；可准备**完整的生图要求**（英文 prompt，§2.3）交用户在 ChatGPT 生成后把图交回 DesignWise 继续阶段 3 | 静默改用 HTML/CSS/SVG 程序绘图冒充「概念图」 |
| **工具报错**（额度/网络/上游拒绝） | 读失败原因，如实说明；**有限重试**（同一次失败先判明是否已受理，不盲目重试，§7） | 悄悄回补一套 HTML 顶上 |
| **任务不命中本通路**（局部修改 / Bug 修复 / 结构性任务） | 走对应链路，不调 GPT（§2.1） | 为「流程完整」强行生图 |

> **区分两种「回落」**，别把二者混为一谈：
> - **合法回落（能力层面）**——用户**本轮明说**「用 HTML 就行 / 不要效果图」，或任务判定为「不适用」（§2.1）。此时回落 **HTML/CSS 原生实现**（**L1 局部优化直接改现有 UI，不铺三方向**；L2 的 HTML fallback 仅限 SKILL `L2 的候选形态` 三种例外）是**用户/规则的选择**，须在**方向确认时**把回落原话或判定依据一并记入 `direction-approved.md`（Gate 文件协议，§3.3）——**不是在回落判定那一刻就创建该文件**。
> - **违规回退（静默层面）**——能力可用、用户也没说不做，却**因为图难出/懒得出**，把 HTML 截图或 SVG 当概念图交给用户。这**掩盖了真实阻塞**，是本文档 §9 点的明确反模式。
>
> 一句话：**回落要写得出来是谁的决定；写不出来就是静默回退，不许做。**

### 2.3 生图 prompt 自动生成规则（英文）

概念图**允许出现 UI 元素**（它就是界面探索），但仍受反 slop 约束。**prompt 由 agent 从 spec 自动生成，不要求用户写**；提示词方法论复用 `huashu-gpt-image`（本 skill **不复制其功能**，只规定自动生成规则）。

🔴 **两种提示词，职责不同（2026-10-16 新增区分）**：

| 阶段 | 提示词 | 目标 | 什么时候用 |
|---|---|---|---|
| **探索期** | **初始视觉提示词**（每个候选方向一条） | **服务「视觉方向探索」**——让几个方向真的长得不一样，用于产生候选方向图。**不追求**直接产出最终生产素材 | §2.2 生成候选图、§2.6.1 Gate 1 之前 |
| **收敛期** | **收敛型最终提示词**（用户选定方向后一条） | **锁定已选视觉语言**，提高正式概念图的**稳定性、明确性与可产品化程度** | §2.8，用户选定方向之后 |

🔴 **探索提示词 ≠ 最终概念图提示词**：**不得**把探索期的某一条 prompt 原封不动拿去当最终概念图的 prompt（§2.8 规定收敛期必须重新生成/优化）。同理，**不得**在收敛期借「优化」之名**引入新的视觉方向**——那是重跑方向选择，禁止。

**初始视觉提示词的必备内容（不为完整而堆无价值细节）**：

1. **产品 / 页面目标**（这是谁的什么界面 / 什么用途）
2. **核心视觉语义**（第一眼必须读出什么）
3. **目标用户或使用场景**（给谁看、在什么场合看）
4. **风格方向**（真实参照名，不用「极简」「高级」这类形容词）
5. **构图 / 形态 / 层级等必要约束**（骨架、信息优先级、留白）
6. **必要的技术或品牌约束**（精确色值、尺寸与安全区、禁用元素、必须出现的品牌元素）

> ✅ **只写必要的**：以上六项是**下限不是清单**——把无关项补进去只会稀释提示词、增加歧义。**没有依据的细节不写**，缺项由 spec 推导。

🔴 **语言规则（硬）**：交给生图模型的 prompt **一律英文**——gpt-image 系列对英文指令最稳。中文只用于①与用户沟通 ②内部推理 ③需要「精确渲染的中文文案」时**以引号原样嵌入**（并注明 `render this Chinese text exactly`）。**验收口径**：任一新设计任务都能自动产出一段英文生图 prompt，无需用户参与。

**自动生成六槽位（默认面向"界面"类载体；图标/符号类见下方专用条款）**（按序拼接；缺项由 spec 推导补全，不得留空）：

| # | 槽位 | 写什么 | 反例 |
|---|---|---|---|
| 1 | **Subject** | 谁的什么界面（具体产品 + 具体屏幕） | `an app` |
| 2 | **Core action** | 首屏第一眼服务的那件核心行为，**放最前** | 罗列全部功能 |
| 3 | **Layout & hierarchy** | 布局骨架 + 信息层级（谁大谁小） | `clean layout` |
| 4 | **Visual style** | **真实参照名**（工作室 / 设计师 / 产品），不用形容词 | `minimal elegant` |
| 5 | **Color & mood** | 底色 + 单 accent + 情绪基调（有色值更佳） | `nice colors` |
| 6 | **Medium & ratio** | 媒介与比例（iPhone home-screen mockup / upright 2:3 / no device frame） | 只写 `image` |

**必写禁令（每条 prompt 结尾固定带上）**：`no device frame unless showing the hardware`；非官方致敬加 `no brand watermark · unofficial tribute`；`no gradient slop · no emoji icons · no lorem text`。

### 2.3.1 🔴 图标 / 标志 / 符号类载体专用条款（App 图标、启动页标志、favicon、品牌符号）

六槽位是为"界面"设计的；**图标是一枚独立符号，槽位要换**。此时按下面结构写（对应"载体不匹配就别硬套"）：

| 槽位 | 写什么 |
|---|---|
| **Subject** | 什么产品的什么图标（`launcher icon for a walking step counter app`） |
| **First-read (用途识别)** | **第一眼必须读出什么用途**——这是图标的第一判据（`instantly reads as walking / step counting`） |
| **Composition** | 图形骨架（可用元素、大致排布、留白）——**写"希望传达什么"，不锁死具体元素数量与手法** |
| **Style** | 平面几何 / 硬边 / 无渐变无阴影（**写视觉特征，不写设计师名当质量保证**） |
| **Color** | 精确色值 + "exactly N colors"；🔴 **明确是否满底、是否不透明** |
| **Medium / ratio** | 方形 1:1、无设备框、1024×1024、**不透明满底 PNG** |
| **Safe area / 小尺寸** | 图形落在安全区内、边长 ≥ 若干 px 仍可辨（如 `legible at 48×48`） |

**🔴 图标 prompt 的三条硬规则（针对上一轮实测缺陷）**：

1. **数量与关键几何必须写进 prompt 正文，不能只写在 Brief 表里**——实测教训：A 方向「刻度 ≤6 条」只写在 `design-brief.md` 的差异化表、**没写进 prompt**，模型出了 9 条，48px 退化成条形码。凡"必须精确的数量/比例"，一律进 prompt 正文。
2. **默认要求不透明满底**：实测教训：三方向里两方向返回了**透明背景（预乘 alpha）**，评审时按 navy 底合成才露馅。凡需要满底的图标，prompt 必须写 `fills the entire square edge to edge with an opaque solid background, no transparency`。
3. **不把参考设计师 / 概念理论当作视觉质量保证**：`ISOTYPE`、`Feltron Annual Report`、`Vignelli` 这类**风格来源可以写（帮模型定气质），但不能替代可核对的质量条款**——必须同时写清「用途识别 / 构图骨架 / 色值 / 小尺寸可辨 / 安全区」。**禁止**用「极简」「高级」「大师级」等抽象形容词代替质量条款。

**🔴 图标 prompt 的负面清单要短且一致**：只列**跨方向共有的真红线**（无文字、无医疗元素、无金色、无 3D/发光/阴影、无绿色渐变）。**不要把"为了区分方向"的元素互斥写进负面清单**（如 B 写 `no tick-mark scale`、A 却以刻度为主体）——那会制造自相矛盾的约束，且不必要地压缩创意。方向差异靠**表达重点与气质**区分。

**尺寸**：iPhone 端默认竖幅 `1024×1536`；桌面 Web 默认 `1536×1024` 或 `1920×1080`（deck 走原链路）；**图标 / 标志默认方形 `1024×1024`**。**比例诉求写进 prompt**，别假设传了 size 模型就照画（见下方 ⚠️）。

**落盘**：prompt 原文写入 `assets/img-prompts/<name>.md`（一图一档，见 §4.4）——为可复现与可迭代，不是为写文档。

**示例**（概念图 · 自动生成）：

> `iPhone home-screen mockup of a personal finance app, primary focus: one-tap expense logging, oversized amount input as the first-screen hero, single-column card stack with a bottom tab bar, visual style of the Stripe design team, warm off-white #FAF7F2 background with a single terracotta #C04A1A accent, upright 2:3 composition, no device frame, no brand watermark, no gradient slop, no emoji icons, no lorem text`

> ⚠️ **CPA 通路不保证按请求尺寸出图——「请求尺寸」与「实际返回尺寸」是两个值，不要混为一谈**（实测：请求 `1024×1536` → 返回 `1024×1536`（一致）；请求 `1024×1024` → 返回 `1254×1254`（不一致））。因此：**比例诉求写进 prompt**（如「竖幅 2:3 构图的手机界面」）以引导模型自选画布贴近目标比例；脚本只做最后一步像素适配——`--fit cover` 裁边满幅、`--fit contain` 补边不裁主体。**别假设「传了 size 模型就按此比例画」，也别据请求尺寸推断产物尺寸**，一律以实际落盘文件为准。

### 2.4 🔎 生成结果质量自检（最终概念图生成后必做 · 是"要不要修"的判断，不是评分）

> 📍 **执行位置**：本节作用在**已生成的真实图**上，在新流程里出现在两处——① 阶段 2 生成候选方向图之后、Gate 1（§2.6.1）之前（逐张自检）；② 用户选定方向后用收敛型最终提示词生成正式概念图之后（§2.8 → 此节）。**不要按节号顺序执行**，阶段 2 的完整次序见文首「阶段 2 执行顺序」表。

> 生图完成后、**展示给用户之前**，先自己看一眼：**这张图作为"这个产品的图标/概念"，立不立得住。** 这一步**替代不了 Gate 1 的视觉比较、也替代不了用户的方向选择权**，只保证用户看到的是**已判明状态的图**——不是把明显违反硬约束的图当"完成态"摆上去。

**第一问（核心，凌驾其他指标）：用户能不能一眼识别与理解它？**
- 把图放到**目标使用尺寸**（图标取 48/96/144px；界面取真实屏宽）看：还能不能读出用途 / 核心信息？
- 问一句「一个不认识这个产品的人，第一眼会以为它是干什么的？」——答不上或答歪就是识别问题，**优先于任何量化指标**。

**第二问：是否违反品牌 / 产品硬约束？**（逐条对照 §2.0 的硬约束清单）
- 色值是否精确落在 token？是否混入禁用色（如金 / 绿）？
- 🔴 **背景：先按目标底色合成，再判断「满底」是否成立**。**透明背景（预乘 alpha）在"要求不透明满底"的图标上就是硬约束违反**。实测教训：三张概念图里**两张是透明底**；若不先合成、只看像素值，会误判成「有暗角 / 光晕」，甚至误判成「满底合规」。
- 是否出现**未经要求**的光晕、渐变、阴影、纹理、文字？（模型自加的「美化」要与 prompt 明确要求的元素区分开）

**第三问：是否有明显的工程实现障碍？**
- 图形是否有不必要的复杂细节、细描边、空心层（48px 或 monochrome 层会丢）？
- 落到 Adaptive Icon 三层（前景 / 背景 / monochrome）有没有结构性障碍？

**可用的辅助手段（是证据，不是判据）**：缩放预览、遮罩裁切模拟、逐像素色合规扫描、连通块 / 腐蚀存活率、**透明通道检查**。
> ⚠️ **技术指标是辅助证据，不是设计优劣的判决**：像素占比高、连通块数为 1、腐蚀存活率高，都**不能**单独推出「这是好设计」；反过来，指标难看也未必该推翻一个概念成立的方向。**用户能否识别和理解才是核心问题。**

**缺陷分级与处理（决定「修不修、怎么修」）**：

| 级别 | 判断 | 处理 |
|---|---|---|
| **硬约束违反**（用途读不出 / 品牌色错 / 出现禁用元素 / 该满底却透明） | 概念没立住或执行跑偏 | **优先明确实际问题**，判断是否需要重新生成；**只针对问题定向重出**，不无理由重生成全部方向 |
| **概念成立，仅精确几何 / 数量待调**（如刻度条数、精确比例、像素级对齐） | 视觉方向有效，只是工程精度 | **在选定方向后由矢量工程实现**（VectorDrawable / SVG），**不为精确绘制反复生图** |
| **仅工程细节**（边缘抗锯齿、裁切余量） | 位图渲染的必然产物 | 记录，进矢量阶段自然消除 |

> 🔴 **展示纪律**：视觉评审前**必须明确展示关键缺陷**（哪张、违反哪条硬约束、影响是什么）。**不得把"需要修复的概念图"报告为"已达到工程可用状态"**——概念图是探索态，工程可用性由阶段 6 承担。用户看图时要能同时看到「它的亮点」与「它哪里没做到」。

### 2.5 展示与停轮节点（阶段 2 → 阶段 3 的衔接）

> 🔴 **停轮点在哪里（2026-10-16 修订）**：**提示词的生成与专家评审不停轮**（用户不必逐条审批提示词）；**停轮点是「多个真实候选方向图已生成 + Gate 1 已给出推荐」之后**——此时展示**真实候选图 + GPT 推荐 + 依据 + 风险**，**等用户选定方向**（§3）。**用户不可达且未获授权时**，按 §2.7 的 ASSUMPTION 分支处理：只做可逆代表屏，不批量实现、不创建 `direction-approved.md`。
>
> ⚠️ **与旧写法的区别**：旧写法把停轮点放在「**单张**最终概念图之后」、用户只做事后确认；**现在停轮点前移到「**候选方向图**之后」**——因为方向必须**先由用户在真实候选里选定**，然后才收敛出最终提示词与正式概念图（§2.7 / §2.8）。

**数量满足即展示**：候选方向图**每个方向 1 张**（§2.2 第 8 项）、且各过完 §2.4 自检与 Gate 1（§2.6.1），就摆出来，**避免无意义的反复调用**（不为「再来一张更好」无限生成，见 §7）。

**展示什么**：
- 🔴 **全部真实候选方向图**（逐张标明对应方向 / 方案卡要点）
- 🔴 **GPT Review Gate 1 的推荐方向 + 依据 + 风险 + 可继续方向**（§2.6.1）——**如实呈现，不替用户选**
- 🔎 **关键缺陷如实标注**（哪张违反哪条硬约束 / 目标尺寸下哪里看不清 / 哪处只是工程精度问题，§2.4 展示纪律）
- 每个候选的一句话定位（核心概念 / 预期优势 / 自报风险）

展示后**结束回合，等用户选定 / 确认方向**——这是**真正只有用户能做的决策**（§2.9），停轮不算阻塞。**用户选定后**才进入 §2.8 的收敛型最终提示词与正式概念图。

### 2.6 🔴 提示词专家评审（生图前 · 自主执行 · 不决定方向）

> **立场**：复用 **Huashu 原有专家评审机制**（`references/critique-guide.md`）的**思考方式**——概念/立意优先、问题要具体可操作、输出 Keep / Fix / Quick Wins；**不新增评分体系、不新增专家角色、不调用额外专家子代理**。评审由当前 agent 自主完成。

**评审对象**：§2.3 产出的**初始视觉提示词 + 候选方向方案卡**（**尚无图片**）。

> 🔴 **位置固定（2026-10-16 修订）**：本节**一定在生图之前**——用通过评审的提示词去生成候选方向图（§2.2.1）。**发现问题先改提示词，再进入生图**；🔴 **不允许跳过本节直接大量生图**。
> 🔴 **本节不决定视觉方向**：它只判「提示词是否站得住、是否会产生有区分度的方向」。**方向由 Gate 1 + 用户决定**（§2.6.1 / §3）——本节结论**不能**当作方向决策。

**评审重点（提示词层，六条）**：

| # | 判什么 | 不合格信号 |
|---|---|---|
| 1 | **是否真正服务需求**（来自 `spec.md` / Visual Brief，而非自造需求） | 提示词描述的事与产品要解决的事对不上 |
| 2 | **是否能够产生有区分度的视觉方向**（几条提示词之间差异是否真落到母题 / 骨架 / 表达重点） | 几条提示词只差配色与形容词 = 生出来的图会是同一张的变体 |
| 3 | **是否存在互相冲突的要求** | 提示词内部互斥、硬约束与创意描述打架、负面清单与主体冲突（§2.3.1 第 3 条） |
| 4 | **是否存在会导致视觉歧义的描述** | 抽象形容词（「极简」「高级」）代替可核对条款；同一说法可被读成两种设计 |
| 5 | **哪些要求应留到后续产品化 / 矢量精修，而不该塞进生图提示词** | 精确刻度条数、像素级对齐、工程几何等本应由矢量阶段承担的项被写进 prompt |
| 6 | **提示词自身是否可执行、可实现** | 依赖不可控材质 / 粒子，或原生无法还原 |

> **前五项与第六项的分工**：1~3 是「该不该用它去生图」，4~6 是「生图前该不该再改一版」。**任一条不合格 → 先改提示词，再重跑本节**，通过后才进生图。

**🔴 第一原则：不能把文字推测当成真实视觉测试结果**

| 类别 | 在 Prompt 阶段能不能判 | 例 |
|---|---|---|
| ✅ **可以判**（依据方案卡与 prompt 原文） | 提示词是否来自真实产品需求；用户能否**理解预期表达**；是否符合品牌体系；方向之间是否真有差异化；是否具有可实现性；**是否存在自相矛盾的要求**；硬约束是否真的写进了 prompt 正文 | 「B 方向 prompt 里同时写了『不出现足迹』与『以足迹为主体』= 自相矛盾」 |
| ❌ **不可判**（必须等真实出图） | 48px / 目标尺寸下的**实际**清晰度；像素级对齐与边缘质量；图层叠加后的**实际**视觉层级；透明底 vs 满底的**实际**结果；真实渲染细节、抗锯齿、裁切余量；🔴 **哪个方向更好看 / 更该被选中** | 「48px 清晰度通过」——**只能断言「prompt 已写明 `legible at 48×48`」，不能断言图已满足**；「方向 A 胜出」——**只能由 §2.6.1 在真实图上判** |

**禁止句式**（写了就是越界）：

- ❌「凭 Prompt 可判定 48px 下清晰可辨」
- ❌「该方案的小尺寸表现已达标」
- ❌「满底合规 / 品牌色准确」（未见图，无从判起）
- ❌ 🔴「方向 X 明显最优 / 已选定方向 X」（**方向决策不属于本节**，须等真实候选图 + Gate 1 + 用户）
- ✅「prompt 已写明 `legible at 48×48` 与不透明满底要求——**待真实出图后按 §2.4 核对**」

**输出（针对每组候选）**：沿用 `references/critique-guide.md` 的 **Keep / Fix / Quick Wins** 形态——

- **Keep**：值得保留的优点（写清是哪一维表达立住了）
- **Fix**：需要修复的问题（⚠️致命 / ⚡重要 / 💡优化，三段式：现状 / 为什么是问题 / 改成什么）
- **Quick Wins**：低成本高价值改善（改 prompt 用词即可解决的）

> 🔴 **不机械依赖总分**：文字阶段**不打 0-10 总评分**——分数是给已成型的视觉作品的，对没有图的 prompt 打分属推测。**结合证据说明优劣**：证据就是方案卡字段与 prompt 原文，说不出证据的判断不写进报告。

### 2.6.1 🔴 GPT Review Gate 1 · 视觉方向评审（默认原生自检；授权后 `scripts/zcode_vision.py --confirm-gpt-review`；Copilot 仅用户点名 · **真实候选图之后**）

> **它是什么**：默认由 **DesignWise 原生自检**直接读真实候选图像素，输出推荐 + 依据 + 风险 + 可继续方向；**用户明确授权 GPT 评审通道后**，才交给 `scripts/zcode_vision.py --confirm-gpt-review`（直连 CPA Responses API 的 `input_image`，只收磁盘真实图片；不是 Copilot 正式 REVIEW，无台账 / 审计 / 轮次限制）。未授权时不得用该脚本绕过 Copilot 的启用限制。
> **Copilot 正式 REVIEW 仅用户点名**：仅当用户**明确点名 Copilot**、或**明确要求使用 `copilot` Skill / Copilot 正式 REVIEW** 时，才按 `~/.zcode/skills/copilot/` 的正式通道执行（`bridge_evidence.py --image` → `call_gpt.py --mode REVIEW`）。
> **它不是什么**：不是 §2.6 的替代品，不是新的评分系统，也不是新的用户审批关卡；**更不是替用户做最终产品决策**。

🔴 **时机（本节的核心，2026-10-16 修订）**：Gate 1 **必须发生在多个真实候选图已经生成之后**（§2.2.1）。**在真实图产生之前不得执行 Gate 1**——那时没有任何像素可比较，任何「方向结论」都是文字推测。

> ⚠️ **与旧写法的区别**：本分支曾把 Gate 1 放在生图前、允许「无真实图时按文字边界出结论」。**该写法已废止**：**没有真实候选图就不做 Gate 1**（阶段 2 步骤 5~6 先把图生出来），只做 §2.6 的提示词级评审。

**🔴 与相邻环节的分工（四者不互相替代）**：

| 环节 | 判什么 | 依据 | 谁执行 |
|---|---|---|---|
| §2.6 提示词专家评审 | 提示词是否服务需求 / 有无区分度 / 有无冲突与歧义 / 哪些要求该留到产品化 | **文字**（方案卡 + prompt 原文） | DesignWise 自主 |
| §2.4 生成结果质量自检 | 用途能否读出 / 是否违反硬约束 / 有无工程障碍（逐张） | 真实图 + 客观测量 | DesignWise 自主 |
| 🔴 **Gate 1（本节）** | **哪个方向最符合需求、最值得继续** / 核心产品语义是否清晰 / 是否有明显视觉误读 / 各方向最重要的差异是什么 / 哪些是**方向级问题** / 哪些只是后续产品化与矢量精修的细节 | **真实候选图**（独立于执行方视角） | **原生自检**（默认）/ **`scripts/zcode_vision.py`**（授权后）/ `copilot`（仅用户点名） |
| §3.1 真实候选图专家评审 | §3.1 七维度 + Keep / Fix / Quick Wins | 真实候选图 | DesignWise 自主 |

**走 / 不走**：

| 走 Gate 1 | 不走 Gate 1 |
|---|---|
| 已生成**多个真实候选方向图**，需要在它们之间取舍 | **尚未生成真实候选图**（此情形**禁止**做 Gate 1，先按 §2.6 改提示词并生图） |
| **用户明示单方向**（或已选定方向后的迭代）且该方向已有真实候选图（做**单方向 Review**，见下） | 结构性载体任务（幻灯片 / 信息图 / 动画 / 纯排版）→ 不进本通路（§2.1） |
| 候选图出现**用途识别**或**方向级语义**疑问，自己判不动 | 问题明显属**工程几何 / 数量 / 像素对齐**（客观可测，直接测量或在矢量阶段解决） |
| 对已有判断出现**争议**，需要独立的第二视角 | 已有明确设计的局部修改 / Bug 修复 / 适配（§2.1） |

> **单方向 Review**：仅在**用户本轮明示「一版就行」**或**已选定方向后的迭代**时使用（§2.2），并记录用户原话；**不得由执行方自行判定「只有一个合理方向」而跳过方向探索**。Gate 1 照做，但**明确写成「单方向评审」**——判「这个概念方向是否成立、用途识别是否清楚、是否值得进入产品化」，**不得伪装成多方向比较**。
> **多方向**：**一次给全候选图**（§2.2 第 8 项产出的全部），标注版本 / 角色，让 GPT 在同一轮里**比较**。**不为凑 Gate 1 而额外生成更多图片**——有几个真实候选就送几个。

**送审证据（原生自检直接读图；外部 GPT 按 `zcode_vision.py` 的图片证据约定执行；用户点名 Copilot 时按其正式 REVIEW 约定执行）**：

- 图片必须是磁盘上的真实文件，由 `--image` 读入后以真实像素内联；**不接受只给路径却不读取文件、文字描述、Base64 文本、截图里的文字描述代替像素**。
- **多个候选要一次给全**，每张写清**版本 / 角色**（如「E4 = 候选 A」「E5 = 候选 B」「E6 = 基准版本」），让 GPT **在同一轮里比较**；**不要分别送审后再由执行方拼接结论**。
- 每张候选图**附带它对应的方案卡要点**（方向名 / 核心概念 / 预期优势 / 自报风险），让「图」与「它想表达什么」对得上——但**方案卡是说明，不是视觉证据**。
- 客观测量（像素差、遮罩裁剪、对比度等）可一并提供，但必须**注明是测量、不是视觉判断**。
- **不给 GPT 喂结论**：任务文本里说清「哪张是哪个版本 / 要判什么」，执行方自评单独标注为「不构成证据」。
- **图片取不到 / 读失败** → 按 `scripts/zcode_vision.py`（用户点名时为 copilot 正式 REVIEW）的证据纪律如实失败，**不得退回纯文字结论**；按缺证处理。

**要 GPT 回答的方向级问题（与 §2.6 的提示词问题区分开）**：

1. 哪个视觉方向**最符合需求**？2. 哪个方向**最值得继续**？3. 各方向的**核心产品语义**是否清晰？4. 是否存在**明显视觉误读**（会被读成别的意思）？5. 各方向之间**最重要的差异**是什么？6. 哪些问题属于**方向级问题**？7. 哪些问题只是**后续产品化 / 矢量精修**该处理的细节？8. **推荐哪个方向，理由是什么，风险是什么**？

**输出怎么用（不只读一个 PASS / FAIL）**：至少提取——当前阶段 / 对核心目标的判断 / **推荐方向与理由** / 关键视觉问题 / 问题严重程度 / **必须修改**项 / **可以保留**项 / 风险 / 是否需要再次 REVIEW / 再次 REVIEW 的触发条件。

**结果处置**：

| GPT 结论 | DesignWise 的动作 |
|---|---|
| **推荐某方向**（或某候选明显更优） | **不自动定方向**——把「推荐 + 依据 + 风险 + 可继续方向」**完整展示给用户**，由用户在真实候选图 + 推荐之间**选定**（§2.5 / §3.3） |
| 可进入下一阶段，但仍有**可选优化** | 该可选优化**不构成**再送审的理由；随用户选定一并处理 |
| 某候选存在**影响核心目标**的问题 | 如实标注该图的关键缺陷（§2.4 展示纪律），**仍交给用户**在知情前提下选择 / 退回 |
| 证据不足（`PARTIAL（缺证）`） | **补取最小必要证据**后**只复验受影响的条件**；不让执行方猜测 |

**留痕**：结论（含证据条目 ID、推荐方向、关键发现、风险）写进 `design-brief.md` 的 `## 创意决策记录（生图后 · Gate 1）`（格式见 §2.8）；🔴 **不写进 `direction-approved.md`**——那是**用户确认真实视觉之后**才创建的物证。

**失败与缺证**：`scripts/zcode_vision.py` 非 0 退出（或响应被截断 / 适配器不可用）→ **如实报告「未获得有效视觉裁决」**，不伪造、不静默改模型或链路冒充，**不得静默切换为 Copilot 或自动无限重试**；此时**如实告知用户「本轮缺 GPT 推荐」并交候选图**，由用户直接选（这是缺证，不是验证通过）。用户点名 Copilot 时若其正式 REVIEW 不可用，同样按缺证处理。

**🔴 停止条件（禁止低价值循环）**：Gate 1 只负责**方向取舍这一次决策**。用户选定方向后，**同一批候选不再重送**；除非出现**新的视觉决策问题**（实质视觉变化 / 进入新阶段 / 新视觉问题 / 争议 / 客观验证无法解决 / 需重选方向），否则**不重新调用**。`Agent 微调 → GPT Review → Agent 微调 → GPT Review` 的循环**禁止**（§3.7.6 / §7 同口径）。

### 2.7 候选方向的取舍与用户选定（🔴 不再自动决策）

> 🔴 **2026-10-16 修订（本节变化最大）**：**本分支曾在这里做「生图前的自动决策：单方向胜出或融合」——该做法已废止。** 理由：方向决策必须建立在**真实候选图**上（§2.6.1）。现在这里只保留**取舍原则**，**决策权归用户**。

**方向决策的唯一合法路径**：

```
多个真实候选图（§2.2） → Gate 1：默认原生自检比较并推荐；授权后 `zcode_vision.py`（Copilot 仅点名）（§2.6.1） → 展示候选图 + 推荐 + 依据（§2.5）
   → 用户选定 / 确认方向（§3.3） → 收敛型最终提示词（§2.8）
```

- ❌ **禁止**：在真实候选图产生前用文字评审「自动选出」方向（§2.6 明确不决定方向）。
- ❌ **禁止**：以「Skill 默认流程」为由替用户作最终产品决策。
- ⚠️ **若产品已有明确授权允许自动选方向**（用户本轮明说「你定就行 / 不用问我」）：可以按授权执行，但**仍必须**保留 **GPT 推荐 + 依据 + 选择记录**（写进 `design-brief.md`，§2.8），并**不得**把它包装成「用户选择」。这类授权属 Fallback「唯一豁免」情形，须在 `direction-approved.md` 落档用户原话。
- 🟡 **用户不可达且未授权自主决定**（autonomous / 无人值守）：**不得批量实现全部页面，也不得创建/写入 `direction-approved.md`**。只允许做**可逆代表屏**——在 `design-brief.md` 的 Gate 1 记录与 `design-state.md` 标注 `状态：ASSUMPTION（待用户确认）` + 选择依据，只实现 **1 个代表屏 + 设计系统草案**；用户回来后可零成本确认或换向。**ASSUMPTION 不等于批准**。

**取舍时可以用的判断（供 GPT 推荐与用户选择参考，不是自动执行器）**：

**A · 某方向明显最优**（最常见）
条件：某一方向在**用途识别 / 核心语义 / 品牌一致性 / 小尺寸表现**上同时立住，且其他方向没有值得吸收的独特价值 → 推荐它。

**B · 融合多方向的优点**
条件：不同方向在**不同表达维度**上各自立住，且能被**提炼**进同一个核心概念。

> **示例（计步器图标）**：「足迹」负责表达走路用途；「起点刻度」负责表达记录与品牌；「极简几何」负责保证小尺寸表现 → 可以融合，形成更好的视觉概念。

**🔴 融合不是简单把多个图形拼在一起，而是提炼各方向最有价值的表达。** 出现融合意图时（由 GPT 推荐或由用户提出），必须过这五条检查：

| # | 检查 | 不通过的处理 |
|---|---|---|
| 1 | **是否仍有清晰的核心概念**（能一句话讲出来）？ | 讲不出 = 拼贴，**退回单一方向** |
| 2 | **是否增加了不必要的元素**？ | 删回必要集，或退回单一方向 |
| 3 | **是否破坏品牌一致性**？ | 退回单一方向 |
| 4 | **是否增加了小尺寸识别风险**？ | 简化，或退回单一方向 |
| 5 | **是否出现相互冲突的视觉语言**？ | 统一，或退回单一方向 |

**一条判据**：**融合结果不如单一方向 → 保留单一方向。** 不规定必须选几个方向，也不设置固定融合比例（可 A+B、A+C、A+B+C，也可以就是 A）。

> **融合的落点（与旧写法的关键区别）**：**融合不是在生图前把几条 prompt 拼起来**，而是在**用户已看到真实候选图**之后——用户可以说「要 A 的母题 + B 的克制感」，DesignWise 据此在 §2.8 的**收敛型最终提示词**里实现，必要时先定向重出一张融合候选图再让用户确认。**不得**未经用户选定就自行融合并直接进入正式概念图。

### 2.8 最终 Prompt 优化与决策记录

**七个动作**（按序；🔴 **本节只在用户选定方向之后执行**，§2.7）：

1. **读取输入**（全部为既有事实，不重新发明）：
   - 原始需求（`spec.md`）
   - 初始视觉提示词（§2.3）
   - 提示词专家评审结果（§2.6 的 Keep / Fix / Quick Wins）
   - **Gate 1 的 GPT 推荐与依据**（§2.6.1）
   - **用户最终选择**（选中的方向 / 或「A 的母题 + B 的气质」式组合）
   - 用户对方向的补充要求（如有）
2. **修正提示词评审与 Gate 1 指出的问题**（§2.6 / §2.6.1 的 Fix 逐条落地）
3. **删除重复、冲突、无效的描述**（prompt 内部自我打架、同义重复、无效禁令）
4. **补齐必要硬约束**（用途识别 / 品牌色 / 尺寸与安全区 / 小尺寸可辨——写进 **prompt 正文**，不是只写在 Brief 表里）
5. 🔴 **只围绕已选定方向收敛**——固化该方向的母题 / 骨架 / 形式语言 / 气质；**不引入新的视觉方向**，**不重新做一次方向选择**。若用户选的是组合（A 母题 + B 气质），把组合写成**一个**自洽的概念，并过 §2.7 的五条检查。
6. **保留 GPT 发挥创造力的空间**（可探索约束仍不锁死手法），但**收敛的目标是稳定与明确**：提高正式概念图的**稳定性、明确性与可产品化程度**（元素数量、色值、安全区、比例写清）。
7. **形成一个明确、可执行的收敛型最终提示词**（英文、可直接投喂；图标/符号类走 §2.3.1 槽位），用它生成**正式概念图**，随后过 §2.4 质量自检。

> 🔴 **探索提示词 ≠ 最终概念图提示词**（§2.3）：**不得**把候选方向那一条 prompt 原封不动当最终提示词——那等于跳过了收敛。**也不得**借「优化」之名夹带新方向试探。
>
> **如需再次提示词专家评审**：只检查**该提示词是否准确表达了用户已经选定的方向**（是否偏离、是否有歧义），**不是**重新选择视觉方向（§2.6 的定位不变）。评审一次即可，不做逐轮复查。

**决策记录（简洁，**追加到 `design-brief.md`**，不额外建文件）——分两节：**

```
## 创意决策记录（生图前 · 提示词层）

- 原始候选方向：A <一句话> / B <一句话> / C <一句话>（方案卡位置：…）
- 提示词专家评审关键发现：A 的 Keep…/Fix…；B 的 Keep…/Fix…；C 的 Keep…/Fix…
- 本轮人工参与：无（提示词生成为自主步骤）／有（<命中的用户介入情形，见 §2.9>）
- 按评审修正后的初始视觉提示词：<英文原文，逐条对应候选方向>
```

```

- 候选方向与真实候选图：A <路径> / B <路径>（/ C <路径>）（**用户明示单方向**时写「单方向 Review：<路径>」，并记录用户原话）

- 收敛型最终提示词：<英文原文>
```

> 🔴 **不要写进 `direction-approved.md`**：那是**真实视觉确认** Gate 的物化证据（§3.3）。**创意决策记录 / 生成记录 ≠ 用户对真实视觉的确认**——用户确认前就创建/写入它，会让后续的**工程实施 Gate** 与**长片渲染 hook** 把「尚未确认」误判为「已批准」。**用户确认前该文件不应存在。**
> **不额外建立复杂文件审批体系**：以上两节就是 `design-brief.md` 里追加的内容（§2.0），**不新增别的文件**。同文件内的 `## 生成记录`（模型 / 张数 / 用量）也在这里，同样**不写进 Gate 文件**。**可追溯性由这三节承载**：初始提示词 / 提示词评审 / 候选方向与真实图 / Gate 1 结果 / 用户选择 / 收敛提示词 / 正式概念图——**逐项可回溯，但不制造重复文件**。

### 2.9 用户介入的边界（提示词阶段自主，方向选择必须由用户做）

**初始视觉提示词的生成、提示词专家评审、按评审修正提示词——由 agent 自主完成，不设人工提示词审批关卡。** 🔴 **但"选定视觉方向"不是自主步骤**：它必须在**真实候选图 + Gate 1 推荐**之后由用户完成（§2.5 / §2.7）。

下列情形**必须停下来问用户**：

1. **原始需求存在关键歧义**，且该歧义会实质改变产品方向
2. 🔴 **方向选择**（看完真实候选图后选定 / 确认方向）——**这是本流程唯一固定属于用户的决策**（§2.7 / §3.3）
3. **提示词评审或 Gate 1 出现无法自行解决的重要产品取舍**（两个方向各代表一个真实用户群，选哪个是产品决策）
4. **涉及既有安全授权边界**（超出任务范围的批量生成、发布/推送等高风险动作）

**普通提示词改写、生图调用、技术性修正不需要逐次确认**——是否命中本通路由 §2.1 判定，费用口径见 §1.5，**不恢复逐次付费生图授权 Gate**。

> **例外一：用户本轮明确授权**「方向你定就行 / 不用问我」。此时可按 §2.7 执行自动选定，但**仍必须保留 Gate 1 推荐 + 依据 + 选择记录**（写进 `design-brief.md`），并在 `direction-approved.md` 落档用户原话。**不得**因为「Skill 默认流程」而把自动选定当成常态。
>
> **例外二：用户不可达且未授权**。此时**不得**替用户定方向、**不得**批量实现。按 §2.7 的 ASSUMPTION 分支只做 1 个可逆代表屏 + 设计系统草案，并在 `design-brief.md` / `design-state.md` 标注 `ASSUMPTION（待用户确认）`；`direction-approved.md` 保持不存在。

## 3. 第一次评审：基于真实候选图的专家评审 + 用户选定方向（Gate · 阶段 3）

> **第一次评审由两道构成**：① **专家机制对真实候选图做评审**（自主执行，判据是**实际图片**而非文字推测）；② 🔴 **用户从多个真实候选方向中选定 / 确认方向**（Gate，未确认前不进入下一阶段）。
>
> 🔴 **与旧流程的区别（2026-10-16 修订）**：旧流程是「方向已在生图前由专家自动定好（旧 §2.7），用户只对**已生成的单张最终图**做事后确认」。**现在不是**：**候选方向各有真实候选图**（§2.2）、**GPT 已在像素上比较并给出推荐**（§2.6.1）、**用户在这些真实候选里选定方向**（§2.7 / §3.3）——**选定之后**才生成收敛型最终提示词与正式概念图（§2.8）。

### 3.0 评审什么（基于真实候选图）

- 🔴 **全部真实候选方向图**（每个方向 1 张，`design-demos/direction-*.png`，§2.2 第 8 项）——**这是本阶段的评审主体**
- **每个候选的一句话方案定位**（来自方案卡：核心概念 / 预期优势 / 自报风险）
- 🔴 **GPT Review Gate 1 的推荐、依据与风险**（§2.6.1，已在此前执行）
- 🔴 **关键缺陷如实标注**：逐张标出「违反哪条硬约束 / 目标尺寸下哪里看不清 / 哪处只是工程精度问题」——**不得把"需要修复的候选图"当"已达工程可用状态"展示**（§2.4 展示纪律）
- **（若用户已选定方向）** 收敛型最终提示词与**正式概念图**（§2.8）——此时 §3.1 的评审对象转为正式概念图

> **两种进入方式**：① 常规——用户在候选图里选定方向（本节主体）；② 撤回/换向——用户在后续阶段指出原方向不成立，回到本节从候选里换（§3.2 / §3.7.3 情况 D）。**两种都以真实图为判据。**

### 3.1 专家评审重点（基于真实图，逐条对照）

**评审对象**：默认是**全部真实候选图**（每张逐条对照，供用户选定方向时参考）；**用户已选定方向后**，转为对**收敛型正式概念图**（§2.8）逐条对照。

| 维度 | 要问的 |
|---|---|
| 🔎 **用户用途识别** | 在真实使用尺寸下，目标用户能不能一眼看出这是干什么的（**核心判据，优先于任何量化指标**） |
| **实际视觉层级** | 真实图里的主次关系是否清楚，核心信息有没有被装饰抢走焦点 |
| **品牌一致性** | 是否延续既有品牌 / 设计体系（有品牌资产时对照 `brand-spec.md`） |
| **视觉细节** | 图形质量、边缘、配色是否落在 token、有无**未经要求**的光晕 / 渐变 / 阴影 / 文字 |
| **小尺寸表现** | **实际**缩到目标尺寸后是否仍能读出用途——**此时才做这个判断**（Prompt 阶段不作数，§2.6） |
| **创新与审美质量** | 是否避免了常见 cliché，是否有「意想不到但很合理」的表达（对照 `references/critique-guide.md`） |
| **工程可实现性** | 用现有工程手段做得出来吗（原生 UI / SVG / VectorDrawable / 素材） |

沿用 `references/critique-guide.md` 的 **Keep / Fix / Quick Wins** 输出，**问题必须具体可操作**（现状 / 为什么是问题 / 改成什么）。

### 3.1.1 🔴 GPT Review Gate 1 的执行位置与结论处置（默认原生自检；授权后 `scripts/zcode_vision.py --confirm-gpt-review`；Copilot 仅用户点名）

🔴 **Gate 1 的位置固定在 §2.6.1：多个真实候选图生成之后、用户选定方向之前。** 本节的职责只有两件——**把它与设计侧自主评审的关系说清**、**把它的结论接进本阶段的动作**。

- **不在此处补做、也不推迟**：候选图一生成完（§2.2.1）即执行 Gate 1（§2.6.1），默认由原生自检承担；**用户授权后**才由 `scripts/zcode_vision.py --confirm-gpt-review` 承担（用户点名 Copilot 时才改走其正式 REVIEW），**不得**等到用户看完图、或到阶段 5 才想起来做。**它必须先于用户的方向选择**——否则用户的选择没有 GPT 推荐可比对。
- **与 §3.1 的分工**：Gate 1 判**哪个方向最符合需求 / 最值得继续 / 有无线索误读 / 哪些是方向级问题**（§2.6.1 八问）；§3.1 的七维度 + Keep / Fix / Quick Wins 由 DesignWise 自主执行。两者**并行、互不替代**：前者服务「选哪个方向」，后者服务「这个方向本身做得怎么样」。
- **结论处置**：
  - GPT **推荐某方向** → 连同**依据与风险**一起在展示里呈现给用户（§2.5 / §3.3），**由用户选定**；DesignWise **不代为选定**。
  - GPT 指出**某方向级问题**（用途误读 / 概念不成立）→ 如实标注在该候选图上（§2.4 展示纪律），**仍交用户知情选择**。
  - 仅剩**可选优化** → 不阻断选定，随 §2.8 收敛一并处理。
  - **证据不足 / 未获得裁决** → 如实告知「本轮缺 GPT 推荐」，交候选图让用户直接选（缺证 ≠ 通过）。
- **留痕**：结论进 `design-brief.md` 的 `## 创意决策记录（生图后 · Gate 1）`（§2.8）；**不进 `direction-approved.md`**（那是用户确认真实视觉之后的 Gate）。
- 🔴 **方向选定后不重跑**：同一批候选**不再重送**；仅当出现新的视觉决策问题才重新送审（§2.6.1 停止条件 / §3.7.6）。

### 3.2 缺陷归因与最低成本修复（发现图片有问题时）

**先区分三类根因，再选成本最低、效果最好的修复方式**：

| 根因 | 典型表现 | 修复方式 |
|---|---|---|
| **Prompt 设计问题** | 用途读不出 / 概念跑偏 / 硬约束没写进 prompt 正文 | **改 prompt 后定向重出这一张**（§3.7.3 情况 A） |
| **GPT 执行偏差** | prompt 写对了但图没照做（数量不对、色偏、多出元素） | **图生图定向编辑**（`--ref`）或改 prompt 重出；**不为精确几何反复生图** |
| **工程几何问题** | 概念成立，只是刻度条数 / 精确比例 / 像素对齐 | **在矢量工程阶段实现**（SVG / VectorDrawable），**不在生图上反复重出**（§2.4 缺陷分级） |

🔴 **不重启完整的多方向探索**——除非评审结论是**当前方向确实不成立**（此时按 §3.7.3 情况 D：**从已有真实候选里换一个**（候选记录见 §2.8 的「生图后 · Gate 1」一节），或再做一次概念探索）。**允许**：修改 prompt、编辑已有图片、必要的定向重生成。

### 3.3 用户可做的动作

🔴 **用户在看完「多个真实候选方向图 + Gate 1 推荐」之后选定方向**（这是本流程的方向决策点，§2.7 / §2.9）：

| 动作 | 处理 |
|---|---|
| **选定某个候选方向** | 该方向成为设计基准 → **进入 §2.8 生成收敛型最终提示词 → 正式概念图**；用户原话写入 `direction-approved.md` 的**用户确认**一节（正式概念图确认后，见下） |
| **要求组合 / 融合若干候选的优点** | 记为用户选择（如「A 的母题 + B 的气质」）→ 在 §2.8 收敛时实现；过 §2.7 五条检查；必要时先定向重出一张融合候选图再确认 |
| **指出某候选方向级问题**（用途误读 / 概念不成立） | 按 §3.2 归因选最小动作：改 prompt 定向重出该方向，或直接从候选里排除它，**不重启完整探索** |
| **要求调整已选定方向** | 按 §3.2 归因选最小动作，**只针对该方向**（同方向微调不重跑多方向探索，命中 Fallback「唯一豁免」第 2 条） |
| **都不满意** | 说明具体不满足的点 → 按 §3.7.3 情况 D 处理（换已有候选，或再做一次概念探索） |

**🔴 在用户选定方向前，不进入正式 UI 实现。**

**🔴 `direction-approved.md` 的写入时机不变**：该文件 = **用户对真实视觉的确认**物证——内容 = **（选定的）概念图路径 + 用户确认原话**（协议见 SKILL.md「Gate文件协议」）。
- **写入时机**：用户在**正式概念图**上确认（或明确以候选图确认并接受后续收敛）之后。🔴 **仅「选定候选方向」这一步本身、方向尚未在正式概念图上确认时，不要写入该文件**——收敛后的正式概念图才算该方向落地。
- **创意决策记录不在这里**（在 `design-brief.md`，§2.0/§2.8 两节）。**「用户说继续」授权的是进入下一步，不是跳过这道门**；跳过必须用户明说，并记进 gate 文件。
- 🔴 **用户确认前该文件不存在属正常状态**；**旧任务的 `direction-approved.md` 不构成新任务的授权**（新方向必须重新确认并更新该文件）。

### 3.4 选定后只针对该方向继续（效率硬规则）

一旦用户选定方向：**只针对该方向继续设计**。
- ❌ **不要再为未采用的方向**制作 HTML、工程资源或完整实现——**也不为其生成额外图片**（§2.7）。
- ✅ 未采用的候选图与方案卡留在 `design-demos/` 作为「探索态」存档即可，**不进交付物**（§3.5.3）。
- ✅ 收敛型最终提示词与正式概念图（§2.8）**只做选定方向这一套**。

## 3.5 概念图 → 视觉规范转译（阶段 3.5 · 🔴 把"看中的图"变成"做得到的设计"）

> **这一步是全流程最容易断链的地方**：用户选了一张 GPT 概念图，然后 HTML/CSS 实现出来却是另一个东西——因为没人把"概念图里到底是哪个视觉决策打动了用户"翻译成可实现的规范。本节就是那道翻译。

**产物（每个选定方向一份）**：`visual-translation.md`（路径与 `direction-approved.md` 同级）。它把概念图拆成**三类**处置，逐条留痕，可追溯、可审计。

### 3.5.1 可提取（→ 进视觉规范）

从概念图里**只提取视觉语言**，不提取内容。逐项对照下表填 `visual-translation.md`：每条写 **【概念图里的表现】→【为什么值得吸收】→【HTML/CSS 怎么落实】**。

| 可提取维度 | 具体看什么 | HTML/CSS 落实方式 |
|---|---|---|
| **色彩关系** | 不是抄色值，而是**关系**：几个色？主/次/强调如何分工？对比强度？ | `:root` token 表；写清 each token 的**职责**（`--ink` 主文字 / `--accent` 唯一强调） |
| **材质与光影** | 扁平 or 有层次？阴影/描边/渐变的**克制程度**与**用在哪** | `box-shadow` / `border` / `linear-gradient`；注明「只用在 X 组件」 |
| **图标与奖章语言** | 图形是线性/面性/双描边？圆角半径感？图形隐喻 | 原生 SVG（**不照抄像素**，重画为统一图标语言）；见 §4.1 |
| **插画风格** | 手绘/几何/摄影感？线条/质感/留白 | 简单图形用 CSS/SVG；**复杂插画才走 §4 正式素材**（GPT 生成） |
| **情绪氛围** | 温度（冷静/温柔/庄重）、节奏（疏/密）、留白率 | 由字重、间距、圆角、留白共同决定；写成一句可检验的"气质条款" |
| **可实现的视觉表现** | 哪些一眼能做、成本低、维护友好 | 直接列 CSS 规则或组件改法 |

### 3.5.2 不得照搬（🔴 硬否决，逐条记入"否决清单"）

| 不得照搬 | 为什么 | 正确做法 |
|---|---|---|
| **虚构数据** | GPT 图里的次要数字/日期**几乎全是编的**（计步器实测：436 主数字对，但距离 0.34→0.32、消耗 17→18、时长 00:04→6分、日期全错） | 一律以 spec 真实数据为准；**把幻觉数据当事实 = 伪造数据，违反产品规范** |
| **错误中文** | 字形/用词/标点常错、可能多字缺字 | 文案以 spec 原文为准；GPT 图里的中文只作**版式参考**，不作文案来源 |
| **假交互** | 按钮是画上去的，不可点、无状态 | 交互以产品规范定义的状态机为准；原型必须真可交互 |
| **不符合产品规范的布局** | GPT 会"顺手"增删 tab、改信息层级、发明不存在的模块 | 结构边界（tab 数/页面数/必含模块）**以 spec 为准**，GPT 只是配色与气质参考 |
| **不可实现 / 高维护成本的效果** | 复杂光影、粒子、依赖位图的精细质感，用 CSS 硬做=脆且丑 | 能原生做的才做；做不到的**如实降级并标注**，或转正式素材 |

### 3.5.3 概念图 / 验证素材 / 正式素材 的边界（防止"把探索态当成品"）

| | 概念参考图（§2） | 验证素材（§3.6.3） | 正式设计素材（§4） |
|---|---|---|---|
| **用途** | 探索方向、给用户选 | 在 HTML 里还原概念图，供判断视觉体验 | 直接进产品，被工程引用 |
| **含 UI 吗** | 可以（它就是界面探索） | 否（UI 由 HTML 真实实现，素材只是其中图片部分） | **不可以**（禁整张 UI、假按钮） |
| **可否交付** | ❌ 永不作为界面交付 | ❌ 不进交付包（可由 §5.1 转为正式素材） | ✅ 可作为素材交付 |
| **数据** | 全部不可信 | 由 spec 提供，素材本身不含业务数据 | 由设计提供规范，素材本身不含业务数据 |
| **落盘** | `design-demos/`（可丢弃） | `prototype/assets/img/`（验证态，附 `img-prompts/`） | `assets/images/`（需留存，附 `img-prompts/`） |

> 三态的完整职责对照与流转见 §3.6.4。

## 3.6 按需制作一套可交互 HTML 原型（阶段 4 · 只做选定方向的一套）

> **HTML 的职责是验证设计和交互，不是重新进行视觉方向探索。** 它是可选的验证手段，不是每个任务都要做。

### 3.6.1 什么时候做 / 什么时候跳过

| **建议制作 HTML** | **通常跳过 HTML** |
|---|---|
| App 首页整体改版 | **App Launcher 图标** |
| 多页面设计 | **简单静态启动页** |
| 交互流程较复杂 | **静态插画** |
| 页面具有多种数据状态 | **单张品牌图片** |
| 需要检查导航、滚动、布局和操作反馈 | **简单局部视觉调整** |
| 静态概念图不足以判断真实体验 | **已明确、无需额外交互验证的设计** |

**判据一句话**：**需要验证交互与多状态体验时才做**。拿不准且任务价值高（多页面/复杂流程）→ 按「建议做」处理；静态单图类 → 按「跳过」处理，直接进阶段 5 轻量评审。

### 3.6.2 HTML 原型要求

1. 🔴 **只制作已经选定方向的一套 HTML，不同时开发多套候选方案**（这是本次升级的效率硬规则）。
2. **必须尽可能还原用户确认的 GPT 视觉概念**（依据 §3.5 转译出的 token 与组件规则）——**目标是还原「视觉」而非只还原「结构」**；只还原布局骨架而丢掉配色气质、材质光影、母题，等于没还原。**视觉价值依赖图片素材时按 §3.6.3 规则生成验证素材**，不用占位图替代。
3. 实现**验证体验所必需**的交互、状态和页面切换。
4. **允许使用模拟数据**（但不得与 spec 真实值冲突——凡是 spec 给了真实值的字段用真实值）。
5. ❌ **不要求接入真实业务、数据库、广告或传感器**。
6. ❌ **不将 HTML 原型做成完整产品**（不做用户没要求的页面/功能，见 `product-value.md` 范围冻结）。
7. **优先使用简单、快速、易修改的实现方式**（原型是为迭代服务的，写死难改就失去意义）。
8. **原型应方便用户直接查看、操作和反馈**（能双击打开、能点、能给具体反馈）。

实现细节仍走原有链路：`references/app-prototype.md`（App/iOS）、`references/react-setup.md`（技术红线）、技术红线中的 deck 架构（如涉及幻灯片）。

### 3.6.3 🔴 图片素材规则（阶段 4 · 视觉验证不能靠占位）

> **这一条在 GPT 视觉概念通路内，优先于通用「诚实 placeholder」原则**（SKILL.md 核心哲学 #4）。原因：阶段 4 的 HTML 是**用户用来判断视觉体验的实物**，用占位图替代会把「视觉评审」变成「结构评审」——评审结论因此失真，返工代价远大于几张图的成本。

**规则的判据不是「有没有图」，而是「视觉价值是否依赖图片表达」**：

| 情形 | 动作 |
|---|---|
| **HTML 的视觉价值依赖图片素材**（插画 / 人物 / 品牌主视觉 / 复杂背景 / 装饰元素 / 产品展示图 / 图标视觉稿…） | 🔴 **必须调用 GPT 图片生成能力制作对应验证素材**——不得用临时占位图、随机图库或人工简单替代（CSS 色块 / 灰块 / 手画 SVG） |
| **视觉价值不依赖图片**（纯布局验证 / 数据列表 / 表单 / 简单几何图形 / 已有正式资源） | **可以不生图**（见下表「可以不生图」清单） |

**可以不生图的情况（边界，避免过度生成）**：

- 纯布局 / 结构 / 信息层级验证
- 数据列表、表格、表单
- 简单几何图形、纯 CSS 可实现的效果
- **已有正式资源**（项目既有素材、§1.a 取到的真实资产）

**不适用生图的对象（照旧走真实资产，不因本条改变）**：

- **真实产品图 / 品牌 Logo / 官方 UI 截图** → 仍走 §1.a 资产协议**取真图**（§4.1）。GPT 生成的真实品牌资产一眼假、失真品牌识别——**本条不豁免这条红线**。
- **「品牌主视觉」的正确理解**：可生成的是**品牌气质的视觉诠释**（氛围图 / 抽象主视觉 / 场景插画），**不是**可识别的官方 logo 或产品外观。

**验证素材的落地与登记**（复用既有机制，不新建资产系统）：

```
prototype/
├── <页面>.html
└── assets/
    ├── img/            # 阶段 4 验证素材（GPT 生成，HTML 直接引用）
    └── img-prompts/    # 一图一档，格式同 §4.4
```

- 生成规则同 §2.3 / §4.3：**英文 prompt 由 agent 自动生成**（六槽位），中文文案引号原样嵌入并注明 `render this Chinese text exactly`；**必写禁令**照带
- 提示词原文落 `prototype/assets/img-prompts/<名>.md`（一图一档，可复现、可迭代）
- **尺寸诉求写进 prompt**，落盘后以**实际文件**为准（CPA 不保证按请求尺寸返回，见 §2.3）
- 🔴 **生图按任务需要正常进行**（§1.5）：视觉价值依赖图片时，**按需要生成对应验证素材，不需要逐次付费审批**；但**按实际需要决定数量，避免无效重复调用**，已有可用素材优先复用。

**生图不可用时的正确动作（不静默降级为占位）**：

1. **明确报告**：说清「这一版 HTML 因缺少验证素材，视觉评审不完整」
2. **把完整英文 prompt 交付用户**，可在 ChatGPT 出图后交回，继续阶段 4/5
3. **不得**用占位图 / 随机图库 / 简单替代**冒充**已还原概念图，也不得让用户以为那是最终视觉

> **与其他素材阶段的关系**：本阶段的产物是**验证素材**（第三类，区别于阶段 2 概念图与阶段 6 正式素材）。三者的职责与流转见 §3.6.4。

### 3.6.4 🔴 素材三态与职责（阶段 2 / 阶段 4 / 阶段 6）

**同一个视觉元素，在三个阶段的职责完全不同**，不要混用，也不要跳态：

| | **阶段 2 · 概念素材** | **阶段 4 · 验证素材** | **阶段 6 · 正式素材** |
|---|---|---|---|
| **目的** | **探索视觉方向**——确认风格、构图、色彩、情绪 | **验证真实视觉体验**——在可交互 HTML 里还原概念图效果 | **进产品被工程引用** |
| **形态** | 2~3 张整屏概念效果图 | 单个可集成素材（插画 / 背景 / 主视觉 / 装饰） | 单个正式素材 |
| **含 UI 吗** | 可以（它就是界面探索） | 否（UI 由 HTML 真实实现，素材只是其中图片部分） | 否（禁整张 UI、假按钮） |
| **落盘** | `design-demos/`（可弃） | `prototype/assets/img/`（验证态） | `assets/images/`（留存，附 `img-prompts/`） |
| **质量要求** | 看方向即可 | 与概念图**视觉一致**，够验证体验 | 过 §4.6 交付规格 |

**流转**：阶段 2 出候选方向 → **Gate 1 推荐 + 用户选定方向**（或按 §2.7 的授权 / ASSUMPTION 分支）→ 收敛型提示词 → 生成最终概念图 → 阶段 4 用验证素材把**确认的方向**在 HTML 里还原出来 → 阶段 5 评审确认 → 阶段 6 处置验证素材（§5.1 三选项 A/B/C）。**禁止专家评审自动定方向。**

> **阶段 4 不等于"做简化线框稿"**：如果 HTML 只还原了结构、没还原概念图的视觉，那它没有完成阶段 4 的职责——**该生成的素材要生成**（§3.6.3 边界内的除外）。

> **跳过 HTML 时**：不补一套「简化 HTML」假动作，直接进阶段 5 的**轻量评审**（§3.7）。

## 3.7 第二次评审：确认设计与定向迭代（阶段 5）

> **第一次评审（§3）决定视觉方向；第二次评审决定已选方案是否满足实际体验要求、是否需要进一步调整。** 两者是不同的问题，不要合并。

### 3.7.1 做了 HTML 时的评审重点

🔴 **第一问（本阶段最关键）：HTML 是否真实还原了 GPT 概念图的视觉，而不是仅还原了结构？**

把已确认概念图与 HTML 渲染截图**并排看**，逐项对照（不要求像素级一致，但**视觉意图必须在**）：

| 检查 | 判据 | 不合格信号 |
|---|---|---|
| **图片素材是否缺失** | 概念图里由图片承载的视觉部分（插画 / 人物 / 主视觉 / 背景 / 装饰 / 产品展示图），在 HTML 里**有对应素材** | 该有图的位置是空白 / 灰块 / 色块 / 氛围缺失 |
| **是否因占位素材导致错误判断** | 当前 HTML 的视觉结论**没有被占位物污染**——用户看到的就是设计意图的近似 | 评审时说不清「这是设计如此，还是图还没做」；结论建立在占位物上 |
| **是否需要重新生成素材** | 素材与概念图的**风格 / 色彩 / 情绪一致**（对照 `visual-translation.md` 的 token 与气质条款） | 素材风格跑偏、与概念图不是同一个视觉语言，或干脆缺图 |

**判定**：三者任一不合格 → 按 §3.7.3 迭代（通常命中**情况 A**：重新生成视觉素材 / 概念图，并更新 HTML），**不得在缺失素材的状态下判定「视觉通过」**。
> 边界照 §3.6.3：**视觉价值不依赖图片**的 HTML（纯布局 / 列表 / 表单 / 几何 / 已有正式资源）不做这项生图要求，如实标 N/A 即可。

其余评审重点：

- **实际体验交互与导航**：能不能点、流程通不通、返回是否符合预期
- **信息层级与布局**：核心行为是否在首屏第一眼被服务
- **必要的数据状态**：空 / 加载 / 错误 / 数据不足四态是否都有（不许留空）
- **「有用、好懂、舒服、有意义」** 四层是否成立
- **是否存在需要调整的设计问题**（说得出具体位置与改法）

### 3.7.2 跳过 HTML 时的评审（轻量）

基于**已选概念图 + 实际使用场景 + 工程约束**做简洁评审：
- 检查是否仍存在**明显设计缺口**（结构边界、信息层级、工程可实现性）
- **无实质问题即可确认，不增加重复流程**——不为「走完流程」硬造评审步骤

### 3.7.3 迭代机制（按具体问题选**最小必要动作**）

| 情况 | 触发 | 最小必要动作 |
|---|---|---|
| **A · 视觉概念需要改进** | 已选方向没问题，但视觉表现不满意 | **允许重新调用 GPT 生图**（属原任务范围内的正常调用，**不触发额外付费审批**），针对已选方向生成调整后的概念图；**若已有 HTML，则据新概念图更新必要部分**。⚠️ 若只是**精确几何 / 数量**问题（如刻度条数），优先改矢量实现，**不无意义地反复生图**（§2.4 缺陷分级） |
| **B · 布局 / 交互 / 信息结构需要调整** | 视觉 OK，是体验层面的问题 | **优先直接修改现有 HTML**；**不必重新 GPT 生图** |
| **C · 视觉与交互都需要调整** | 两者都有问题 | **允许重新 GPT 生图**，并修改或重做对应 HTML；仍**只针对当前选定方向** |
| **D · 整个视觉方向不成立** | 不是微调能解决的 | **从已评审的候选里换一个**（候选的评审依据见 §2.8 决策记录）；候选都不合适 → 再进行**新一轮概念探索**（重跑 §2.2~§2.8，不是"再选一次"）。⚠️ **不重启完整三方向探索 = 不无理由重出图片**（§3.2） |
| **E · 设计已满足要求** | 关键设计要求达标 | **直接通过评审**，进入产品化落地（阶段 6） |

### 3.7.4 迭代原则（防过度设计 / 防形式流程）

- **每轮调整都要有具体原因**（说得出改哪一处、为什么、改成什么）
- **不要求每次都重新生图**，也**不要求每次都重做 HTML**——按 A-E 选最小动作
- 🔴 **不同时制作多个 HTML 方案**（任何情况都只维护选定方向的一套）
- **不机械限制迭代次数，也不无限优化**——用户满意且关键设计要求达标后**立即停止探索**
- **用户反馈优先**；必要时由 DesignWise 指出明显的功能、可用性、工程风险（如「这个效果 CSS 做不稳」「这个交互会误导用户」）
- **调整完成后再次评审**，直到设计达到合理完成标准，或出现**需要用户决策的阻塞**（此时停下报告，不自行拍板）

### 3.7.5 第二次评审的物化留痕

第二次评审是阶段 5 的检查点，**物化为 `direction-approved.md` 里的 `## 第二次评审记录` 一节**（Gate 文件协议，见 SKILL.md）——记录：

- 评审轮次与依据（概念图路径 / HTML 路径 / 转译表的落实情况）
- 命中的情况（A/B/C/D/E 哪一类）与具体问题
- 采取了什么最小动作、结果如何
- 最终结论（通过 / 需用户决策的阻塞）

**该节存在且结论为「通过」= 阶段 5 完成，可进阶段 6**。跳过 HTML 的任务同样写这一节（轻量评审，五类问题里通常直接命中 E，如实写「无实质问题，直接确认」即可）。

记录里**另加一行 Gate 2**：`GPT Review Gate 2（默认原生自检；授权后 zcode_vision.py，§3.7.6；用户点名 Copilot 时注明 Copilot 正式 REVIEW）：<已执行（证据条目 ID / 裁决 / 关键发现 / 采用的定向修改）｜未执行（原因）>`。

### 3.7.6 🔴 GPT Review Gate 2 · 阶段门槛评审（默认原生自检；授权后 `scripts/zcode_vision.py --confirm-gpt-review`；Copilot 仅用户点名）

> **审的是「阶段门槛」，不是继续找所有可能的审美优化**：方向是否**仍然成立** / 实际呈现是否**偏离选定方向** / 关键视觉语义是否仍清晰 / 小尺寸是否存在**真实**问题 / 是否出现**新的视觉歧义** / 是否已达到进入下一阶段或收口的标准。

**触发时机**（任一即应执行，不是每轮修改都执行）：① 一套 HTML 原型完成后（与 §3.7.1 的第二次评审同时进行）；② 产品化 / 矢量精修完成后；③ **任务本身不需要 HTML**（§3.6.1 判定跳过）时，直接在产品化产物上执行。

**调用与证据**：默认由原生自检直接读图；**用户授权后**才调用 `scripts/zcode_vision.py --confirm-gpt-review`（直连 CPA 的 `input_image`，只收磁盘真实图片；Copilot 正式 REVIEW 仅用户点名时走 `bridge_evidence.py --image` → `call_gpt.py --mode REVIEW`）；证据 = **真实渲染截图 / 产品化产物的真实图片** + **已确认概念图（作对照）** + 客观测量（几何 / 遮罩裁剪 / 对比度等，**注明是测量而非视觉判断**）。

- **小尺寸结论必须建立在真实小尺寸像素上**——按 §2.4 与 `critique-guide.md`「视觉还原检查」的口径准备证据（原生像素或**整数倍最近邻**放大，标注原始尺寸、是否放大、倍数与方式）；**不得把非整数缩放 / 二次压缩的图当真实尺寸证据**。
- **缺素材不得送审当真**：若 HTML 的视觉结论被占位物污染（§3.7.1 第一问不合格），先按情况 A 补齐验证素材再送 Gate 2——**缺证时的视觉裁决无效**。
- **不做逐像素比对**：判据仍是「用户能否识别与理解」「是否偏离已确认的设计意图」，**不要求像素级一致**（§6.1 同口径）。

**输出怎么用**：

| GPT 结论 | 动作 |
|---|---|
| 方向仍成立、无影响决策的问题、剩余属可客观验证的细节 | **阶段门槛通过** → 进产品化 / 收口（对应 §3.7.3 情况 E） |
| 可进入下一阶段但仍有**可选优化** | **默认通过**——不因「还可以再优化」继续送审 |
| 存在**影响核心目标**的问题 | 按 §3.7.3 选**最小必要动作**（改 HTML / 重出视觉素材 / 矢量实现），改完**只复验受影响项** |
| 方向已不成立 | 按 §3.7.3 情况 D 处理（从已有依据的候选换向 或 再做一次概念探索） |
| 证据不足（`PARTIAL（缺证）`）或 `scripts/zcode_vision.py` 非 0 退出（用户点名时为 copilot 非 0 退出） | **如实报告缺证 / 未获得有效视觉裁决**，补取最小必要证据后复验；不伪造、不静默换链路冒充（不得自动改用 Copilot） |

**🔴 停止条件与禁止循环**：Gate 2 通过、或只剩可客观验证的细节 → **停止调用 GPT**。禁止 `Agent 微调 → GPT Review → Agent 微调 → GPT Review` 的循环（§3.7.4 同理）。仅当出现新的视觉决策问题（实质视觉变化 / 进入新阶段 / 新视觉问题 / 争议 / 客观验证解决不了 / 需重选方向）才重新送审——**1~2% 的像素级几何调整、间距 / 圆角 / 单节点位置微调、已由客观测量确认解决的问题，不得自动重新送审**。

**留痕**：结论写入 `direction-approved.md` 的 `## 第二次评审记录`（§3.7.5）——与 DesignWise 自主评审结论并列，**标明哪条来自原生自检（默认）/ `scripts/zcode_vision.py`（授权后）或用户点名时的 Copilot 正式 REVIEW**。

## 4. 正式产品图片素材（阶段 6 的一部分）

**这是独立能力，与概念效果图、验证素材分开管理。**

> 🔴 **三个阶段是三种不同职责，不要混淆**（完整对照见 §3.6.4）：
> - **阶段 2（§2）**：GPT 负责**探索视觉方向**——概念图是给用户选方向的，可丢弃（`design-demos/`）。
> - **阶段 4（§3.6.3）**：GPT 负责**制作验证素材**——在 HTML 里还原概念图效果，供用户判断真实视觉体验（`prototype/assets/img/`）。
> - **阶段 6（本节）**：GPT **按需负责制作正式产品图片素材**——插画 / 品牌图形 / 背景 / 场景 / 视觉装饰，直接进产品被工程引用（`assets/images/`）。
>
> **按需的第二层含义**：如果**简单矢量图或代码实现更可靠**（图标 / 几何 / 文字 / 布局），**不必重复调用 GPT 生图**（§4.1 分流）。**不强制每个任务都在阶段 6 生图**；阶段 4 的验证素材也可选用矢量/代码替代（§5.1 选项 C）。
>
> **红线**：❌ 不得直接把未经适配的概念图当作可发布素材交付（§3.5.3 / §4.2）。

### 4.1 用途分流（谁是图，谁不是图）

| 设计需要的元素 | 用什么 | 理由 |
|---|---|---|
| **原创插画 / 背景 / 场景图 / 氛围图** | ✅ **可用 GPT 生成** | 这类没有「真图」可言，GPT 生成即最优载体 |
| **真实产品图片 / 品牌 Logo** | ❌ 优先官方或用户提供的**真实素材**（§1.a 资产协议） | 生成的产品图/logo 一眼假，且失真品牌识别 |
| **图标 / 图表 / 按钮 / 文字** | ❌ 优先真实 UI 组件 / SVG / CSS | GPT 画 UI 文字必糊、按钮不可交互 |

### 4.2 概念图 ≠ 正式界面（红线）

**不能把整张 GPT App 效果图直接当成正式 App 界面交付。** 效果图是视觉意图的表达，不是可运行的界面——它没有真实布局、按钮不可点、内容不可动态更新。

### 4.3 正式素材 prompt 要点

- **语言与原规则同**：同 §2.3——prompt **用英文自动生成**，中文文案以引号原样嵌入并注明 `render this Chinese text exactly`
- **禁止包含整张 UI、虚假按钮、界面文字**（除必要的品牌名/必要标签，且需核实准确）
- **单一元素 / 可独立集成**：一张图一个用途（一个背景 / 一张插画），不要塞多个元素
- **留出集成余量**：居中或留白构图，便于裁切与叠加
- **需要透明背景或精确元素时**：走图生图（`--ref` 参考图编辑）或在 HTML 中做叠加，别指望一次成图

### 4.4 素材落地：目录与 metadata（复用现有机制，不建资产管理系统）

沿用项目目录约定，只加一处专用子目录：

```
项目名/
├── spec.md                    # 需求与真实数据（原有，事实来源）
├── design-brief.md            # Visual Brief（§2.0）+ `## 创意决策记录（生图前）`（§2.8）+ `## 生成记录`（§1.5）
├── design-demos/              # 概念效果图（探索态，可丢弃）
│   ├── direction-a-<逻辑名>.png
│   ├── direction-b-<逻辑名>.png
│   └── direction-c-<逻辑名>.png
├── prototype/                 # 阶段 4 的 HTML 原型（仅选定方向，按需；验证体验用）
│   └── <页面>.html
├── assets/
│   ├── images/                # 正式素材（集成进交付物，需留存）
│   │   ├── bg-<用途>.png
│   │   └── illustration-<用途>.png
│   └── img-prompts/           # 生成素材的 prompt 与来源（一图一档）
│       └── bg-<用途>.md
├── brand-spec.md              # 涉及品牌时（原有）
├── direction-approved.md      # 🔴 真实视觉确认 Gate：只在**用户确认真实概念图之后**创建（概念图路径 + 用户确认原话 + `## 第二次评审记录`）；生图前不存在属正常
├── visual-translation.md      # 概念图→视觉规范转译（§3.5，GPT 概念生图通路必备）
└── handoff/                   # 设计交付包（§5 / design-handoff.md，交 Web/Android/PPT 时必备）
    ├── README.md · structure.md · design-tokens.md · states-interactions.md
    ├── copy-data.md · assets.md · adaptation-a11y.md
    └── baselines/*.png
```

**`assets/img-prompts/<名>.md` 至少记录**：生成用的**提示词原文**、**实际使用的图片文件名**、**原始图（若做过裁切/后处理）**、**素材用途**、**来源与模型**。**保存提示词是为了可复现与可迭代，不是为了写文档。**

> **原始图 vs 实际使用图**：脚本若做了像素适配/裁切，两版都留（原图存档，使用版进 `assets/images/`），避免「想改一点却发现只有裁切版」。

### 4.5 优先真实素材

- 真实产品图、品牌 Logo、官方 UI 截图 → **先走 §1.a 资产协议取真图**，取不到才用 GPT 生成并**明确标注是生成物**
- 真实素材与生成素材**分开存放**，在 `brand-spec.md` / `img-prompts/` 里注明来源，避免交付时混用

### 4.6 正式素材交付规格（🔴 进入产品前必须逐项落实）

概念图随便看看即可；**正式素材要被工程直接引用**，所以每张都过这张清单（写进 `img-prompts/<名>.md` 或素材清单）：

| 项 | 要求 |
|---|---|
| **用途与目标尺寸** | 用在哪（哪页/哪组件/哪种状态），目标像素与显示区域尺寸；**尺寸诉求写进 prompt**，落盘后**实测**并以实测值记录 |
| **文件格式** | PNG / WebP / JPG；**是否需要透明背景**；若需透明 → 图生图或 `chroma_key.py` 处理，不指望一次成图 |
| **Prompt / 模型 / 来源** | 提示词原文、实际模型名（来自 §1 检测，非硬编码）、生成时间、原始图（若裁过） |
| **验证项** | 尺寸、清晰度（非糊/非伪影）、裁切效果（主体不被切）、无 letterbox 黑边、色彩数非纯色 |
| **引用关系** | 素材对应哪个页面/组件；工程侧引用路径（如 `assets/images/bg-<用途>.png` → 组件 `HomeBanner`） |
| **可引用性** | 落进产品可访问的目录；Android 侧给 `res/drawable-*` 规格建议，Web 侧给相对路径——**工程拿来就能用** |

> **不是每种视觉元素都需要 GPT 生图**：简单图标 / 文字 / 布局 / 几何图形**优先原生 UI / SVG / CSS**（§4.1）。只在生图有明显价值时（原创插画、氛围背景、复杂质感）才用 GPT。**为"流程完整"而生的图 = 无价值生成步骤**，不做。

> **明确区分两类产物**（呼应 §3.5.3）：概念参考图落 `design-demos/`（探索态，可丢）；正式素材落 `assets/images/` + `img-prompts/`（集成态，留存并进交付包）。**交付包里出现的是后者，不是前者。**

## 4.7 开发阶段按需生成（Dev-time On-demand · 🔴 本节重点）

> **场景**：设计已交付（`handoff/` 已给实现端），**开发过程中**发现缺一个视觉素材——比如某个空状态要一张插画、某页要一张氛围背景、某组件要一个原创图形。这时由**实现端/开发 agent**发起素材需求，DesignWise 规范提供判断与生成规则。
>
> **与 §4 的区别**：§4 是**设计阶段**按已定方向预生成正式素材；本节是**开发阶段**的**按需补料**。两者共用同一套 prompt 规则（§4.3）与规格（§4.6），成本口径同 §1.5 / §4.7.3。

### 4.7.1 十步规程（缺素材时按序走）

| # | 步骤 | 动作 / 判据 |
|---|---|---|
| 1 | **识别需求** | 说清：哪一页/哪一组件、哪种状态、**为什么现有手段不够**（不是"想要图"）。产出一行素材需求：「用途 + 目标尺寸 + 为何必须位图」 |
| 2 | **先查复用** | 按顺序找：① 已交付的 `assets/images/`；② 项目已有的图/图标；③ `handoff/assets.md` 里已列的素材。**找到合格的就停，不生成**（🔴 不重复生成已有合格素材） |
| 3 | **判能否原生** | 简单图标 / 几何 / 图形 / 文字 / 布局 → **SVG / CSS / 原生组件**（§4.1）。只在"原创插画 / 氛围背景 / 复杂质感"这类**位图才有价值**时才继续往下 |
| 4 | **读设计上下文** | 读 `design-brief.md`（Visual Brief）+ `handoff/design-tokens.md`（Token）+ `visual-translation.md`（已选方向 + 视觉语言）+ `handoff/assets.md`。**素材必须继承已选定的视觉风格**——这一条保证"不因进入开发阶段而丢失已选方向" |
| 5 | **自动生成 prompt** | 用 §4.3 规则（英文、六槽位、必写禁令）自动产出。**不要求用户写 prompt**；风格槽位填 §4 读到的 token 色值 / 参照名，不用形容词 |
| 6 | **定模型** | 用 §1 默认模型（当前实测 `gpt-image-2.5`）。**不硬编码到其它文档**，走 §1 口径 |
| 7 | **核对生成范围** | 核对本次生图是否落在**本轮任务范围内**（§1.5）：是不是为已明确的交付物服务、数量是否与实际需要相称。**超出任务范围的大规模批量生图 → 按正常任务范围变更与用户确认**（不是逐张付费审批） |
| 8 | **调用生成** | 按 §1.5 自助调用（ZCode 默认 `scripts/zcode_image.py`；方法论见已迁移的 `huashu-gpt-image`，**不复制其实现**）。⚠️ **按实际需要生成，避免无效重复调用** |
| 9 | **验收新图** | 过 §4.6 六项（尺寸 / 格式与透明 / prompt与来源 / 清晰度与裁切 / 引用关系 / 可引用性）+ **风格一致性**：色值是否落在 `design-tokens.md` 的 token、气质是否与 `visual-translation.md` 一致。不合格 → 定向重生成一次（**不为微小差异反复生图**） |
| 10 | **登记入清单** | 写入 `handoff/assets.md` + `assets/img-prompts/<名>.md`（一图一档），登记用途/尺寸/来源/模型/引用关系。**实现端按清单引用**，不各自散落 |

### 4.7.2 素材需求记录格式（一图一档，追加进 `assets/img-prompts/`）

```
素材：bg-empty-state（开发阶段补 · 2026-10-14）
需求来源：<哪页/组件/状态>，为何必须位图：<一句话>
用途 / 目标尺寸：<页面区块> / 1024×768
Prompt：<自动生成的英文原文>
模型：gpt-image-2.5（§1 默认）
风格继承：token <--bg #F4F5F3> / <--navy #17375E>；参照 <visual-translation.md 的母题>
实际文件：`assets/images/<名>.png`（落盘后填实测尺寸与格式）
引用：<组件名> → res/drawable/bg_empty_state.png
授权依据：本轮任务范围（§1.5）；生成记录见 design-brief.md「## 生成记录」
```

### 4.7.3 生成范围与成本记录（不再分立审批）

**不再按"授权范围"分立审批。** 概念图、阶段 4 验证素材、开发期素材都是**同一类正常模型调用**——任务需要就生成，**不需要逐次申请付费授权**（§1.5）。但要**分用途记账**，便于回溯与发现"任务规模异常扩大"：

| 用途 | 覆盖 | 默认数量 | 记账 |
|---|---|---|---|
| `concept` | 阶段 2 最终概念图（探索方向） | **1 张**（候选方向先只出 Prompt，§2.6~§2.8） | 记张数 + 模型 |
| `validation` | 阶段 4 HTML 验证素材（还原概念图，§3.6.3） | 按实际需要，一次列清单 | 记张数 + 模型 |
| `dev-asset` | 开发阶段按需正式素材（§4.7） | 按实际需要 | 记张数 + 模型 |

**记录格式**（`design-brief.md` 的「## 生成记录」一节，或项目产物目录；🔴 **不写进 `direction-approved.md`**——那是真实视觉确认 Gate 的物证，§3.3）：

```
| 用途 | 张数 | 模型 | 链路 | 计费 | 时间 |
| concept | 3 | gpt-image-2.5 | 本机 CPA 127.0.0.1:8317 | 是（按量） | 2026-10-14 |
```

**硬规则（成本控制，不是审批）**：
- **不作无意义的重复生成**（同一条件不重跑）；**数量按实际任务需要**（§7）
- **任务规模明显扩大**（如从「3 张概念图」变成「批量产品素材」）→ 按**正常任务范围变更**与用户确认，**不是**恢复逐张付费审批
- 生成失败先读原因、**有限重试**，不无限循环
- 记账口径同 §1.5：**留痕供回溯，不阻断执行**

### 4.7.4 生图通路不可用时的处理（不假装生成）

生图**通路不可用**时，**不得**假装生成。按优先级提供替代：

1. **复用**（回到 §4.7.1 第 2 步）——再找一次项目里有没有能用的现成图
2. **原生**（回到第 3 步）——用 SVG / CSS / 渐变 / 几何拼出等效视觉，标注"非生图实现"
3. **诚实 placeholder**——留一个带尺寸标注的占位块 + 一句"此素材待制作"，**继续推进开发**，交付说明里点名
4. **报告技术阻塞**——把 §4.7.1 的素材需求 + 完整英文 prompt 交付用户（可自行出图后交回）

> **红线**：**不得假装生成**（无通路却报"已生成"），也**不得**用占位图冒充已还原的视觉。生图通路不可用是**技术限制**，如实报告即可（§2.2.1）——它不是"未授权"。**同时**：生图自主**不等于**可以随意发起——**用户没要求、任务也不需要时，不得发起生图调用**（"任务范围内自主"的前提是先命中本通路，§1.5）。

### 4.7.5 边界（谁做什么）

| 谁 | 负责 |
|---|---|
| **实现端 / 开发 agent** | 发起需求、走十步规程、按 `assets.md` 引用成品 |
| **DesignWise（本 skill）** | 提供判断规范（§4.7.1）、prompt 规则（§4.3）、规格（§4.6）、成本口径（§1.5/§4.7.3）、登记格式（§4.7.2） |
| **用户** | 明确任务范围与交付物（生图在任务范围内自主执行，见 §1.5） |

> **不要求所有项目都生成图片**：多数开发期缺料可用复用或原生解决（第 2、3 步）。**只有位图确有价值时才走生图**——为"流程完整"生成 = 无价值步骤。

## 5. 产品化落地（阶段 6 · 正式实现）

**设计确认后，由 Reasonix/实现端自主选择适合实际项目的技术方案**：

| 平台 / 场景 | 可选技术方案 |
|---|---|
| Android | **XML 布局** / **Jetpack Compose** |
| Web | **HTML / CSS / JavaScript** |
| 矢量图形 | **SVG** / Android **VectorDrawable** |
| 位图 | **PNG** / **WebP** |
| Android 图标 | **Adaptive Icon**（`mipmap-anydpi-v26/`） |
| 其他 | 其他适合该项目的技术方案 |

> 🔴 **正式开发应以已经确认的设计为基准**——按 `visual-translation.md` 的 token 与组件规则实现，**不要在工程阶段无理由重新发明视觉方向**。若工程约束确实要求偏离已确认设计（如某效果原生做不稳），**如实说明并回到设计环节确认**，不静默改掉。

### 5.1 阶段 4 验证素材的处置（三选项 · 不浪费已生成成果）

阶段 4 生成的验证素材（`prototype/assets/img/`）**默认不丢弃**——先判断它能否直接进产品，避免重复生图：

| 选项 | 何时选 | 动作 |
|---|---|---|
| **A · 直接复用** | 质量已满足产品需求（清晰度 / 尺寸 / 透明背景 / 风格一致） | 迁入 `assets/images/`，按 §4.6 交付规格登记 + 补 `img-prompts/`，**不重复生成** |
| **B · 按工程要求重新生成正式素材** | 复用不达标（尺寸 / 格式 / 透明背景 / 需更高保真），但**视觉语言不变** | 以验证素材为参考（可走 `--ref` 图生图）重出正式版，落 `assets/images/`，过 §4.6 |
| **C · 用矢量 / 代码实现替代** | 工程师能更简单地实现、且**收益更高**（可缩放 / 体积小 / 可主题化 / 维护友好） | 改用 SVG / VectorDrawable / CSS 实现，标注「非位图实现」，不保留位图素材 |

**选择原则**：**哪个方案在真实产品里更可靠、维护成本更低就选哪个**——不为「用上生成成果」而保留难维护的位图，也不为省钱而在位图确有价值时硬做 CSS。
> **判定依据**：A/B 都要过 §4.6（尺寸 / 格式与透明 / 清晰度 / 引用关系）；C 要在 `handoff/assets.md` 写明替代理由与实现位置。三者都是合法终态，**不存在"必须生图"或"必须复用"**。

方向确认后，由 DesignWise 依据**已批准的效果图 + 设计 Spec + 产品功能需求 + 正式图片素材**实现真实 UI：

- **页面布局真实**（用 CSS Grid/Flex 真排版，不是把效果图当背景）
- **按钮和交互有效**（可点击、状态可切换）
- **内容可动态更新**（不是写死的图片）
- **适配目标屏幕**（真机尺寸 / 响应式）
- ❌ **不把视觉效果图作为静态界面交付**（§4.2 红线）

实现细节走原有链路：`references/app-prototype.md`（App/iOS）、`references/react-setup.md`（技术红线）、`references/product-value.md`（产品价值）。

**实现完成 ≠ 交付完成**：原型要交给 Web/Android 工程或 PPT 制作方落地，必须附**设计交付包**（页面结构 / 设计规范 / 状态与交互 / 真实文案与数据 / 素材清单 / 适配与无障碍 / 验收基准图）——**不许让开发 agent 对着截图猜**。完整契约见 `references/design-handoff.md`。

> 🔴 **HTML 原型 ≠ Android 最终实现代码**：HTML 是**设计交付物与视觉基准**，不是拿去编译的源码。Android 侧请按交付包用原生实现（Kotlin/Compose/XML），Web 侧按交付包选定技术栈实现。把原型 HTML 硬塞进 App 是反模式。

## 6. 真实运行与验收（阶段 7 · 验证与反馈闭环）

**保留现有全部验收机制**：产品价值判断、Spec 一致性、Scope 冻结、UX 评审（`critique-guide.md` 5 维度 + 用户价值 + Spec 核验）、浏览器验证（`references/verification.md`）。

### 6.0 验证手段（按项目实际情况选择）

| 验证项 | 用什么 |
|---|---|
| **视觉还原度** | §6.1 对比已确认概念图 vs 真实渲染/真机截图 |
| **交互与功能正确性** | 点击测试、`pageerror` 为 0、状态可切换（`references/verification.md`） |
| **真机或真实浏览器验证** | 真机安装 / 真实浏览器打开（不是只看代码） |
| **大字体、多语言与多尺寸适配** | 系统字体放大、多语言串、多分辨率 |
| **性能与兼容性** | 启动/渲染耗时、目标 API 区间、厂商遮罩等 |
| **安全、隐私、广告及其他必要业务回归** | 按项目既有回归清单 |
| **修改范围和回滚能力** | diff 只含本任务；回滚路径可执行 |

> 🔴 **设计本身的问题回设计环节修，不用代码补丁掩盖**：若验收发现的缺陷根源在视觉方向或信息结构（不是实现 bug），**回到阶段 3/4/5 相应环节处理**（必要时重发生图或改原型），**不得用额外代码补丁把设计缺陷盖过去**。

### 6.1 视觉还原检查（轻量，对比概念图 vs 实现）

对比 **GPT 已确认效果图** 与 **DesignWise 真实渲染截图**，识别明显偏差：

| 检查项 | 关注什么 |
|---|---|
| **布局偏差** | 主要区块的位置/比例关系是否走样（首屏核心行为是否仍在视觉首要位置） |
| **字体层级差异** | 标题/正文/标签的大小对比是否被压平 |
| **图片素材错误** | 素材是否错位、拉伸、还是用错了图 |
| **配色与视觉气质偏差** | 主色/底色/情绪基调是否跑偏 |

**判定原则**：**不要求机械像素级一致**——以**用户确认的设计意图**和**真实产品可用性**为准。效果图是意图，实现对意图负责，不对像素负责。

**情感意图核对（轻量，可跳过）**：若 Brief 第 4 段定义过情绪机会，对照实现看一眼——**那处机会在实现里是保留了，还是被削弱了？** 判定唯一标准仍是「用户会不会真的这样感受」（`references/product-value.md` §0.5），**不是**「效果图里有所以实现必须照做」：概念图里的情绪表达**本来就是探索态**，实现可以选择不做。

**同时验证**核心功能与交互（点击测试，`pageerror` 为 0）。

### 6.2 闭环检查清单（✅/❌ + 证据，逐项写进交付报告）

| # | 检查 | 判据 | 证据 |
|---|---|---|---|
| 1 | **原始需求是否保留** | 逐条比对 spec 的功能/边界，无增删 | spec.md ↔ 实现页面 diff |
| 2 | **用户选择的视觉方向是否正确继承** | `visual-translation.md` 的"落实"逐条在实现里找得到；母题有对应物 | 截图标注 + 转译表 |
| 3 | **GPT 虚构数据是否被排除** | 实现里所有数字/日期 = spec 真实值，**零幻觉值** | 数值逐项核对表（计步器实测过 4 项幻觉） |
| 4 | **正式素材是否可被工程引用** | §4.6 清单每张素材都过；路径可解析 | 素材清单 + 引用路径 |
| 5 | **HTML 页面是否正常渲染** | 无 console error、`pageerror`=0、无溢出/截断 | `scripts/verify.py` 输出 |
| 6 | **交付内容是否完整** | `design-handoff.md` 六段齐全（§10） | 交付包清单 |
| 7 | **截图 vs 设计基准差异** | §6.1 偏差清单，只修实质偏差 | 偏差清单 |
| 8 | **情感价值点是否可信（可选）** | Brief 第 4 段若有情绪机会 → 说得出「谁 / 哪个时刻 / 因为什么」；说不出即装饰，删掉不算缺陷 | 一句话说明，或标 N/A |

### 6.3 定向修复，不推倒重来

**发现问题 → 只修被点名的实质项**，复验范围按缺陷影响面决定，**不重跑全流程、不重新生成全部设计**。风格/措辞/可读性偏好不算实质问题，不改。

**输出**：偏差清单（现状 / 是否影响意图 / 改什么），只修实质偏差，不为「更像效果图」牺牲可用性。

## 7. 费用与重复调用治理

- **概念阶段**：🔴 **每个候选方向各 1 张真实候选图**（§2.2，必要投入、不逐张试探、不为凑数硬出方向）→ Gate 1 在其上比较（§2.6.1）→ 用户选定方向后**用收敛型最终提示词生成正式概念图**（§2.8）；定向迭代只重出受影响的那张
- **验证素材（阶段 4）**：只为**视觉价值依赖图片**的元素生成（§3.6.3 边界内不生成）；一次列清单、不逐张试探；同一张能复用时优先复用
- **有限重试**：一次调用失败先读原因再决定（`zcode_image.py` 失败即非零退出并报告原因，人工分档；`gen_via_cpa.py` 的 allow/deny/unknown 自动分档未随迁）；**不盲目重试**，也不无限循环
- **编辑优先**：已在某方向上的微调走图生图（`--ref`），不从零重新生成
- **正式素材**：方向锁定后才生成，且**复用**已有素材（含阶段 4 验证素材，§5.1），不为验证反复生成
- **同方向微调不重复多方向探索**（§3）
- **视觉评审不重复送审**：Gate 1（§2.6.1）与 Gate 2（§3.7.6）各自**走一次**；像素级微调、间距 / 圆角 / 单节点位置调整、已由客观测量确认解决的问题**不重新送审**；**不为凑 Gate 送审而额外生成候选图**（有几个真实候选就送几个）。
- 🔴 **成本不得转嫁为视觉失真**：为省生图成本而用占位图顶替需要图片的视觉 → 评审结论失真，是**禁止**的省钱方式；同时**不强制所有项目生图**（§3.6.3 边界）。
- **GPT 生图成本口径 = §1.5 生成范围与成本控制**：**任务范围内直接生成，不需逐次付费审批**；按实际需要决定数量、失败有限重试、已有素材优先复用、规模明显扩大按任务范围变更处理。**不做"探测式"生成**，也不为省 token/费用牺牲需要图片的视觉。

## 8. 降级与能力映射（agent-agnostic）

本文件按**能力**而非工具名编写（呼应 `references/runtime-adapters.md`）：

| 能力 | 本机已验证载体 | 缺失时 |
|---|---|---|
| **GPT 图像生成** | ZCode 默认 `scripts/zcode_image.py`（本机 CPA，OpenAI 兼容 `/v1/images/*`；方法论见已迁移的 `~/.zcode/skills/huashu-gpt-image/`） | OpenAI Images API（自备 key）；再不行 → **明确报告技术限制、暂停生图环节**（§2.2.1），并可交付完整 prompt 让用户在 ChatGPT 出图后交回继续；**不得静默改用 SVG/程序绘图冒充概念图** |
| **图生图 / 参考图编辑** | 同上脚本 `--ref`（`/v1/images/edits`） | 无编辑能力时：改 prompt 重新生成，或转 HTML/CSS 微调（属阶段 4/5 的合法迭代动作） |
| **视觉评审（Gate 1 / Gate 2）** | 默认 **原生自检**（主模型直接读真实图片，结论标注「自检」）；**用户明确授权 GPT 评审通道后**，才用 **`scripts/zcode_vision.py --confirm-gpt-review`**：直连 CPA Responses API 的 `input_image`（`/responses`），只收磁盘真实图片（默认模型 `gpt-6-astra-high`）；**无台账 / 审计 / 轮次限制，不是 copilot 正式 REVIEW**（Gate 1 §2.6.1 在候选图之后、Gate 2 §3.7.6）。**用户明确点名 Copilot 时**才走 `copilot` Skill 正式 REVIEW（`~/.zcode/skills/copilot/`）：`bridge_evidence.py --image` 采集真实像素证据 → `call_gpt.py --mode REVIEW` 出裁决（视觉评审只走 REVIEW，不另设 DECIDE 入口；一次性视觉 REVIEW 显式加 `--one-shot-visual-review`；文本 / 续轮 REVIEW 用 `--review-ledger`） | 外部入口不可用 / 调用失败 → **如实报告「本轮未获得有效视觉裁决」**，按缺证处理（Gate 1 缺证时交候选图让用户直接选；不伪造 PASS、不换模型冒充、不静默切换为 Copilot）；**不在任务里另写一次性实现；使用上述既有入口**（不自行实现图片传输 / CPA 调用 / Base64 内联） |

**降级底线**：GPT 不可用 → **L1 / L3 及判定为「不适用」的任务保留原有 HTML/CSS 设计能力**（60 种风格库、资产协议、反 slop 底线一条不少）；**L2 的 GPT 概念通路按 §1 / §2.2.1 报告并暂停，不得用 HTML 三方向冒充**。**降级牺牲的是「探索通路」，绝不牺牲反 slop 底线与真实资产协议。**

> ⚠️ **两类「HTML/CSS 回落」的边界**（呼应 §2.2.1）：任务性质判定为「不适用」（幻灯片/信息图/动画/纯排版/局部微调）→ 走 HTML/CSS 是**规则的选择**，正常；而**需要探索视觉方向的任务**因生图不可用而回落 → 必须**明确报告并暂停生图环节**，不得把 HTML/SVG 当概念图交付。回落到 HTML/CSS 时，在**方向确认时**把回落依据（用户原话或判定类型）写进 `direction-approved.md`（Gate 文件协议，§3.3）。

## 9. 反模式（做了就背离本文目的）

| 反模式 | 为什么错 |
|---|---|
| **把效果图当界面交付** | 假界面：按钮不可点、内容不可更新，是伪装成成品的概念图 |
| **把 GPT 当默认答案** | 幻灯片/信息图/动画等结构性任务强上 GPT = 文字糊、结构错，原有 HTML/CSS 更强 |
| 🔴 **方向定下来之前为每个候选方向分别做 HTML** | 无效工作；应先出真实候选图 → Gate 1 → 用户选定方向（§2.6.1 / §2.7），再对**选定方向**按需做一套（§3.4 / §3.6） |
| 🔴 **需要探索视觉方向却跳过 GPT 生图、直接画 HTML/SVG 当概念图** | **静默回退**：掩盖真实阻塞（能力缺失），且程序绘图不是创意探索（§2.2.1） |
| 🔴 **只交方案卡 / 文字描述就宣称「多方向探索完成」，或在真实候选图产生前定方向** | **未见图先定方向**：Gate 1 拿不到像素、用户也失去选择依据；方向必须由真实候选图 + Gate 1 + 用户共同确定（§2.2.1 / §2.6.1 / §2.7） |
| 🔴 **用间距 / 圆角 / 尺寸等微小变化包装成两个独立视觉方向** | 伪多方向：用户以为在做方向选择，实际只是同一方案的微调（§2.2） |
| 🔴 **把探索期的候选提示词原封不动当最终概念图提示词** | 跳过收敛：探索提示词的目的是「产生不同方向」，最终概念图需要锁定已选方向的稳定与明确（§2.3 / §2.8） |
| 🔴 **借「优化最终提示词」之名夹带新方向试探** | 那是重跑方向选择，不是收敛；会绕过用户已做的方向决策（§2.8） |
| **多方向只是换配色** | 用户拿不到真实的方向选择依据，等于只给了 1 个方向 |
| 🔴 **生图前把候选提示词摆给用户逐条人工挑** | 提示词层的审批是人工关卡；用户的决策点是**看完真实候选图后选方向**，不是审提示词（§2.5 / §2.9） |
| 🔴 **自动替用户选定方向**（Skill 默认流程下） | 方向选择是唯一固定属于用户的决策；只有用户本轮明确授权时才可自动选定，且须保留 Gate 1 推荐 + 依据 + 选择记录（§2.7 / §2.9） |
| 🔴 **为「省生图成本」跳过候选方向图、只出文字方案** | 省下的成本远小于方向选错造成的返工；候选方向图是必要投入（§1.5 / §2.2.1） |
| **为凑数硬出视觉方向**（价值低的任务强行凑满几个） | 方向数按 SKILL 的 L2 规则（默认 3，可 2，不得 1；用户明示或选定后迭代除外）；单方向仅在用户明示时做单方向 Review（§2.2） |
| 🔴 **把「多方向融合」做成几个图形拼在一起** | 拼贴会破坏核心概念与品牌一致性；融合是**提炼各方向最有价值的表达**，且必须过 §2.7 的五条检查，过不了就保留单一方向 |
| 🔴 **凭 Prompt 文字宣称视觉结论**（如「48px 清晰度通过」「满底合规」「品牌色准确」「方向 X 最优」） | 文字推测 ≠ 真实视觉测试结果；视觉结论**只能**由 §2.4 / §2.6.1 / §3.1 在真实图上得出（§2.6） |
| 🔴 **用户确认真实视觉前创建/写入 `direction-approved.md`**（把创意决策记录或生成记录写进去） | **创意决策 / Gate 1 推荐 ≠ 用户对真实视觉的确认**：该文件是真实视觉确认 Gate 的物证，提前写入会让**工程实施 Gate** 与**长片渲染 hook** 把「尚未确认」误判为「已批准」（§2.0 / §2.8 / §3.3） |
| **把旧任务的 `direction-approved.md` 当作新任务的授权** | 该文件按**当前任务**确认；旧记录只证明「当时那个方向被确认过」，不构成新方向的授权（§3.3 / SKILL.md Gate 协议） |
| **把提示词评审做成新的评分系统 / 新增专家角色 / 额外子代理** | §2.6 是**复用** `critique-guide.md` 的思考方式，不新增评分体系与角色（§2） |
| **发现配置就报告「生图可用」** | 未经真实出图验证 = 假装成功（§1 铁律） |
| **用 HTML 截图冒充 GPT 生成图** | 欺骗性交付，且掩盖通路不可用的真实阻塞 |
| 🔴 **把「要求不透明满底」的图当满底交付，却不先按目标底色合成核对** | 实测教训：三张概念图里两张实为透明底；只看像素值会误判成「有暗角/光晕」或误判成「满底合规」（§2.4） |
| 🔴 **只靠像素占比 / 连通块 / 腐蚀存活率等技术指标判设计优劣** | 指标是辅助证据；用户能否识别和理解才是核心（§2.4） |
| **把"需要修复的概念图"当"已达工程可用状态"报告** | 概念图是探索态；关键缺陷必须在评审前明确展示（§2.4） |
| **为精确几何 / 数量在生图上反复重出** | 概念成立时该类调整应由矢量工程实现，反复生图是无价值调用（§2.4） |
| **超出任务范围的大规模批量生图** | 应走正常任务范围变更，而非自行扩大（§1.5） |
| **为验证无限生成图片** | 费用失控；应复用已有测试素材（§7） |
| **为「流程完整」强行做 HTML / 强行生图** | 静态图标、简单启动页不必做 HTML；工程能可靠实现时不必在阶段 6 生图（§3.6.1 / §4） |
| 🔴 **阶段 4 用占位图 / 随机图库 / 简单替代交付需要图片的 HTML** | 把「视觉评审」变成「结构评审」，评审结论失真、可能误判通过（§3.6.3） |
| 🔴 **阶段 4 用占位素材却不声明，让用户以为已还原概念图** | 同上，且属隐瞒——正确做法是报告 + 交付 prompt + 报告技术阻塞（§3.6.3） |
| **第二次评审在没有验证素材的状态下判定「视觉通过」** | 缺素材时视觉意图无法判断，应命中情况 A 补素材再评（§3.7.1） |
| **阶段 6 无脑丢弃阶段 4 已生成的验证素材** | 可能造成重复生图；应先判断能否直接复用（§5.1 选项 A） |
| **第二次评审发现问题就从头重跑全流程** | 应按 §3.7.3 选最小必要动作（重发生图 / 改现有 HTML / 两者结合），不推倒重来 |
| 🔴 **DesignWise 在任务里另写一次性 GPT 调用 / 图片 Base64 / `input_image` / evidence bridge，或改动适配器本身** | 重复实现已有能力；视觉评审应走原生自检（默认）/ `scripts/zcode_vision.py`（授权后）或用户点名时的 copilot 正式 REVIEW，不要自行绕过安全隔离与缺证显式化（§2.6.1 / §3.7.6） |
| 🔴 **只给图片路径却不读取真实文件 / 文字描述 / Base64 文本，就当把视觉证据交给了 GPT** | 那不是像素：GPT 的视觉结论必须建立在真实 `input_image` 像素上（§2.6.1 / §3.7.6） |
| 🔴 **把几个候选分别送审，再由执行方拼接结论** | 应一次给全候选（标注版本 / 角色）让 GPT 直接比较（§2.6.1） |
| 🔴 **每次微调都重新视觉评审（`zcode_vision.py` 或用户点名时的 copilot）**（间距 / 圆角 / 1~2% 几何 / 单节点位置） | 无决策价值的循环；这类问题用客观测量自验，不重送审（§2.6.1 / §3.7.6 / §7） |
| 🔴 **Gate 2 在缺验证素材时判「视觉通过」** | 视觉意图无从判断；先按 §3.7.1 情况 A 补素材再送审（§3.7.6） |
| **把视觉评审裁决（`zcode_vision.py` 或用户点名时的 copilot）当成部署 / 推送 / 发布授权** | 它是内部判断依据，不改变授权边界，也不替代 `direction-approved.md` 的用户确认 Gate（§2.6.1） |
| **验收时用代码补丁掩盖设计缺陷** | 根源在视觉方向或信息结构的问题应回设计环节修，补丁会累积技术债（§6.0） |
| **真实产品图/Logo 用 GPT 生成** | 一眼假 + 失真品牌识别；应走 §1.a 取真图 |
| **概念图与正式素材混放** | 交付时易误用；且无法区分「探索态」与「集成态」 |
| **把 GPT 图里的数据/中文当事实** | 模型幻觉：次要数字、日期、中文常编错；一律以 spec 为准（§3.5.2） |
| **用户选定方向后直接开写 HTML，不转译** | 断链：实现与用户所选概念图对不上（§3.5 存在的原因） |
| **把原型 HTML 当 Android 最终代码** | 原型是设计基准不是产品源码；Android/Web 按交付包各自实现（`design-handoff.md`） |
| **让开发 agent 对着截图猜规格** | 交付包缺原理化规格 = 返工；必须给 token / 状态 / 数据口径（`design-handoff.md`） |
| **型号版本号抄进多个文档** | 升级时多处失同步；只在本文件 §1 写口径，别处引用 |
