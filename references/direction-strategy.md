# 方向策略 · 探索、判断与重出

> **读这份文档的时机**：阶段 1 要决定"出几个方向、怎么组织 prompt、怎么判断方向够不够不同、不合格怎么办"。
> **权威**：阶段与 Gate 在 `SKILL.md`；本文只展开阶段 1 的方法。
> **一句话立场**：方向是**结构假设**，不是配色选项。数量由实质分歧决定，差异由实测证明，取舍由设计判断负责。

---

## 0. 两个真实教训

- **固定三方向会产出换皮**：上游三轮失败的经验是"三版常常是同一个骨架换颜色和字重"（`directions.md:9`）。强制数量不等于强制差异。
- **只有一张也会跑偏**：没有比较就没有反证。所以不是"越少越好"，而是**有分歧才比较**。
- **融合是有效的**：乐乐第二轮把"世界地图（A）"与"纵向路线（B）"融合成"世界地图 + 当前站路线"，是真实成功的决策；但融合必须说明统一逻辑，否则就是拼图。

---

## 1. 方向数量：按实质分歧决定

| 情形 | 方向数 | 判据 |
|---|---|---|
| 现有设计系统/品牌/用户已指定结构，且无相互冲突的组织方式 | **1** | 再出两个只会是同骨架换皮 |
| 存在两种都成立的信息组织（例：时间轴 vs 地图；单列长卷 vs 分区卡片） | **2** | 分歧是真的，比较有价值 |
| 三种结构分别服务不同用户假设，且都能落地 | **3** | 需要第三方作反证 |
| 两个方向互补（A 的空间骨架 + B 的操作路径） | 先 2–3，后**融合** | 融合要写统一逻辑 |
| 现有方向明显不合格 | **先拒绝，再重出** | 不拿"最不差"凑数 |

**判断"实质分歧"的三个问题**：

1. 两种方案的信息优先级不同吗？（第一眼看到的东西不一样）
2. 完成任务的主路径不同吗？（操作顺序、页面跳转不同）
3. 如果产品换一个近似题材，这套结构还成立吗？成立 → 它是模板，不算真实分歧。

三个都答"否" → 只有一个真实方向，给 1 个最优方案，把精力放在打磨上。

**不要问用户"你想要几个方向"**：这是设计判断，不是用户偏好。

## 2. 方向的三个来源（App UI 版）

上游的三个来源是"最佳设计师 ×2 / 同媒介真实参照 ×2 / 随机风格轮盘 ×2"。**随机风格不适合产品 UI**——App 的第一要求是完成任务，风格抽签会直接违反"有用"。V3 改写为：

| 来源 | 做法 | 适用 |
|---|---|---|
| **A · 现有体系推导** | 从项目现有 token、组件、已发布界面的真实视觉语言出发，重构信息架构；不凭空造体系 | 有设计系统 / 已发布产品（最常见） |
| **B · 同品类真实参照** | 找 2–3 个**同任务类型**的真实 App 界面，**核实存在并亲眼看**，拆出可迁移规则（几栏、标题正文比、主色占比、图文关系、导航形态）；写不出具体规则就是没看懂 | 需要跳出本项目惯性 |
| **C · 产品独有的结构隐喻** | 从产品内容本身长出结构（例：计步的"路线/站点"、阅读的"书架/书页"、财务的"账本/流水"）；必须回答"这个结构为什么只能属于这个产品" | 需要差异化、现有体系平庸 |

**禁止**：把"风格库随机抽一个"当方向；把某设计师的名字当方向而不写具体结构；用装饰性插画代替结构差异。

参照要**同媒介**：拿网页版式套 App 会过头或无聊；拿游戏 UI 套工具 App 会误导用户预期。

## 3. 方向卡（零成本，先写卡）

出图前先写卡。卡片便宜，换皮的代价贵。六栏：

| 栏 | 写什么 | 不合格 |
|---|---|---|
| **逻辑与来源** | 来自 A/B/C 哪一类，具体依据（现有哪个 token/哪个 App/产品哪段内容） | "参考了优秀设计" |
| **借用的是什么** | 可迁移的具体规则：网格、字号关系、主色占比、图文关系、信息密度 | "简洁高级" |
| **主角信息与素材** | 这一屏的主角是什么（数字、地图、列表、封面），需要什么真实素材 | "放一些图" |
| **结构骨架** | 一句话说清版式：几栏、层级几层、首屏锚点、导航形态 | "卡片式布局" |
| **差异点** | 与其它方向真正不同的那一处（胆量花在哪） | "颜色不同" |
| **form 来自产品的哪里** | 这个形式为什么只能属于这个产品/这批用户 | 答不出 → 还在抽签 |

**一张卡写不出一句话的"差异点"，就不要为它出图。**

## 4. 提示词结构

多方向时（1 个方向时共用块与方向块合并）：

```
[任务块]        逐字相同：产品定位、用户与场景、本页核心问题、
                最重要的信息与操作、业务规则与数据口径、平台硬约束、
                本页禁止出现的编造数据/假定状态/伪控件
[原则转译块]    逐字相同：有用/好懂/舒服/有意义 → 4–6 条本页可检查要求
[方向块]        各不相同：方向名与真实锚点、结构骨架、生成意图、
                与其它方向的结构差异、视觉语言
[载体与边界]    比例尺寸、不可迁移声明（图内文字为示意）、图内文字语言
```

规则：

- **共用块不得被用来制造差异**：为体现不同而增删业务功能、数据口径、硬约束，算违约不算方向。
- **共用块也不得过度锁死解法**：它可以锁定"必须显示什么、优先级是什么"，不能锁定"必须几栏、必须什么母题"——那是方向块的空间。
- 一方向一 prompt 一 job；不在一张 prompt 里塞多个方向。
- 提示词必须带真实产品资料（规则、数据、约束），不能只有风格词。方法见 `references/image-generation.md`。

## 5. 差异实测（不靠"看起来不一样"）

```bash
python3 scripts/direction_divergence.py \
  --image design-demos/<task>/concepts/A.png \
  --image design-demos/<task>/concepts/B.png \
  --image design-demos/<task>/concepts/C.png \
  --out design-demos/<task>/direction-divergence.json \
  --strict
```

输出每对图片的：

| 指标 | 含义 | 判定 |
|---|---|---|
| `palette_distance` | 4×4×4 RGB 直方图距离（0–1） | `< 0.06` → 判"色板几乎相同" |
| `skeleton_correlation` | 32×20 灰度边缘图相关系数 | `> 0.55` → 判"版式骨架高度相似" |
| `verdict` | `distinct` / `same-palette` / `same-skeleton` / `reskin` | `reskin` 同时满足上面两条 |

`--strict`：任一对为 `same-skeleton` 或 `reskin` 时退出码 1。

**局限（必须知道）**：

- 概念图常带设备外框，会让骨架相关性整体偏高；脚本默认裁掉 8% 边框，但仍偏向保守。
- 它证明不了"方向对不对"，只证明"两张图在结构/色板上到底有多像"。
- 判为 `distinct` 不等于设计合格；判为 `same-skeleton` 也不等于一定没差异（可能只是构图巧合）。**结论由 ZCode 结合方向卡给出，脚本只给事实。**

**重出规则**：判为换皮/同骨架 → **换骨架或换来源**，不是换颜色、加装饰、调圆角。

## 6. 选择：按顺序判断

1. **单看就够好**：拿出去不丢人；缩略图都撑不住的，完整版救不回来。
2. **彼此真的不同**：不同骨架（有实测支撑）、不同气质，不是同一套换色。
3. **不撞最近交付**：查 `check-ui.mjs --ledger-check`，避免和最近项目同一外观家族。
4. **不用力过头**：最多一个方向把整页变成隐喻道具（地图/终端/报纸/仪表盘）且饱和度/字号拉满，且只有内容真需要时才成立。测试：去掉这个手法，信息是更清楚还是更糊？去掉更清楚就是过头。
5. **能落地**：目标平台能实现，最大字号不崩，素材拿得到。
6. **答得上产品问题**：方向的差异能对应 brief 里的真实问题或用户假设。

**顺序不能颠倒**：先"够好"，再"不同"，再"不重复"，最后才是"有胆量"。

## 7. 决策记录（`direction-approved.md`）

必须写：

- 方向数与**依据**（为什么是 1/2/3）。
- 每张图：id、路径、sha256、模型、请求/实际尺寸、生成时间。
- 差异实测结果（文件路径 + 关键指标）。
- 逐方向合格性：核心需求、信息与操作清晰度、严重可用性/可读性问题、是否违反产品规则、是否编造数据/诱导、原生可实现性。
- 三出口之一：**采用 / 融合 / 全部拒绝**。
- 采用：修正项、进入原型前必须改的点。
- 融合：保留什么、舍弃什么、统一后的层级与交互逻辑；改变主要骨架时补的真实整合图指纹。
- 全部拒绝：可执行修正项、只重出哪些方向。
- 放弃方向的机会成本、主要风险。
- 与 `P*`/`S*` 的对应。
- 用户否决/确认原话（如有）；可选独立复核意见（如有）。
- **状态**：`实施基线` 或 `实验推荐`（同一任务同一时刻只有一个基线）。

**这不是审批记录，是设计判断的可追溯证据。** 用户可否决；否决后记录原话并按用户方向继续，不把设计判断写成用户选择。

## 8. 失败归因与重出

反复失败时先归因，再改，不要只把同一句话写得更重。

| 归因 | 症状 | 改法 |
|---|---|---|
| **模型没执行结构指令** | 图很漂亮，但骨架和你写的不一样 | 把结构写成可数的事实（几栏、首屏锚点、信息顺序），减少形容词；必要时给骨架草图或局部参考 |
| **共用块自相矛盾** | 同一张图里两个要求打架（如"高密度"+"大留白"） | 删到不冲突；原则不适用就写"本版不适用" |
| **要求本身不可视化** | 抽象原则（"有掌控感"）无法落成画面 | 转译成可见事实（进度可见、下一步明确、状态可回退） |
| **参考不足** | 模型只能编 | 提供真实参考图或产品真实截图（`--ref`）；没有就明确说"按文字理解" |
| **需求本身不清楚** | 每次改都换一个错法 | 回阶段 0 补 brief / 状态地图，不要继续出图 |

重出时：

- 只重出受影响方向，保留仍有效的候选。
- 已有 ≥2 个合格方向可比时，允许淘汰不合格方向直接比较，不必为"全都合格"继续生成。
- 只剩 1 个合格方向且需要比较时，重出受影响方向。
- 不设固定重试轮次；**不重复无信息增量的生成**。

## 9. 反模式

| 反模式 | 为什么坏 |
|---|---|
| 为了"给用户选择"硬凑 A/B/C | 用户收到的是三个换皮，等于没选择 |
| 用配色当方向差异 | 结构没变，落地时等于没探索 |
| 概念图里放编造数据/伪控件 | 会被当成规格抄进实现 |
| 只写"高级、简洁、有质感" | 不可检查、不可复现、不可判断 |
| 全部方向都"及格"就选最顺眼的 | 跳过合格性判断；应写清每个的致命问题 |
| 融合＝把两版的部件拼在一起 | 没有统一层级，落地必然打架 |
| 反复重出同一句话直到好看 | 没有归因，浪费生成额度 |
| 拿方向图当验收基准 | 概念图不是规格，尺寸/文案/状态都不可信 |
