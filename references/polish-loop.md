# 打磨环 · 看、挑刺、改、再看

> **读这份文档的时机**：阶段 3（设计评审与完善）。方向已定、原型能点，接下来是把它从"草稿"变成"能交付"。
> **权威**：阶段与 Gate 在 `SKILL.md`；本文只给打磨的方法、看什么、改多少、什么时候停。
> **一句话立场**：同一个模型，看过自己的截图再改三轮，和写完就交，产出一个档次。**这一步不能省，也不能假装做了。**

---

## 0. 前提：第一版只是草稿

HTML 原型第一次能点通，只能说明结构搭起来了。**没逐屏看过原图的版本不算设计过。**

- 整页长图缩成一张看，字号、间距、裁切全糊，问题看不出来 → 必须逐屏、按原尺寸看。
- 脚本能报数字（字号、对比度、点击区、溢出），**不能替你判断好不好看**；数字是提示你往哪看，不是结论。
- 一次改十几处等于没改：看不出哪个改动起作用，还容易把好的地方改坏。

---

## 1. 怎么拿到要看的图

对每个要打磨的屏，按真实设备尺寸出图（**不是**桌面浏览器的宽屏截图）：

```bash
# 单屏原尺寸截图：宽度按目标设备；高度用 --full 可看整屏长内容
node scripts/check-ui.mjs --url "file:///…/index.html?screen=p1-today" \
  --width 460 --height 960 --font-min 14 --tap 48 \
  --shot design-demos/<task>/prototype/screenshots/r1-p1-today.png
```

- **一屏一张图**，按 `P*`/`S*` 编号命名，轮次前缀 `r1-`/`r2-`。
- 弹层与覆盖态**单独出图**（`?screen=…&overlay=s4`），不要只截它弹出来那一刻的底页。
- 大字号屏单独出图：`?fs=16`（1.6）与 `?fs=20`（2.0）；设备宽度下三列/标签+数值结构必须在这里看。
- 出图后**逐张打开看**（宿主有图像读取能力就直接读 PNG）。看的是原图，不是缩略图拼贴。
- 同一轮所有图放在同一目录（`screenshots/r1-*`），后续对比和证据引用都用这个路径。

脚本只报"连续多屏结构雷同""接近空屏""对比度不足"这类事实；这些提示指方向，不替代看图。

## 2. 看什么：八个问题

每轮带着这八个问题看，把**最伤的三处**写进 `prototype-notes.md`。写清"哪一屏、哪个元素、怎么不对"，不写"感觉一般"。

1. **首屏三秒**：没看过这个项目的人，三秒内知道这是什么 App、给谁用、现在最该做什么吗？产品独有的东西（那个数字、那张地图、那本书）在第一眼里吗？
2. **主任务可达**：这一屏最重要的操作，拇指够得到吗？点下去会发生什么，和用户预期一致吗？有没有"看起来能点其实不能"的伪控件？
3. **每屏有没有事件**：往下看/切页，每一屏有没有一个让人停一下的东西，还是"标题 + 三张卡片"一路重复到底？安静的屏是留白还是空？
4. **层级**：眯眼看每一屏，最先跳出来的是不是最重要的那个？次要信息有没有在抢戏（同字号、同色重、同面积）？
5. **状态完整**：空、加载、失败、锁定、未授权、永久拒绝、额度用尽、首装首启——brief 里列的状态，在原型里真的能看到吗？**只有正常态的屏，交付后一定被实现端自己发明。**
6. **大字号与适配**：1.6 / 2.0 下，多列、label+value 同行、固定高度、卡片内文字、底部操作条还成立吗？弹层关闭按钮还够得到吗？内容溢出时是滚动还是裁切？**裁切是缺陷，滚动是设计。**
7. **手艺**：对齐、间距节奏、行尾孤字、难看的断行、溢出、裂图、图标与文字基线、和周围不是一套的元素、对比度、48dp 点击区。
8. **对照方向卡**：把截图和 `direction-approved.md` 的方向卡并排看——"借用的是什么"里写的那几条规则落实了吗？走样在哪？另外问一句：**去掉哪一样东西，这一屏反而更好？**

第 5、6 问是 App UI 最容易漏的两处，也是乐乐两次改版真实翻车的地方（锁定态缺失、1.6 三列错位、弹层裁切）。**它们不是"打磨项"，是致命项。**

## 3. 改什么：一轮三处

- **一轮只改最伤的三处**，改完重新出图再看。不是"顺手把看见的都改了"。
- **先结构，后手艺**：首屏不成立、主角信息缺席、整屏平庸、状态缺失 → 先改这些；对齐、孤字、间距 → 后改。
- **哪一屏怎么看都平庸，就别修修补补**：推倒重做，换一种组织信息的办法。重做前问一句："一家顶尖工作室接了这个项目，会在这一屏上多花三天做什么？"
- **改的是被指出的那个问题**：不要借打磨顺手重做方向、换字体体系、加装饰。方向问题回阶段 1，不在打磨里偷偷改。
- **每处改动留证据**：改前图 + 改后图 + 一句话说明改了什么、为什么。不写"优化了视觉层级"这种不可核对的话。

## 4. 看几轮

| 阶段 | 轮数 |
|---|---|
| 概念方向图 | 1 轮：看、挑最伤的三处、必要时重出。方向图是给人做决策的，不用磨到完工 |
| 方向确定后的 HTML 原型 | **至少 2 轮**；到某一轮认真看完找不出值得改的三处为止，通常 3–5 轮 |
| 用户赶时间 | 1 轮，交付时明说"只打磨了一轮"，不写成"已完成打磨" |
| 只改单屏视觉 | 该屏 1–2 轮 + 受影响屏复看 |

**停止判据**：不是"改到没时间"，也不是"改到分数够"，而是**认真逐屏看完，找不出值得改的三处**。

**回退判据**：到第 5 轮还在大改结构 → 问题在方向或信息架构，不在打磨。停下来回阶段 1/2，不要用打磨掩盖方案问题。

## 5. 记录与交付证据

`prototype-notes.md` 每轮一节：

```markdown
## 打磨轮次 2（2026-11-12）
- 看图范围：P1 P3 P6 S4 S9 @1.0 / P3 P6 @1.6 / S4 @2.0（screenshots/r2-*）
- 本轮改的三处：
  1. P6 三列摘要 @1.6：第三列数值换行后被裁 → 改 2 列 + 关键值单独一行（r1-p6-16.png → r2-p6-16.png）
  2. S4 目标选择 @2.0：确认按钮被键盘遮挡且不可滚动 → 底部按钮固定 + 列表独立滚动（r1-s4-20.png → r2-s4-20.png）
  3. P3 今日：主数字与"开始"按钮同色重，视线分散 → 主数字升一档字重，按钮降饱和度（r1-p3.png → r2-p3.png）
- 未改但记录：P8 地图缩略图在 1.0 偏小（可接受，原生用真实地图）
- 下一轮打算看：空/错误态、P2 城市详情的滚动长度
```

- **每轮截图保留**，不覆盖、不删。
- 交付时给用户看**第一轮与最后一轮**同屏并排（首屏 + 最难的那一屏），让他看到改了什么。
- 不给"分数趋势"、不编"提升 30%"：打磨的证据是图，不是数字。

---

## 6. 能力边界

- **不能看图就不要声称打磨过**。宿主/模型读不了截图时：跑脚本拿事实（字号、对比度、点击区、溢出、裂图），逐条修；交付时明说"本版未经看图打磨"，并附截图路径让用户自己看。
- **脚本通过 ≠ 好看**：`check-ui.mjs` 全绿只证明没有机械缺陷。
- **不要用叙述代替看图**："已逐屏检查，视觉层级清晰"这种句子不是证据；证据是图 + 具体改动。

---

## 7. 反模式

| 反模式 | 为什么坏 |
|---|---|
| 只看整页长图 | 字和间距全糊，问题看不见 |
| 只截 1.0 一档就宣布完成 | 大字号错位、弹层裁切都是在大档才出现 |
| 一轮改十几处 | 无法归因，容易改坏好的地方 |
| 打磨中偷偷换方向/换配色体系 | 绕过方向决策，返工成本翻倍 |
| 用分数、评级、百分比证明改善 | 编造的量化不如两张图 |
| 修到没时间就停 | 停止判据是"找不出值得改的三处"，不是时间 |
| 只改视觉不改状态 | 状态缺失是致命项，不是打磨项 |
| 反复打磨掩盖方案问题 | ≥5 轮还在大改 → 回阶段 1/2 |
