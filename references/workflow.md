# 工作流 · 从接到任务到真机收口

> **读这份文档的时机**：准备开工、需要问用户问题、需要写假设或组织项目目录时。
> **权威**：流程阶段、Gate 与红线以 `SKILL.md` 为准；阶段操作细节与模板见 `references/app-visual-workflow.md`。本文只补「怎么问、怎么想、怎么组织现场」。

---

## 1. 开工前的思考顺序

1. **这是不是 App UI？** 不是 → 说明不在范围（见 `references/routing-table.md`）。
2. **是新任务还是局部迭代？** 新任务 → 完整 0–7；已有方向记录的小改 → 从阶段 4 继续。
3. **事实先于假设**：具体产品/技术/版本/规格先查权威来源；查不到问用户。
4. **读现场**：项目规则、现有设计系统、代码、素材、截图。
5. **产品三问**：谁在用 / 要完成什么 / 系统替他承担哪部分复杂性。
6. **整机重设计先建页面地图**：每页目标/功能/关键信息/业务规则/状态/问题/保留项/重构项，加导航与任务路径；**数量与截图不算理解**。
7. **原生可行性**：平台、系统版本、字体、系统栏、密度、触控、导航、权限、性能、素材格式。做不到的不要画进方向。
8. **范围冻结**：本次不做什么。

## 2. 怎么问用户

### 2.1 只问影响决策的缺口

不设问题数量下限；已知信息不重复问。优先一次性列出关键问题让用户批量答；宿主限制时（如一次最多 3 个）只问阻塞项，其余记为 `ASSUMPTION`。

### 2.2 缺口检查清单

| 类别 | 要确认什么 | 没答案时 |
|---|---|---|
| **设计上下文** | 有没有 design system / UI kit / 代码 / Figma / 截图 / 参考站 | 去项目里找；找不到按可探索约束处理 |
| **品牌资产** | logo、产品图、UI 截图、色板、字体、禁区 | 走 `brand-asset-protocol.md` 取官方资产 |
| **目标用户与场景** | 谁、什么场景、什么任务 | 按合理假设并标注 |
| **业务规则** | 必须保留的页面/流程、数据口径、权限、商业化边界 | **必须问**（不能自行发明） |
| **平台** | iOS / Android / 双端、最低版本 | 按项目现状判断；不确定问 |
| **交付形态** | HTML 原型 + 原生实现？只做原型？只做方向？ | 默认完整流程到原生；用户明确只做原型则到阶段 4 |
| **成功标准** | 怎么算完成 | 与用户确认或按产品三问推导，写进 brief |

### 2.3 不要问的

- 不要问「你想要几个方向」：新任务固定 **3 个**（流程要求）。
- 不要问「要平铺还是可操作」：App 原型默认平铺 4–6 屏且每台可交互。
- 不要问「要不要用 GPT 生图」：方向阶段必须真实生图；不可用则报告暂停。
- 不要用问题替代自己该做的调查。

## 3. 假设与对齐

- 在 `design-brief.md` 写清 `ASSUMPTION`，并说明影响；不要让假设悄悄进入设计。
- **对齐不是停轮仪式**：阶段 0–2 可以连续推进；需要用户拍板的只有业务规则、范围变化、授权边界。
- **早期展示**：HTML 原型可以先给灰色结构 + 标签，让用户尽早看到信息架构；但方向阶段必须给真实概念图，不能只给文字。
- **理解错了早改比晚改便宜 100 倍**：但不要用「等确认」拖住整个流程。

## 4. 项目目录组织

全文其余部分的相对路径（`prototype/`、`assets/`、`asset-manifest.json`、`handoff/`…）都相对**任务工作根**。
任务工作根默认是 `design-demos/<task>/`；项目已有设计目录时用项目目录，但目录内部结构不变。

```
design-demos/<task>/                 # 一次任务的完整产物
├── design-brief.md                  # 含页面地图（P*/S*）与目标→问题映射
├── concept-prompts.md               # 三方向 prompt + 生图前 CONSULT 预审记录（请求/回复/采纳）
├── concept-index.json               # 方向 id / 路径 / sha256 / 模型 / 尺寸 / 时间 / 来源
├── concepts/
│   ├── A.png / B.png / C.png
│   ├── merged.png                   # 可选：融合改变结构时的真实整合图
│   └── prompts/A.md B.md C.md       # 每方向一个 prompt 原文
├── direction-approved.md            # Copilot 方向证据与三出口；裁决前不得创建
├── .designwise/                     # 请求、证据包、回复、评审截图清单（不含秘密）
├── prototype/
│   ├── index.html
│   ├── vendor/                      # 可选：React/Babel 等本地库副本
│   └── screenshots/
├── prototype-notes.md               # 覆盖对照、设计评审记录、与选定方向的偏差、已知限制
├── assets/
│   ├── images/
│   ├── prompts/                     # 每张正式素材的生成 prompt
│   └── icons/
├── asset-manifest.json
├── generation-log.md                # 真实出图、处理、检查命令与结果
├── handoff/
│   ├── README.md
│   ├── structure.md
│   ├── design-tokens.md
│   ├── states-interactions.md
│   ├── copy-data.md
│   ├── assets.md
│   ├── adaptation-a11y.md
│   └── baselines/
├── native/                          # 原生工程（或项目内既有工程，则记录其路径）
└── verification-report.md           # 阶段 6 起维护落地对照表；阶段 7 双验收
```

**规则**：

- 不把临时验证素材路径写进 `handoff/`；交付引用 `assets/` 下的最终素材。
- 不把 API key、Cookie、内部链接、真实用户隐私写进任何文件。
- 单文件 HTML 的图片 base64 内嵌；多文件才用相对路径 + 启动说明。

## 5. 各阶段的心态

| 阶段 | 心态 |
|---|---|
| 0 理解 | 先调查再问；整机重设计先建页面地图，别拿截图当理解 |
| 1 目标 | 写契约，不写小说；目标要回指问题或保留项 |
| 2 三方向 | 先预审提示词再出图；三个方向是三次结构性回答，不是三套配色 |
| 3 方向选择 | 让 Copilot 看像素；采用 / 融合 / 拒绝都行，拼图不算融合 |
| 4 原型 | 还原视觉意图，不复制概念图的错误；真实截图评审之后才算完 |
| 5 素材 | 先复用再生成；清单是事实源 |
| 6 原生 | 落地设计目标，不是换 token；dp/sp 不等于 px |
| 7 验收 | 工程与设计分开判；三方对照；未验证不算通过 |

---

## 6. 什么时候停

- **需要停**：业务规则冲突、范围实质变化、需要新授权、Copilot/生图/真机不可用且无法在授权内解决、**生图前预审不可用（暂停生成）**、**旧版基线无法取得且影响落地判断**。
- **不需要停**：常规设计自由度内的选择、三个方向的结构决策（Copilot 判断）、融合方式、素材处理方式、原型实现细节。
- **不停不等于不报告**：每个 Gate 的证据要在交付说明里能查到；设计评审与落地对照的缺口要如实写。

---

## 7. 异常处理

| 异常 | 处理 |
|---|---|
| 用户拒答/赶时间 | 不豁免三方向与 Copilot；可压缩文档长度，不压缩证据 |
| 用户要求跳过方向探索 | 说明这是流程硬门；只有「沿用上次已确认方向」可复用记录 |
| 生图不可用 | 报告并暂停；可交付 prompt 让用户外部出图后交回真实文件 |
| 预审/方向/原型评审的 Copilot 不可用 | 受影响动作 `BLOCKED`；预审不可用暂停生成，评审不可用不声称 G4 通过 |
| 原生只换了皮 | 回阶段 6 按落地映射重构；测试通过、构建成功都不算收口 |
| 旧版基线缺失 | 复用既有截图/记录；不降级安装、不清数据、不恢复旧包；缺证如实标注 |
| 项目规则冲突 | 暂停受影响动作，说明条款与影响，其余继续 |
| 真机不可用 | 设计交付照常，原生/真机标 `PARTIAL`/`BLOCKED` |
| 事实不确定 | 先查权威来源；查不到问用户 |
