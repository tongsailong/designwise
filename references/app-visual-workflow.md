**治理接口不在本表**：SG 只是设计工作的事实状态。需要跨交接跟踪验收承诺时，按

## 2. 阶段 1 · 概念方向（SG1）

方法细节在 `direction-strategy.md`。这里只给执行顺序与记录格式。

### 2.1 执行顺序

1. **数方向**：按 `SKILL.md` 阶段 1 的场景规则（新产品概念默认三个独立结构假设；已有产品按实质分歧，或先候选后融合）。写清依据。
2. **写方向卡**（七栏，含核心交互）。写不出"差异点"或"form 来自产品的哪里"的方向不出图。
3. **写 prompt**：任务块 + 原则转译块逐字相同，方向块不同。带真实产品资料，不只风格词。
4. **真实生成**：`python3 scripts/zcode_image.py --health` → 逐张串行 → 同比例同尺寸同模型。App 默认竖版 `1024x1536`。
5. **逐张自检**：可解码、尺寸正确、结构差异可辨、共用块逐字一致、无编造数据。
6. **差异实测**（多方向）：`scripts/direction_divergence.py --strict`。
7. **设计决策**：采用 / 融合 / 全部拒绝，写入 `direction-approved.md`。
8. **可选审美咨询**：方向图已出、且视觉表达/原创性/取舍仍有实质不确定时，把真实方向图与方向卡交 `design-review-handoff.md` 的视觉咨询，可同时问创造性替代（母题/构图/值得保留的细节）；意见写入 `direction-approved.md` 并逐条标 accepted/modified/rejected，不投票、不等待。
9. **可选独立复核**：高风险或用户要求第二意见时派 ZCode 内置子 Agent 做只读复核。

### 2.2 `concept-prompts.md` 模板

```markdown

### 原则转译块
<有用→… / 好懂→… / 舒服→… / 有意义→…，转成 4–6 条可检查要求>

## 方向 A · <名称>（来源：A 现有体系 / B 同品类参照 / C 产品结构隐喻）
- 方向卡：逻辑与来源 / 借用的是什么 / 主角信息与素材 / 结构骨架 / 核心交互 / 差异点 / form 来自产品的哪里

<与其它方向的结构差异 + 视觉语言>

<比例尺寸 / 图内文字为示意 / 语言>

```

```json

  "task": "<task>",
  "shared_block_sha256": "<hash>",
  "concepts": [

     "model": "gpt-image-2.6-sunburst", "profile": "final", "complexity": "high", "quality": "high",
     "requested_size": "1024x1536", "actual_size": "1024x1536", "output_format": "webp",
     "generated_at": "…", "source": "A|B|C", "structure": "…"}
  ]

```

### 2.4 差异实测与判断

```bash
python3 scripts/direction_divergence.py --image concepts/A.png --image concepts/B.png \
  [--image concepts/C.png] --out direction-divergence.json --strict
```

- 判 `same-skeleton` / `reskin` → 换骨架或换来源重出，不是换颜色。
- 判 `distinct` 只是"不像"，**不等于合格**；合格性仍按六条逐项判断。
- 脚本只给事实，决策理由必须由 ZCode 结合方向卡写出。

## 3. 阶段 2 · HTML 原型与覆盖（SG2）

### 3.1 执行清单

1. 只做已选定方向；不做未采用方向的 HTML。
2. 默认单页 inline React；iOS 用 `assets/ios_frame.jsx`，Android 用 `assets/android_frame.jsx`；**不手写设备外框**。
3. 真实交互：tab 切换、按钮/卡片/开关、弹层开合、返回可达、关键流程走通。
4. `P*`/`S*`/`X*` 逐项有去向：`rendered` / `deferred-native`(+理由+`native_verify`) / `not-applicable`(+理由)。
5. 缩放矩阵：`1.0/1.3/1.6/2.0`；多列、label+value 同行、固定高度结构**必须在最大档渲染**。
6. 真实素材或阶段 3 生成，不用灰块/色块/手画 SVG 顶替。
7. 概念图的伪控件、编造数据、不可实现效果按真实产品修正，并记录修正点。
8. 机械验证：`check-ui.mjs`（含 `--click/--expect` 交互断言）、`check-contrast.py`、`check-motion.py`；退出码 1 即不得进评审。
9. 按目标视口截图作基准图，命名与 `P*`/`S*` 对齐。
10. **原生平台语法**：导航/密度/触控反馈/表面层级按 `native-platform.md`；设备框只用现成组件；不出现网页套路。
11. **动效与反馈**：motion token + 基础动效（按压/选中/tab/弹层/加载/内容入场/结果）+ 必要的转场/共享元素；可中断、可重复触发、减少动态有降级；动效矩阵写入 `prototype-notes.md`。
12. **完整体验状态**：数据态 + 交互态 + 转场态可演；乐观更新失败回滚；完成态有下一步。状态切换不改布局骨架。

## 4. 阶段 3 · 设计评审与完善（SG3）

### 4.1 执行清单

1. 用**当前版本真实截图**（含弹层、空/错/大字体）评审，逐屏打开原图。
2. 按 `critique-guide.md` 六维 + App 三项附加检查逐条给结论；视觉层级与细节执行必须落到「构成与视觉关系判据」十条（重心/第一眼/视线路径/版式比例/字体节奏/色彩关系/形状线条/材质光/图形语言/密度与跨页），不能只写「清晰」「精致」。
3. 每条缺陷：位置（`P*`/`S*` + 屏名 + 元素）、现象、判据、严重度、改法；**客观缺陷与主观偏好分开写**。
4. 严重度：致命 / 重要 / 打磨。**致命清零**才可交接。构图/重心/视线路径若妨碍理解或主任务，按重要缺陷处理，不只算打磨。
5. 打磨环：一轮三处，**顺序固定为 构图与主角 → 层级与节奏 → 色彩/字体/材质关系 → 工艺细节**，改后重出受影响屏截图（见 `polish-loop.md`）。
6. 素材按需：复用优先 → 需要才生成 → 登记 `asset-manifest.json`。
7. 可选独立复核：只读复核子代理查截图与记录，findings 写入笔记。
8. **原生质感**：按 `native-platform.md` §9 十问查导航/密度/触控反馈/表面层级/反网页套路；按 `visual-depth.md` §8 查图层、光源、材质与跨页一致性；视觉 DNA 必须已落盘（`visual-depth.md` §6.1），否则记证据不足。
9. **动效与状态**：按 `motion-design.md` §9 看录屏/连续帧，检查方向、时长、缓动、中断、重复触发、减少动态；按 `experience-states.md` 查转场、失败回滚与完成态。静态截图不能证明动效，动效也不能替代静态评审。
10. **可选审美咨询**：ZCode 自行判断，不需要用户点名。影响面大 × 有真实新截图 × 自评仍有实质不确定，三者同时成立时，用 `review_packet.py` 生成交接包（真实截图 + sha256 + 屏幕/状态/改动），交 Copilot 的 `cognition-consult`（`--image`，单次 ≤6 张）给咨询意见；缺陷、值得保留与创造性选项合并一次问，只在有新实质产物时重问，意见逐条标 accepted/modified/rejected（见 `design-review-handoff.md`）。**跳过是正常结果**，写一句理由；只改局部细节或同批图同问题不发起。**它不改变阶段、不构成审批，缺它照常完成自评。**
