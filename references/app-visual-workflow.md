# App UI 标准流程 · 阶段细则与证据契约

> **读这份文档的时机**：开始任何 App UI 设计任务，或需要判断「这一步算不算真的做完了」时。
> **与 `SKILL.md` 的关系**：`SKILL.md` 是唯一流程权威（阶段、Gate、红线）；本文只展开每阶段的**操作细节、模板与证据格式**，不另立流程，不改变阶段顺序。
> **一句话立场**：**每个阶段都以「真实证据」结束，不以「我说做完了」结束。**

---

## 0. 流程总览

```
0 任务受理与产品理解
   ↓  design-brief.md v1（事实/约束/原生可行性/范围）
1 设计目标与假设
   ↓  design-brief.md 完整版（硬约束 / 可探索约束 / 成功标准）
2 GPT 三方向概念图
   ↓  3 张真实图片 + concept-prompts.md + concept-index.json
3 Copilot 方向选择
   ↓  direction-approved.md（身份核验 + 逐图差异 + 推荐 + 放弃成本）
4 HTML 高保真原型
   ↓  prototype/index.html + 基准截图 + prototype-notes.md
5 设计完善与素材生成/复用
   ↓  assets/ + asset-manifest.json + generation-log.md
6 App 原生实现
   ↓  原生工程 + 构建/安装日志 + 真机截图
7 真机验收与收口
   ↓  verification-report.md（PASS / PARTIAL / BLOCKED）
```

**阶段 Gate（证据门）**

| Gate | 通过条件（缺一不可） |
|---|---|
| G0 理解 | 事实有来源；项目规则已读；原生可行性已记录；范围已冻结 |
| G1 目标 | 硬/可探索约束分层；成功标准可判定；假设已标注 |
| G2 三方向 | 3 张真实、可解码、同比例、结构可辨、硬约束不破 |
| G3 方向 | 3 张图在 Copilot 请求内；身份核验通过；有明确推荐 + 逐图差异 + 理由 + 放弃成本 |
| G4 原型 | 真实渲染；控制台 0 error；状态/对比度/触控达标；与选定方向的偏差已记录 |
| G5 素材 | 每张素材有来源、sha256、消费者；无未决临时图；无秘密 |
| G6 原生 | 构建成功；装到真机；可启动；关键流程可走 |
| G7 验收 | 验收矩阵逐项有本轮真实证据；结论三态；未验证项已标注 |

**Gate 不是审批仪式**：不需要每阶段停轮等用户点头。它要求的是「该阶段结束时，证据真的存在」。只有**方向选择**必须由 Copilot 裁决（阶段 3），用户仍可否决。

## 1. 阶段 0 · 任务受理与产品理解

### 1.1 必做清单

- [ ] 读项目 `AGENTS.md` / `CLAUDE.md` / 设计规范 / 现有 token
- [ ] 看现有界面、代码、真实素材与截图；确认项目身份与工作区
- [ ] 涉及具体产品/技术/版本/规格 → 先查权威来源，写入 brief 的「事实」节
- [ ] 回答产品三问：谁在用 / 要完成什么 / 系统承担哪部分复杂性
- [ ] 原生可行性前置检查（§1.2）
- [ ] 范围冻结：本次不做什么；不擅自加页面/功能/商业化机制
- [ ] 列出未确认假设（`ASSUMPTION`），能问用户只问阻塞项

### 1.2 原生可行性前置检查（不得推迟到阶段 6）

| 维度 | 要确认什么 | 做不到的后果 |
|---|---|---|
| 平台 | iOS / Android / 双端；最低系统版本 | 双端差异会影响导航、系统栏、控件形态 |
| 字体 | 中文/数字/西文字族是否可用；是否需要内嵌字体 | 概念图里的字体可能根本不可用 |
| 系统 UI | 状态栏、导航栏、手势条、安全区、键盘 | 首屏内容被系统栏遮挡是常见返工 |
| 密度 | Android dp/sp、iOS pt；目标设备 dpi | CSS px 直接照搬会整体偏大/偏小 |
| 触控 | 最小触控目标（Android 48dp / iOS 44pt） | 概念图里的小按钮不可用 |
| 导航 | 平台惯例（返回、Tab、抽屉、手势） | 自定义导航可能违背平台预期 |
| 权限 | 相机/定位/通知/健康等权限的时机与文案 | 权限弹窗会打断核心流程 |
| 性能 | 大图、模糊、实时阴影、列表规模 | 概念图可以画，原生跑不动 |
| 素材 | 图标矢量化、位图格式、透明、深色模式变体 | 后期重做素材成本高 |

**原则**：概念图可以探索，但**不能把平台根本做不到的东西画成方向卖点**。做不到的要在 brief 里写明替代方案。

## 2. 阶段 1 · 设计目标与假设

阶段 1 不是再写一份长文档，而是把阶段 0 的输入**收敛成三个方向可共用的探索契约**：

1. **硬约束**逐条可核对（品牌色、必须保留的业务规则、平台限制、无障碍门槛）。
2. **可探索约束**明确哪些地方允许方向自由诠释（布局、信息组织、视觉母题、气质）。
3. **成功标准**可判定（不是「好看」，而是「首屏 3 秒能看懂今天该做什么」「核心操作 2 步内完成」）。
4. **假设**全部标 `ASSUMPTION`；影响方向正确性的假设要么问用户，要么在交付时明确风险。

**写薄的典型症状**：三个方向都在换皮、HTML 阶段才发现业务规则没处放、原生阶段才发现字体不可用。出现任一症状，回到阶段 0/1 补，不要硬做。

## 3. 阶段 2 · GPT 三方向概念图

### 3.1 什么叫「实质不同的三个方向」

差异必须至少落在以下两处，且三张图一眼能看出结构不同：

| 维度 | 可以怎么不同 | 不算差异 |
|---|---|---|
| **布局骨架** | 单列 / 双列 / 卡片流 / 时间轴 / 地图为主 / 对话为主 | 只换间距、圆角 |
| **信息组织** | 首页先给结论 / 先给过程 / 先给行动；导航层级 1 层 vs 2 层 | 只换排序 |
| **视觉母题** | 从内容长出的独特结构或隐喻（仪表盘、日记页、路线图、票据） | 只换配色、字体 |
| **交互模型** | 浏览优先 / 对话优先 / 任务清单优先 / 地图优先 | 只换按钮样式 |

**三个方向都必须遵守**：产品原则、硬约束、原生可行性。方向不是「三种风格」，是「三种对同一需求的结构性回答」。

### 3.2 三个方向的取材逻辑（各写各的 prompt）

1. **风格库锚定**：从 `references/design-styles.md` 的 App 区/东亚区抽一个风格名，写进 prompt 的方向段。
2. **现实参照**：先核实真实网站/产品存在，再把它可迁移的设计语言写成结构描述（不要只写品牌名）。
3. **最佳设计师/工作室**：写真名 + 其设计哲学 + 要解决的具体问题，不写形容词堆。

三种逻辑可以混用，但**每个方向只能有一个主锚点**；同一任务的三张图不要都用同一种逻辑，否则容易趋同。

### 3.3 方向图 prompt 五段结构

```text
1) 任务块（三方向逐字共用）：产品定位 / 目标用户与场景 / 本页核心问题 /
   用户最重要的信息与操作 / 业务规则与平台硬约束（含本页禁止出现的编造数据、假定状态与伪控件）
2) 原则转译块（三方向逐字共用）：有用 / 好懂 / 舒服 / 有意义 各落成 1–2 条本页可检查的要求
3) 载体与比例：App 竖版界面概念图，单屏/3 屏并排，比例 2:3
4) 方向块（各方向不同）：方向名与主锚点、结构骨架、生成意图
5) 不可迁移声明 + 图内文字：图内文字为示意，不作文案与精确规格依据；
   描述性文字用中文；不出现外文 nameplate/水印/签名
```

**共用块不得改写**：任务块与原则转译块在三张 prompt 里逐字相同，差异只允许出现在方向块。为了「看起来不同」增加、删除或改写业务功能、数据口径、硬约束，都不算方向，只算违约。

**原则转译怎么写**（每条都要能在图里检查，或明确留给后续阶段验证；不写原则名称）：

| 原则 | 不合格（只有原则名/口号） | 合格（本页可检查） |
|---|---|---|
| **有用** | 「满足用户需求」 | 「第一眼是今天可读的一篇；`开始阅读` 是唯一主按钮，不被装饰或统计抢占」 |
| **好懂** | 「层级清晰」 | 「顺序固定：可用时长 → 文章标题 → 真实阅读状态 → 开始阅读；其他文章入口不重复成两个同权重入口」 |
| **舒服** | 「简约舒适」 | 「正文可读、触控区足够大；信息密度按内容需要，不靠大留白凑气质；封面缺失时标题、时长、入口仍成立」 |
| **有意义** | 「体现成长感」 | 「本版不做签到/积分/进度百分比；只在有真实记录时显示续读，不编造完成度」 |

转译块里区分两类要求：**图上可检查**（信息顺序、层级、文案与控件可见性、是否出现编造数据/未授权机制）写进 prompt；**只能在 HTML/原生阶段验证**（真实交互、对比度实测、触控命中、业务逻辑）写进 `design-brief.md` 与阶段 3 的待验证项，不当成图片义务。

**必须写结构骨架**：方向图的用途是让 Copilot 比较「哪个结构更适合这个产品」，只给情绪无法比较。**必须写不可迁移声明**：模型会臆造文字与控件，不声明就会被当成文案与规格。

**位置类要求用结构表达，不用百分比坐标**：要让主按钮落在下半部 / 拇指区，写「固定在底部的操作区」这类结构，不要只写「按钮在 55% 处」。2026-11-10 读点心三方向实测：只给纵向百分比时模型会把 CTA 紧跟推荐区上提（连续两轮 40–52%），改成底部固定操作区后 A/B 一次到位（83–96%）。图上位置能不能算合格，仍以可见像素为准，不能拿 prompt 里的百分比当已满足。

**不要写**：`Subject:` / `Style:` / `Constraints:` 伪结构；英文段落式 prompt；一堆形容词；**出版物/厂商品牌名**（如出版社系列名、产品商标，会被画成 nameplate）。设计师名、流派与风格名可以写，但必须紧跟可迁移的结构描述（方向块要求），且第 5 段的 nameplate 声明不能省。**视觉锚点由本产品需求决定**：先前任务用过的风格只是历史，不构成以后任务的默认三方向。

### 3.4 生成执行

```bash
# 0) 零成本核验接口（只证明接口可用，不等于出图成功）
python3 scripts/zcode_image.py --health

# 1) 逐张串行生成（同尺寸请求、同模型）
python3 scripts/zcode_image.py \
  --prompt "<方向A prompt>" \
  --out design-demos/<task>/concepts/A.png --size 1024x1536 --fit contain

python3 scripts/zcode_image.py \
  --prompt "<方向B prompt>" \
  --out design-demos/<task>/concepts/B.png --size 1024x1536 --fit contain

python3 scripts/zcode_image.py \
  --prompt "<方向C prompt>" \
  --out design-demos/<task>/concepts/C.png --size 1024x1536 --fit contain
```

- **串行**，一次一张；失败先读错误，按 `references/image-generation.md` 的失败树处理。
- `--size` 只是请求；CPA 可能自选画布，最终像素由 `--fit` 适配。**三张用同一请求尺寸**，保证并排可比。
- **真实出图成功才算 G2 通过**；`--health` 通过不代表能出图。
- 生图不可用：报告并暂停；可交付完整 prompt，让用户在外部真实出图后交回文件。

### 3.5 逐张自检

- [ ] 文件存在、可解码、不是 0 字节/截断
- [ ] 三张同比例/同尺寸；并排看不出明显尺寸差
- [ ] 三张结构骨架一眼可辨不同，不是只换颜色
- [ ] 任务块与原则转译块在三张 prompt 中逐字一致；差异只在方向块
- [ ] 转译块每条约一条可检查要求，没有「有用 / 好懂」单独成句
- [ ] 每张都写了不可迁移声明；图内文字没有被当成文案
- [ ] 硬约束没有被突破（业务规则、必须保留的业务结构、平台可行性、未授权机制）
- [ ] 图内没有编造计数、假定用户已设置过的计划或伪控件
- [ ] 没有明显 AI slop（紫渐变、emoji 图标、假数据仪表盘、伪 chrome）

### 3.6 记录格式

`concept-prompts.md`：**共用任务块与原则转译块先写一次**，再按方向各记一段「方向名、主锚点、方向块全文、完整 prompt、生成命令、失败重试记录」。

`concept-index.json`：

## 4. 阶段 3 · Copilot 方向选择

### 4.1 原则

- **必须看真实像素**：三张图都作为 `--image` 进入证据包，由 `call_gpt.py` 内联为真实 `input_image`。
- **必须可绑定**：请求、图片清单、回复、身份核验记录能互相对上。
- **必须失败关闭**：任何一项证据不成立，就不能把回复当裁决。
- **不是正式 REVIEW**：用 `CONSULT`；不建 REVIEW 台账、不声称 G3、不替代用户决策。
- **不伪造**：不得由执行 agent 先自选、再让 Copilot「背书」；不得把文字总结当图片证据；不得编造 Copilot 回复。

### 4.2 请求文件模板

`.designwise/direction-request.md`：

```markdown
# App 设计方向选择请求

## 产品背景
- 产品/功能：
- 目标用户与场景：
- 核心任务：
- 产品定位与本次目标：

## 本页设计目标
- 本页核心问题：
- 用户最重要的信息与操作：
- 原则转译（与三个 prompt 共用，逐条可检查）：
  - 有用：
  - 好懂：
  - 舒服：
  - 有意义：

## 必须遵守的硬约束
- 品牌/视觉资产：
- 平台与系统版本：
- 业务规则 / 数据口径：
- 无障碍 / 法务 / 隐私：

## 成功标准
- ...

## 三个方向
### A · <方向名>
- 生成意图：为什么这个结构服务这类用户与场景
- 结构骨架：
- 信息组织：
- 视觉母题：
- 预期优势：
- 已知代价：

### B · <方向名>
...

### C · <方向名>
...

## 请回答（按三步，不得跳过第一步）
1. **合格性**：逐方向给出「合格 / 不合格 + 具体依据」。检查核心用户需求、信息与操作是否清晰、严重可用性或可读性问题、是否违反产品规则、是否出现不必要的游戏化/虚假数据/诱导性设计、实现可能性；并区分哪些问题图片可证实、哪些要等 HTML/原生阶段验证。
2. **比较**：只在合格方向里选综合最佳——选哪个方向、逐图差异、选择理由、放弃方向的机会成本、主要风险、进入 HTML 前必须修正的点；两个方向都成立需用户拍板时说明分歧点。
3. **全部拒绝**：三个方向都违反关键产品原则或必要约束时，明确不合格原因，并给出可执行的 prompt 修正建议（改哪条任务块/转译块/方向块、只重出哪些方向）；不要选「最不差」。
```

**图片说明**：每张 `--image` 后的 `::` 只写「方向 id + 方向名 + 结构定位」，不要写长结论，避免用文字替图说话。

**转译块一致性**：请求里的「原则转译」必须与三张 prompt 的转译块是同一份内容，不得为了「让 Copilot 好判断」另写一套更宽松的说法；方向块里的生成意图要说明这个结构为什么服务当前用户与场景，而不是「这是一种风格」。

### 4.3 证据桥接与调用

```bash

  --goal-file .designwise/direction-request.md \
  --image design-demos/<task>/concepts/A.png::A · <方向名> · <结构定位> \
  --image design-demos/<task>/concepts/B.png::B · <方向名> · <结构定位> \
  --image design-demos/<task>/concepts/C.png::C · <方向名> · <结构定位> \
  --out .designwise/evidence-direction.md \
  --manifest .designwise/evidence-direction.json

python3 ~/.zcode/skills/copilot/scripts/call_gpt.py --mode CONSULT \
  --subject "<项目>-app-direction-<YYYYMMDD>" \
  --prompt-file .designwise/direction-request.md \
  --evidence .designwise/evidence-direction.md \
  --audit-log ~/.zcode/skills/copilot/.audit/copilot.jsonl \
  --out .designwise/direction-reply.md \
  --timeout 280
```

### 4.4 通过条件（逐条核验）

- [ ] 三张图都出现在证据包与请求中；图片数量 = 3
- [ ] 图片可解码、非重复（sha256 互不相同）
- [ ] 请求包含与本页共用的任务块、原则转译块与各方向生成意图（不是只有成功率/风格词）
- [ ] 调用成功；模型身份核验通过（审计记录 `model_identity_ok=true`）
- [ ] 回复**先逐方向给出合格性结论**（合格 / 不合格 + 依据），再在合格方向中给出**一个推荐方向**
- [ ] 推荐含逐图差异、理由、放弃成本、风险；全部不合格时给出可执行的 prompt 修正建议，没有选「最不差」
- [ ] 回复没有出现「看不到图 / 无法判断 / 只能根据文字」之类声明
- [ ] 回复不是只有泛泛评价；推荐可落地到具体结构
- [ ] 回复区分了「图片可证实的问题」与「需 HTML/原生阶段验证的问题」

### 4.5 失败关闭

| 失败 | 处理 |
|---|---|
| 图片缺失/不可解码/重复 | 补齐/重出；不得用 2 张凑 3 张 |
| 图片未进入请求 | 重建证据包并核对 manifest；不调用 |
| 身份核验失败/未知 | 停止；报告；不采用回复 |
| 回复承认看不到图 | 视为无效裁决；报告 |
| 只有泛泛评价、无明确推荐 | 补证据/改请求后重试；不得自行选一个当结果 |
| 未做合格性判断、直接挑「最不差」 | 视为无效裁决；按三步重问，不把「最不差」当选择 |
| 三个方向全部不合格 | 按修正建议改 prompt、只重出受影响方向再送选；不设固定轮次，不重复无信息增量的生成；原因指向需求本身时与用户/项目侧确认目标 |
| Copilot 整体不可用 | **BLOCKED**：写明缺什么、需要什么条件；不替代裁决 |

## 5. 阶段 4 · HTML 高保真原型

### 5.1 目标

HTML 原型是**选定方向的视觉与交互基准**，不是产品实现。它要回答：

- 选定方向的视觉意图是否真的成立？
- 信息层级、导航、核心任务是否走得通？
- 状态、文案、数据是否真实？
- 交互是否有死控件？

### 5.2 架构与设备框

| 场景 | 架构 |
|---|---|
| 单人做 4–6 屏（主流） | 单页 inline React（库可本地 vendor），`file://` 双击可开 |
| >1000 行难维护 | 拆 `components.jsx` + `data.js`，附 `python3 -m http.server` 启动说明 |
| 多 agent 并行 | 每屏独立 HTML + `index.html` iframe 聚合 |

- iOS 必须用 `assets/ios_frame.jsx`；Android 用 `assets/android_frame.jsx`。
- **禁止手写** Dynamic Island、状态栏、Home Indicator、设备外框。
- 本地图片 base64 内嵌；引用外部图片必须能解释为什么（例如真实品牌资产 CDN 不可内嵌时）。

### 5.3 屏幕与交互

- 默认**平铺 4–6 个主界面，每台可交互**：tab 可切、按钮/卡片/开关可点、能弹层。
- 每台是独立迷你状态机，初始落在不同主界面；tab 切换后能互相到达。
- 用户明确要「单流程 demo」时才单台；用户明确要「静态看 layout」时才纯静态。
- 同一方向可以包含完整页面流程、多状态、多尺寸适配；**方向数量不影响交付物数量**。

### 5.4 忠实度与概念偏差

- 目标是还原**视觉意图**，不是像素级复制概念图。
- **概念图不是 UI 真相**：以下必须按真实产品修正，并写入 `prototype-notes.md`：
  - 图内文字是示意，不能当文案；
  - 伪控件/假交互必须变成真实可点或删除；
  - 不可实现的阴影/模糊/3D 效果换成平台可行方案；
  - 不可达的对比度必须调整；
  - 错误的信息架构必须纠正。
- 视觉价值依赖图片时，用真实素材或阶段 5 生成验证素材；不得用灰块/色块/手画 SVG 顶替。

### 5.5 状态与内容

- 每页至少考虑：默认 / 加载 / 空 / 错误 / 数据不足。
- 真实文案与真实数据口径；没有真实数据就写诚实的「数据积累中」「待接入」，不编造看起来像数据的假数据。
- 触控目标 ≥48dp（Android）/ ≥44pt（iOS）；正文 ≥14，标签 ≥12；对比度按三档。

### 5.6 机械验证

```bash
node scripts/check-ui.mjs prototype/index.html
python3 scripts/check-contrast.py pairs.json
# Playwright：进入详情 / 关键操作 / tab 切换，pageerror 必须为 0
```

- `check-ui.mjs` 查结构、溢出、图片引用、控制台错误；CSS px 不能直接证明 Android 48dp。
- `check-contrast.py` 输出逐对实测表；档 ①/② 不合格阻断。
- Playwright 3 项真实点击；有交互 bug 先修再交付。
- 按目标设备视口（如 1080×1920 @3x 对应 CSS 360×640）截图，存 `prototype/screenshots/` 作为基准图。

```markdown
|---|---|---|---|
```

## 6. 阶段 5 · 设计完善与素材生成/复用

### 6.1 循环

```
选定方向 + HTML 原型
  → 识别缺什么视觉资产（插画/背景/装饰/局部元素/图标视觉稿）
  → 先查复用（manifest / 项目已有 / 概念图可提取部分）
  → 能原生实现（CSS/SVG/矢量）就不生图
  → 需要生成 → 写 prompt → 生成 → 校验 → 登记
  → 替换原型中的临时素材 → 复验视觉一致性
```

### 6.2 素材三态

| 状态 | 用途 | 能不能进产品 |
|---|---|---|
| 参考图 | 判断输入，可作 `--ref` | 否 |
| 概念图 | 方向比较 | **否**（只能提取视觉语言，不能当正式素材） |
| 正式素材 | 产品/原生实现 | 是；必须登记来源与许可 |

### 6.3 复用优先

- 同一视觉元素在概念图、HTML、原生三处尽量复用同一素材或同一矢量化实现。
- 不为局部微小差异重复生成；需要变体时登记为同一资产 id 的变体。
- 替换/删除素材前查 manifest 的消费者，不留悬空引用。

### 6.4 一致性

- 参考图、尺寸、裁切、视觉语言与选定方向一致。
- 生成素材与真实品牌资产同时出现时，生成物不得冒充真实产品/品牌图。
- 图标优先矢量化；复杂插画/背景/装饰才用位图。
- 透明、压缩、格式、色彩空间按原生要求处理；记录转换过程。

### 6.5 清单

`asset-manifest.json` 是唯一事实源，结构见 `references/image-assets.md`。最低字段：

```json
{
  "assets": [
    {
      "id": "bg-home-hero",
      "file": "assets/images/<asset-id>.png",
      "sha256": "...",
      "type": "background",
      "source": "generated",
      "provenance": {"model": "gpt-image-2.5", "prompt_file": "...", "ref": null},
      "variants": [{"size": "1080x1920", "crop": "center", "format": "png"}],
      "consumers": ["prototype/index.html", "android:home"],
      "license": "generated-for-project",
      "status": "final"
    }
  ]
}
```

**登记纪律**：`status=temp` 的素材不得进入交付包；`status=final` 必须有来源、sha256、消费者；没有来源的素材不得标 final。

## 7. 阶段 6 · App 原生实现

### 7.1 交付包（规格，不是截图）

目录 `handoff/`：

```
handoff/
├── README.md               # 产物性质、技术栈、清单勾选
├── structure.md            # 页面/导航/状态入口/信息层级
├── design-tokens.md        # 色彩/字体/间距/圆角/阴影/动效（给值）
├── states-interactions.md  # 状态矩阵与交互行为
├── copy-data.md            # 真实文案与数据口径
├── assets.md               # 素材清单与引用关系
├── adaptation-a11y.md      # 适配/字体缩放/对比度/触控/无障碍
└── baselines/              # 关键页面基准图（PNG，来自真实渲染）
```

完整逐项规格见 `references/design-handoff.md`。

### 7.2 原生转译

| 设计侧 | Android | iOS |
|---|---|---|
| 色值 | `colors.xml` / Compose `Color` | Asset Catalog / SwiftUI `Color` |
| 字号 | `sp`；`dimens.xml` / Compose `sp` | `pt`；Dynamic Type |
| 间距 | `dp`；`dimens.xml` | `pt`；布局常量 |
| 圆角/阴影 | shape / elevation | cornerRadius / shadow |
| 图标 | VectorDrawable | SF Symbols / PDF vector |
| 图片 | drawable / `CENTER_CROP` | Asset Catalog / `scaleAspectFill` |
| 触控 | ≥48dp | ≥44pt |
| 系统 UI | status/nav bar、insets、edge-to-edge | safe area、home indicator |
| 深色模式 | `values-night` | semantic colors / dark variant |
| 字体缩放 | `sp` + 布局自适应 | Dynamic Type |

**硬要求**：

- CSS px 不直接等于 dp/sp；按目标设备密度与设计基准换算，并在真机核对。
- 系统栏、安全区、键盘、字体缩放、深色模式、横竖屏按平台规范处理。
- **禁止把原型 HTML 塞进 App**；WebView 只能用于明确的产品需求，不能当设计实现捷径。
- 素材按原生要求导出：密度桶、透明、格式、深色变体；裁切焦点与 CSS `cover` 不是同一件事。

### 7.3 构建、安装与取证

- 用项目既有工具链构建；不改无关项目。
- 真机装包只走宿主授权入口（`~/.zcode/skills/app-testing/runtime/mi6-verify/adb-auto-install.sh`）；**禁止裸 `adb install`**；多台设备在线即停止。
- 记录：设备型号、系统版本/API、屏幕密度、构建 hash、安装日志、启动截图、关键流程截图/录屏。
- 没有真机/工具链：设计交付照常，原生与真机验收标 `PARTIAL`/`BLOCKED`；不用模拟器截图冒充真机。

## 8. 阶段 7 · 真机验收与收口

### 8.1 验收矩阵

| # | 维度 | 判据 | 证据 |
|---|---|---|---|
| 1 | 方向一致性 | 继承选定方向的视觉意图 | 真机截图 vs 基准图 |
| 2 | 布局/信息层级 | 首屏主角、导航、区块比例正确；无溢出/遮挡 | 真机截图 |
| 3 | 字体/排版 | 层级成立；1.0/1.3 字体缩放不截断 | 截图 + 设置记录 |
| 4 | 色彩/对比度 | 正文 ≥4.5:1；图标/图形 ≥3:1 | 逐对实测表 |
| 5 | 素材 | 与清单一致；无拉伸/错图/低清 | 截图 + manifest |
| 6 | 状态 | 默认/加载/空/错误/数据不足齐全 | 逐态截图 |
| 7 | 真实数据 | 数值/文案等于真实口径；幻觉为 0 | 数据核对 |
| 8 | 触控/交互 | 目标达标；关键操作可完成；无死控件 | 操作记录/录屏 |
| 9 | 平台规范 | 系统栏/返回/权限/深色/横竖屏 | 截图 |
| 10 | 性能/稳定性 | 无崩溃；可测卡顿有记录 | logcat/启动日志 |

### 8.2 修复循环

```
发现偏差 → 判断是设计错误还是实现错误
  → 设计错误（规格缺失/矛盾）→ 改 handoff/原型，再改实现
  → 实现错误（没按规格做）→ 只改实现
  → 定向修复被点名项 → 复验受影响条件 → 回到验收矩阵
```

**不推倒重来，不无限循环**：风格偏好、措辞偏好不算实质缺陷；修到验收矩阵不再有阻断项即收口。

### 8.3 结论三态

- **PASS**：目标达成、验收矩阵逐项有本轮真实证据、无阻断项。
- **PARTIAL**：仍有可在原授权内解决的问题；继续推进，不当作终点。
- **BLOCKED**：缺授权、缺设备/工具链、缺用户决策或真实外部限制；写明缺什么、需要什么条件。

**未验证项不得写成通过。** 模拟器、静态图、源码推断都不等于真机证据。

### 8.4 `verification-report.md` 模板

```markdown

## 环境
- 设备：
- 系统/API：
- 密度：
- 构建 hash：
- 安装方式/日志：

## 验收矩阵
| # | 维度 | 结果 | 证据 | 备注 |
|---|---|---|---|---|

## 缺陷与修复
| 缺陷 | 侧（设计/实现） | 修复 | 复验 |
|---|---|---|---|

PASS / PARTIAL / BLOCKED
- 未验证项：
```

## 9. 局部迭代判定

| 改动 | 判定 | 走法 |
|---|---|---|
| 文案、间距、圆角、单组件状态、Bug、适配、替换已登记素材 | 局部 | 复用 brief + 三图 + direction-approved；从阶段 4 继续 |
| 新增/替换 token 或视觉母题 | 实质 | 重新走 0–7 |
| 信息架构/导航变化 | 实质 | 重新走 0–7 |
| 跨多页面视觉体系 | 实质 | 重新走 0–7 |
| 新核心流程/新页面类型 | 实质 | 重新走 0–7 |
| 品牌视觉探索 | 实质 | 重新走 0–7 |

**局部迭代也要过质量门**：对比度、触控、状态、真实数据、真机验证不因「只是小改」豁免。

## 10. 常见反模式

| 反模式 | 后果 | 修正 |
|---|---|---|
| 用文字描述代替三张真实图 | 方向选择没有依据 | 真实生图；不可用则暂停 |
| 三张图只换配色 | 不是三个方向 | 重写结构骨架 |
| 执行 agent 自选方向后让 Copilot 背书 | 伪造裁决 | 三张图原样送入，失败关闭 |
| 概念图直接当 UI 稿/素材 | 幻觉文字、伪控件进产品 | 转译 + 修正 + 登记 |
| HTML 只还原结构不还原视觉 | 方向丢失 | 真实素材 + 视觉还原检查 |
| 为了「像概念图」保留错误文案/假控件 | 产品错误 | 以真实产品与平台规范为准 |
| 素材复制后改一版不登记 | 孤儿文件、悬空引用 | 变体登记 + 消费者 |
| CSS px 直接当 dp | 整体尺寸错误 | 密度换算 + 真机核对 |
| 用模拟器截图冒充真机 | 伪造验收 | 真机取证或标 PARTIAL |
| 把未验证项写成通过 | 交付失真 | 三态结论 + 未验证项 |
